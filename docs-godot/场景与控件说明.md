# 场景与控件说明

本文根据 `client-godot/scenes` 下的 31 个场景及其挂载脚本整理，保留 Godot 节点名称，方便对照场景树查找。场景清单与源码阅读路线核对日期：2026-10-01；本次基准为 `f1cb9e2`，源码阅读路线覆盖 99 个 `src` GDScript 文件。

场景既包括完整窗口，也包括消息气泡、评论行等可复用组件。列表项、角色模型及部分子场景由脚本在运行时创建，因此编辑器里的静态节点树不等于完整运行界面。以下说明基于源码阅读，不代表本次进行了运行验证。

## 从场景开始读完整个客户端

建议按 **入口 → 账号 → 登录后生命周期 → 聊天界面 → 消息收发 → 历史 → 语音 → 图片 → 角色 → 设置 → 动态 → 日志 → 通用控件与平台 → 离线预览 → 原生代码与测试构建** 的顺序阅读。

下面的 R01—R15 是阅读顺序，后文 1—31 是场景查阅编号，两者用途不同。阅读某个阶段时，同时打开对应场景说明核对节点。新增界面风格页放在第 31 节，保留原有场景编号。

第一次阅读前三阶段，可以直接按独立讲义逐步操作：[R01：入口与应用装配](R01-入口与应用装配详解.md) → [R02：账号登录](R02-账号登录详解.md) → [R03：登录后生命周期](R03-登录后生命周期详解.md)。讲义包含节点定位、关键代码解释、成功/失败路径、检查理解的答案及可选断点。

只有 C 语言课后作业经验时，优先读新版 R01：它按“首次启动、无账号记录”分成26个连续小课，先解释新语法，再进入项目调用，标明返回位置，并配三个可恢复的小修改练习。R01 的运行验证独立于本文的源码索引核对，具体见 [练习验证记录](r01-evidence/README.md)。

最新更新补充消息时间来源与时间条、评论触底分页和失败重试、严格圈复杂度检查，以及拆分后的函数阅读入口。此前的界面/图标风格、未读卡片、聊天布局和构建版本输入说明继续保留。函数拆分是内部实现调整，不据此推断新增产品功能。

### 如何沿着一个节点读脚本

1. 打开 `.tscn`，先看根节点类型、`script`、`ext_resource`、实例化的子场景和导出的资源。布局数值先知道用途即可。
2. 选中本阶段列出的节点，找到脚本中的 `%NodeName`、`$NodePath` 或 `@onready` 引用。`%` 对应场景的唯一名称，不一定是根节点的直接子节点。
3. 看 `signal`、`@export`、`setup()`、`_init()` 和 `_ready()`：依赖是谁传来的，事件在哪里连接，状态在哪里初始化。不是每个脚本都有这些方法。
4. 从按钮的 `.pressed.connect(...)`、输入或滚动事件进入回调，顺着 `session/controller` 调用追到业务层。
5. 再反向追一次：业务状态或网络响应 → `changed` 等信号 → UI 刷新函数 → 节点文字、可见性、禁用状态。只读请求方向不能理解整个功能。
6. 最后看 `stop()`、`cancel()`、`_exit_tree()`、`queue_free()` 等释放路径，以及失败、重试和迟到回调如何处理。

每读完一条功能线，都回到 `application.gd` 或 `application_services.gd` 确认所有权：谁创建、谁注入、谁启动、谁停止。遇到已经读过的底层服务，只回看本次用到的方法。

本路线覆盖项目自己的场景、`src` 脚本、原生实现、资源接线和测试构建入口。`.uid`、`.import`、缓存、DLL 和图片等不是需要逐行阅读的源码；第三方 Cubism/Godot 内核需要从依赖来源继续读，不能视为本仓库已包含的全部实现。

5. [chat_time.gd](../client-godot/src/ui/chat_time.gd)：`markers()` → `seconds()` → `label()`，再看数字与日历时间解析。首条有效非系统消息显示时间；后续时间与此前最高有效时间相差至少 300 秒才再次显示，乱序时间不回退比较基线。系统消息和无效时间不参与分组。

**时间条规则：** 支持 Unix 秒/毫秒、数字字符串及带时区/小数的日历字符串；带时区或 Unix 时间按当前系统时区偏移显示，无时区日历字符串按本地墙上时间处理。当天显示 `HH:MM`，其他日期显示 `YYYY-MM-DD HH:MM`。时间条属于原消息气泡，不生成额外消息 ID，不改变阅读锚点；标记变化会使对应高度缓存失效。日期和时区显示在消息列表重算时更新。

**返回方向：** 会话发出 `changed` → `ChatView._refresh()` → 列表 `set_messages()` → 气泡 `configure/update_message()` → 更新正文与投递状态。`Caption` 只显示 `failed/uncertain` 异常；等待历史、排队、发送中和成功状态不显示额外文字，也不预留状态行高度。列表、气泡和语音行逐层接收同一 UiStyle 服务。

### R05：消息收发——把一次文字聊天追完整

**节点入口：** `Input / Send`，结果看 `Status` 和气泡 `Text / Caption`。

1. [chat_session.gd](../client-godot/src/session/chat_session.gd)：先读初始化依赖与信号、`start()`、`send_text()`、`get_messages()`；接着读 `_receive()` → `_receive_reply(payload, event_timestamp)` → `_reply_timestamp()` / `_log_reply()` / `_update_reply()` → `_present_replies()`，最后读 `_delivery_changed()` 和 `stop()`。音频、图片、历史相关方法分别在后续阶段展开。
2. [websocket_transport.gd](../client-godot/src/network/websocket_transport.gd)：`start()` → `send_event()` → `_process()` → `_handle_event()`，理解连接、收发、ACK 与断线处理。
3. [reliable_outbox.gd](../client-godot/src/network/reliable_outbox.gd)：从 `enqueue()` 和 `acknowledge()` 进入，继续读重试、超时及状态变化。文件名中的 reliable 不等于可以直接假定所有失败都能自动重发成功。
4. 回到 ChatSession 的 `_delivery_changed()` 和 ChatView 的 `_refresh()`，确认网络状态怎样映射为用户看见的消息状态。

```text
发送：Input/Send → ChatView._send → ChatSession.send_text
      → WebSocketTransport.send_event → ReliableOutbox.enqueue
      → transport._process 发包
确认：服务端 ACK → transport._handle_event → outbox.acknowledge
      → ChatSession._delivery_changed → changed → 气泡更新，成功时隐藏 Caption
接收：transport 收包 → ChatSession._receive → _receive_reply(payload, event.ts)
      → _present_replies → changed → ChatView → 气泡 Text
```

**消息时间来源：** 本地文字/图片在创建消息时记录系统 Unix 秒时间；ACK 只更新投递状态，不改变时间。助手回复首次 UUID 聚合时取事件 envelope 的有限正数 `ts`（协议毫秒，除以 1000），缺失或无效则使用本地到达时间；后续分片与重复终包不移动首次时间。历史页合并到相同 UUID 时使用历史 timestamp，但保留已有实时正文。该协议时间读取与 ChatTime 的多格式显示解析是两层不同职责。

**读完自查：** 本地消息何时出现？收到 ACK 与收到角色回复有什么区别？文本、表情、音频分片怎样按同一回复聚合？首批历史未完成时发送暂存，下一阶段补齐这个分支。
