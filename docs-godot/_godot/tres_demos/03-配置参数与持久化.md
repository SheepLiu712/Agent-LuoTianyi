# 03. `.tres` 配参数，`user://` 存用户数据

## 现有工程演示

[`dynamics.tres`](../../../client_godot/resources/platform/dynamics.tres) 把同一种脚本配置成一个专用设置对象：

```ini
[gd_resource type="Resource" load_steps=2 format=3]
[ext_resource type="Script" path="res://src/storage/godot_settings_store.gd" id="1"]
[resource]
resource_local_to_scene = true
script = ExtResource("1")
file_path = "user://dynamics-window.cfg"
```

[`godot_settings_store.gd`](../../../client_godot/src/storage/godot_settings_store.gd) 中 `@export var file_path` 对应最后一行；其 `load_settings()`、`get_value()`、`set_value()`、`save_settings()` 使用 `ConfigFile` 读写。类似的 [`framing.tres`](../../../client_godot/resources/platform/framing.tres) 和 [`preview.tres`](../../../client_godot/resources/platform/preview.tres) 复用同一个脚本，只是 `file_path` 不同。

这说明 `.tres` 中保存的是**配置路径**，用户设置的值保存在 `user://*.cfg` 中。修改 `.tres` 不等于修改已保存的用户值；调用 `save_settings()` 也不会改写 `.tres`。

## 独立练习：安全地读写一个测试配置

下面代码利用现成的 `.tres`，但先复制资源并改用测试文件名，避免覆盖真实动态窗口配置：

```gdscript
extends Node

func _ready() -> void:
	var original: Resource = load("res://resources/platform/dynamics.tres")
	var settings: Resource = original.duplicate(true)
	settings.set("file_path", "user://tres-demo-settings.cfg")

	settings.call("set_value", "demo", "volume", 75)
	var save_error = settings.call("save_settings")
	if save_error != OK:
		push_error("配置保存失败: %s" % save_error)
		return

	var reloaded: Resource = original.duplicate(true)
	reloaded.set("file_path", settings.get("file_path"))
	var load_error = reloaded.call("load_settings")
	if load_error == OK:
		print(reloaded.call("get_value", "demo", "volume", 0))
```

预期控制台打印 `75`；文件写在当前项目的 `user://` 目录。项目在 `project.godot` 中启用了自定义用户目录 `AgentLuo-Godot`。在脚本中执行 `print(ProjectSettings.globalize_path("user://"))` 可查看当前机器上的实际位置。

## 常见误区

- `res://resources/platform/dynamics.tres` 是工程资源，随应用发布；`user://dynamics-window.cfg` 是运行时用户文件。
- `resource_local_to_scene = true` 只关系到场景实例的资源隔离，不负责磁盘写入。
- 导出后的应用通常不能把用户配置写回打包在 PCK 中的 `res://*.tres`。本项目使用 `ConfigFile` 是刻意的职责划分。

## `ConfigFile` 的数据形状

项目的设置存储对象把数据分成“节”和“键”：

```gdscript
settings.call("set_value", "window", "width", 960)
settings.call("set_value", "window", "maximized", false)
settings.call("save_settings")
```

对应的配置文件大致是：

```ini
[window]

width=960
maximized=false
```

读取时要提供 fallback：

```gdscript
var width = settings.call("get_value", "window", "width", 480)
```

这样首次启动、文件缺失或某个键尚未写入时，UI 仍有确定的默认值。`load_settings()` 返回 `Error`，调用方应区分“文件不存在”和“文件损坏”等错误，而不是无条件覆盖内存中的默认值。

## 为什么资源中仍然保存 `file_path`

`godot_settings_store.gd` 是行为实现，`file_path` 是装配参数。把路径写在不同 `.tres` 中可以得到多个职责明确的实例：

| 资源 | 路径 | 使用场景 |
| --- | --- | --- |
| `dynamics.tres` | `user://dynamics-window.cfg` | 动态窗口布局 |
| `framing.tres` | `user://avatar_framing.cfg` | 角色构图 |
| `preview.tres` | `user://preview_layout.cfg` | 离线预览布局 |

若把路径硬编码进脚本，三个调用方就无法复用同一个实现；若把用户实际值写进 `.tres`，又会把运行时数据和发布资源混在一起。当前设计把这两个问题分开了。

## 失败场景 demo

```gdscript
var path := "user://tres-demo-missing.cfg"
var settings: Resource = load("res://resources/platform/dynamics.tres").duplicate(true)
settings.set("file_path", path)
var error = settings.call("load_settings")
if error != OK:
	print("首次运行，使用默认值: ", error)
	settings.call("set_value", "window", "width", 480)
```

首次运行时文件通常不存在，这是正常分支，不应显示成致命错误。保存失败则应提示用户或记录日志，并保留内存中的设置，不能假设磁盘已经成功更新。
