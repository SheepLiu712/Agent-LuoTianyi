# 02. 场景用 `.tres` 注入平台实现

## 现有工程演示

[`application.gd`](../../../client_godot/src/application.gd) 暴露了 `runtime`、`window_system`、`decoder_factory` 等 `Resource` 属性。例如：

```gdscript
@export var window_system: Resource = preload("res://src/platform/window_system.gd").new()
@export var runtime: Resource = preload("res://src/platform/runtime_environment.gd").new()
```

[`main.tscn`](../../../client_godot/scenes/main.tscn) 为这些属性选定实际资源：

```ini
[ext_resource type="Resource" path="res://resources/platform/windows.tres" id="isolation_window_system"]
[ext_resource type="Resource" path="res://resources/platform/runtime.tres" id="isolation_runtime"]

[node name="AgentLuo" type="Control"]
script = ExtResource("1_app")
runtime = ExtResource("isolation_runtime")
window_system = ExtResource("isolation_window_system")
```

**读取顺序**：场景加载 `.tres`，创建 `AgentLuo` 节点，把 `.tres` 对象赋给脚本的导出属性，然后脚本在生命周期方法中调用这些资源。脚本中的 `.new()` 是未通过场景覆盖时的默认对象，不是场景最终使用的 Windows 实现。

编辑器中打开 `main.tscn`，选中根节点 `AgentLuo`，在 Inspector 的脚本导出属性中可查看引用。拖入另一份类型兼容的资源，保存场景，Godot 会改写 `.tscn` 中的引用。当前代码把属性标注为通用 `Resource`，因此 Inspector 不会自动保证对象实现了预期接口；更换时要检查脚本方法和项目测试。

## 最小复现实验

项目还有一个范围较小的例子：[`window_chrome.gd`](../../../client_godot/src/ui/window_chrome.gd) 导出 `host`；[`window_chrome.tscn`](../../../client_godot/scenes/ui/window_chrome.tscn) 将 [`window_host.tres`](../../../client_godot/resources/platform/window_host.tres) 赋给它。用临时 `Node` 脚本检查注入结果：

```gdscript
extends Node

func _ready() -> void:
	var packed: PackedScene = load("res://scenes/ui/window_chrome.tscn")
	var chrome = packed.instantiate()
	var host: Resource = chrome.get("host")
	print(host.get_script().resource_path)
	chrome.free()
```

预期打印 `res://src/platform/desktop_window_host.gd`。此例只实例化场景，不把它加入场景树，因此不会触发 `window_chrome.gd` 的 `_enter_tree()` 中的窗口附着行为。

## 为什么不把实现路径写死在业务脚本中

项目通过 `Resource` 保存平台实现，通过 `.tscn` 选择具体对象。要替换一个实现，可调整场景资源引用，并保留脚本对稳定方法的调用。`main.tscn` 的 `windows.tres`、`runtime.tres`、`decoder.tres` 都遵循这个模式。

## Inspector 中的实际操作步骤

以 `window_chrome.tscn` 为例：

1. 打开 [`client_godot/scenes/ui/window_chrome.tscn`](../../../client_godot/scenes/ui/window_chrome.tscn)。
2. 选中 `WindowChrome` 根节点。
3. 在 Inspector 找到脚本导出的 `Host` 属性。
4. 将 `res://resources/platform/window_host.tres` 拖入资源槽。
5. 保存场景。
6. 打开场景文本，确认出现 `host = ExtResource("isolation_host")`。

拖拽动作产生两部分序列化内容：顶部的 `[ext_resource type="Resource" path="..."]` 声明文件，节点属性中的 `ExtResource(...)` 保存连接。只复制其中一部分会导致场景加载失败。

## 设计一个可替换的接口

项目的基础接口采用 `Resource` 脚本，例如 [`window_system.gd`](../../../client_godot/src/platform/window_system.gd)。一个独立练习可以简化成：

```gdscript
# res://tests/manual/message_port.gd
extends Resource

func send_message(text: String) -> Error:
	print("base: ", text)
	return OK
```

```gdscript
# res://tests/manual/console_message_port.gd
extends "res://tests/manual/message_port.gd"

@export var prefix := "demo"

func send_message(text: String) -> Error:
	print(prefix, ": ", text)
	return OK
```

场景脚本只声明：

```gdscript
@export var message_port: Resource

func submit() -> void:
	var error: Error = message_port.call("send_message", "hello")
	if error != OK:
		push_error("发送失败: %s" % error)
```

然后在 Inspector 中替换 `.tres`，业务代码不用知道具体类名。这里使用 `call()` 是因为示例属性声明为通用 `Resource`；生产代码中如果需要更强的类型检查，可将导出属性改成自定义 Resource 类型，并让实现脚本继承该类型。

## 注入失败的排查顺序

1. 看 `.tscn` 的 `ext_resource path` 是否是 `res://` 且大小写正确。
2. 看 `.tres` 的 `script` 路径是否存在，脚本是否能单独打开。
3. 看节点脚本的属性名是否和 `.tscn` 中赋值名一致。
4. 看资源脚本是否真的提供调用的方法；`Resource` 类型本身不会替你保证接口。
5. 若资源只在运行时为空，检查是否手工 `instantiate()` 了一个未保存的场景副本。

## 与 `preload` 默认值的关系

项目的 `Application` 使用类似下面的写法：

```gdscript
@export var runtime: Resource = preload("res://src/platform/runtime_environment.gd").new()
```

这提供了一个可以在没有 Inspector 注入时工作的 fallback。场景序列化的 `runtime = ExtResource("isolation_runtime")` 会覆盖默认值。调试时不要只看脚本的默认值，要同时检查实际运行的场景文件。
