## 修复政策与界限

- ACTIVE 时才允许接纳新 PCM，RECONNECTING 不放宽新入站接纳，保持现有 ACK/背压语义
- 断线时关闭 provider 输入门；已从有界队列取出但正在 push 的帧允许完成，后续已接纳帧暂停而非弹出丢弃
- 恢复成功并完成 ACTIVE 状态发布后打开门，按原队列顺序继续排空；队列容量仍为 `pcm_queue_capacity`
- RECONNECTING 期间 provider 已产生的业务事件由原单消费者暂停持有，恢复后按 provider 顺序处理；不另建 Stage 事件队列
- provider 新增独立 `wait_failure()` 终止信号，不与业务事件 FIFO 争用消费者；它只保存单个终止事实，因此空间上限为一，不会为寻找 failure 无限读取或绕开 provider 原有有界队列
- Aliyun 原业务事件缓冲继续受 `event_queue_size` 限制并保持 FIFO；终止事实由 `_set_terminal` 同时唤醒独立 waiter，即使普通队列已满或 Stage 正暂停一个业务事件，也不会发生 head-of-line 阻塞
- Stage 持有一个 owned failure waiter；normal close 返回 `None`，failure 立即按 `PROVIDER_FAILED` 终止；cleanup 会取消并等待 event consumer、failure waiter、PCM drain 等全部 owned task
- `TurnCompleted` 保留事件到达时的单调时钟与时间戳；若到达时连接不连续，永久标记 FIRST_AUDIO 失格，不在恢复后重置计时起点
- 恢复后真正到达的新轮次仍可正常记录 FIRST_AUDIO
- `SpeechStarted`、`SpeechStopped`、`TurnInvalid` 使用同一门禁及原有 item identity 规则；晚到旧事件不会越过恢复握手产生业务输出
- `ProviderFailed` 不等待恢复、不等待三秒期限；`resume()` 在同一 lifecycle lock 内先检查终止请求，已知 failure 不得转 ACTIVE、打开输入门或返回成功
- `can_resume()` 同样排除已有终止请求，使公开 Manager/Adapter admission 在生成 `call.resumed`、提交 cursor 或绑定新代际前失败
- 超时、失败或挂断时既有 `_cleanup` 取消消费者、清空有界 PCM 队列、关闭 provider/Context 并释放 ownership；暂停事件不会兑现
- Adapter 已有 `_PreparedTransport` 在 resume commit 期间有界缓存新业务输出，并保证 `call.resumed -> replay -> new business output`；本修复在 Stage 收到 ACTIVE 后才放行 provider 输入，因此不会把新生成输出插到 replay 前

## 中文 PR 草稿

### 标题

修复通话恢复期已接纳 PCM 与完成轮次丢失

### 说明

Refs #325

触发条件：服务端已接纳多帧 PCM，provider 首次 push 阻塞时连接断开；恢复窗口内 provider 完成用户轮次。

被违反的不变量：已接纳 PCM 在成功恢复后应按序恰好一次送达 provider；恢复期有效完成轮次应恰好一次进入 Agent；跨断线轮次不得伪装为连续连接 FIRST_AUDIO 成功样本。

根因：PCM drain 在出队后按瞬时 ACTIVE 状态决定是否 push，断线时会直接丢弃该帧；`_on_turn` 又以 ACTIVE 门直接忽略 RECONNECTING 期间事件。

修复：在 CallStage 内增加恢复门，暂停既有有界 PCM drain 和业务事件消费；provider 提供独立单事实终止信号，使 failure 不被暂停业务事件或已满 FIFO 阻塞。成功恢复后按原顺序继续，终止则由既有 cleanup 丢弃并清理。完成事件保存到达时刻和连接连续性，兼容 #330 FIRST_AUDIO 政策。未改变 wire、ACK 或 Adapter 公开契约。

验证：受影响 Stage/Adapter/binding/provider 回归 `141 passed`；Ruff 0.14.10、Black 26.5.1、架构检查与 diff 检查通过。未验证真实 provider、付费服务和真机。
