## 当前恢复契约

正常 `ENDED + CONNECTED` 记录只要 `summary=PENDING` 或 `maintenance=PENDING`，仍会进入恢复候选；不能在查询层按 digest 是否存在排除整类 normal pending。

恢复层按持久事实区分：

1. **无 normal claim digest，存在合法 deterministic Conversation winner**
   - 只验证 winner 并修复 summary CAS
   - 保留原概要，不调用 provider，不写失败 fallback
   - maintenance 只依据可验证的真实 projection 或既有终态处理

2. **无 normal claim digest，且没有合法 winner**
   - 安全返回 `skipped`
   - 不创建 Conversation，不 CAS 假成功
   - 不 claim recovery digest，不把记录改成 `SYSTEM_FAILURE`
   - 记录可以在后续启动再次被安全扫描并再次 `skipped`

3. **存在 normal claim digest，且 projection 为空**
   - 允许生成安全的 `FAILED_CALL_SUMMARY` Conversation
   - 没有 verified completed batch 时，maintenance 收敛为 `FAILED`
   - 完成后下一次启动 `scanned=0`

4. **稳定 normal FAILED**
   - 不重新进入扫描，保留 CR5 的稳定失败契约

5. **SYSTEM_FAILURE / recovery digest**
   - 继续使用 `INTERRUPTED_CALL_SUMMARY`
   - 保持原有 recovery digest、冲突检查和恢复语义

## 当前生产修复

- `CallSettlement` 保持总预算 15 秒，不新增产品配置；短测试预算按相同比例缩放
- maintenance retry 共享同一 phase 剩余预算，不重新获取完整时间
- maintenance 取消后等待 handler 和 owned cleanup 真正停止，不产生 detached 后台任务
- summary 超时或执行失败使用 `FAILED_CALL_SUMMARY`；常量位于 `domain.call`，Stage 不反向依赖 Agent
- summary Conversation 与 maintenance ledger 改为窄串行持久化，不再并行 `gather`
- Conversation 写入失败且无合法 winner 时，summary ledger 显式转为 `FAILED`
- deterministic Conversation ID、winner 验证、唯一键竞争后的 winner 重读和冲突处理保持不变
- verified completed batch 优先，未成功维护不会被虚假推进为成功

## Timeout 与所有权边界

phase timeout 会取消 Agent coroutine，并等待其清理完成。如果 handler 已进入 `complete_owned(asyncio.to_thread(...))` 的 SQL/thread 写入，Python 无法强杀已启动的线程写入；系统会继续保持 Context 和 FINALIZING 占用，等待 owned write 真正返回，即使实际耗时超过 15 秒目标，也不会提前释放占用或留下 detached 写入。

因此 15 秒是阶段和总目标预算，不是对已进入 owned SQL/thread 的强杀保证。
