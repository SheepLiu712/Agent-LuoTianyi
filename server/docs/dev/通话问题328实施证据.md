## 实现策略

Attempt 1 的中间候选曾在 RECONNECTING 到期时固定触发 TIME_LIMIT，且配置只在 direct constructor 测试中注入、未进入生产 Manager 装配；本轮已用下述状态等待和正式配置路径替换，旧行为不作为交付结论。

- `CallStage` 接通时创建唯一 owned `call-time-limit` task
- 默认 `time_limit_seconds=1800`、`time_limit_warning_seconds=30`；均要求有限值，且 `0 <= warning < limit`
- timer 使用 `_connected_monotonic`，不读取 wall clock；测试唤醒端口只通知重算，不改变生产时基
- 提示点只提交一次 `CallTimeLimitWarning` 正式 Stage stimulus
- Agent handler 产生固定 CALL `Say` ActionPlan，不调用生成模型、不创建第二 Context、不增加 wire 字段
- 提示通过正常 Agent → plan → realize → sink → transport 链输出，不误建用户正式 turn，也不参与 FIRST_AUDIO 用户轮次指标
- 提示 handle 独立运行；生成、发送失败或阻塞不会阻塞 hard deadline
- ACTIVE 到达 hard deadline 直接请求 `terminate(TIME_LIMIT)`；RECONNECTING 到期则等待 resume/终止状态通知，不忙轮询、不另建 detached task
- 恢复成功且 absolute deadline 已过时立即 TIME_LIMIT，并让成功恢复波动计入有效时长；恢复失败时 time-limit 不覆盖 `RECOVERY_TIMEOUT`
- 终止沿用 StageManager owned finalization、冻结快照、Context 关闭和 ownership 回收
- 提前挂断及其他终止由既有 `_cleanup` 取消并等待 timer 和提示 handle，无 detached task
- provider failure 与 deadline 竞争使用既有首次终止原因所有权；已请求 provider failure 时 TIME_LIMIT 不覆盖
- 生产配置路径为 `stage_manager.call_stage -> StageManager._call_stage_config -> _create_call_stage -> CallStage(config=...)`；ChatStage 仍只接收原 `stage` 子配置

## 日志设施失败补偿

- 最新窄审查发现：若 `_establish_open_call` 的诊断 `get_logger()` 或 `logger.error()` 自身抛异常，原顺序会跳过 control retirement，并产生未回收 control 与未检索 task exception
- 修复顺序改为：`_create_call_stage` owned 补偿返回 → identity-guarded `_retire_failed_call_control` → best-effort 日志（`Exception` 被吞）→ finally 唤醒 `_stage_available` / `_ready`
- `test_diagnostic_failure_cannot_block_invalid_config_control_retirement` 参数化覆盖 logger lookup 与 logger.error 两种故障；两例均保持 ledger FAILED、claim/lease/ownership/stage/control 索引清理，provider 未创建，并使同 request 重试返回 durable `CALL_START_FAILED`

## 中文 PR 草稿

### 标题

实现实时通话时长上限与提前提示

### 说明

Refs #328

触发条件：通话已进入 ACTIVE，单调有效时长接近或达到配置上限。

根因：`TIME_LIMIT` 只有结束原因枚举，CallStage 没有对应 owned timer，也没有通过 Agent 输出提前提示的正式刺激。

修复：CallStage 从首次 ACTIVE 起以单调时钟维护唯一提示点和硬截止点；提示通过固定 Agent ActionPlan 输出，不依赖付费生成。ACTIVE 到期强制 TIME_LIMIT；RECONNECTING 到期保留原三秒恢复机会，恢复成功后按绝对 deadline 立即判断，未恢复则保持 RECOVERY_TIMEOUT 与断线 duration 口径。生产配置由 `stage_manager.call_stage` 下传，ChatStage 配置不受影响。

验证：相关 Agent、Domain、Stage、恢复、生产配置和 Adapter 回归 `105 passed`；Ruff 0.14.10、Black 26.5.1、架构边界与 diff 检查通过。未验证真实 provider、公网、真机及真实 30 分钟等待。

## 2026-10-16 集成补修同步

- 固定 wall clock 下，ACTIVE / ENDING / ENDED 可能携带不同 payload 却共享同一 `updated_at`，导致内存与 SQLite 的严格 CAS 拒绝后续生命周期写入。补修将 ledger `updated_at` 维持为严格递增 logical version（至少前值 +1 微秒），而 `ended_at` 继续保存真实 wall clock。
- 公开 Adapter → Manager → CallStage 的 5 秒 warning / 7 秒 deadline 用例现同时覆盖 memory 与真实 SQLite，并断言四次生命周期写入严格递增、真实 `ended_at` 不被 logical version 改写。
- CAS 契约没有放宽；只修正 producer 版本生成。此提交不包含 #324、#325 网络 fixture 或 App 补修。
