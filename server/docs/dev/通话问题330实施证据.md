## 指标语义

`call.first_audio` 是服务端首包指标，不代表客户端开始播放，也不能替代端点判断延迟。

- **计量单位**：`duration_ms`，来自注入的单调时钟
- **起点**：一个有效 `TurnCompleted` 经 `FakeRealtimeSpeechSession.emit` / provider `events()` 被 `CallStage._consume_events` 接纳为正式通话轮次的时刻
- **终点**：属于该轮次的任意 `Say` response 第一个非空 canonical PCM 块成功由业务 transport 接纳的时刻。它不等同于客户端已收到或开始播放
- **每轮定义**：每个正式通话轮次至多记录一个成功样本。一个轮次内的多个 `Say`、多个 stream 和后续 PCM chunk 不会重复记录；`RECALL` 的 provisional 过渡语属于该轮次，符合 AC-06「可计入首包」的口径
- **重连排除**：`disconnect()` 会标记当时尚未记录首音频的正式轮次为不连续。即使 Adapter 在 resume 事务中缓存并随后重新投递输出，该轮次也不产生成功样本；不会在重试时重置原 `TurnCompleted` 起点。恢复成功后的新轮次正常测量；已经记录的旧轮次不会因重放重复记录。此最小安全口径避免将跨连接缓冲/重放误记成连续首包
- **其他排除**：setup 中的音频不计；没有关联正式轮次的输出不计；PCM 发送失败、输出取消或被用户打断而从未成功发送 PCM 时不产生成功样本。重试在同一轮次内：若先前未成功发送，重试的首个成功 PCM 可记录；若已经记录，不重复记录
- **标签**：仅 `result=succeeded`。没有 `call_id`、`turn_seq`、response ID、文本、转写或音频作为 metric label；观测存储仍以既有 `call_id` trace 关联

首次 PCM 的记录点位于真实 `provider → CallStage._consume_events → Agent → OutputSink → transport` 输出链上，且在 `send_pcm` 成功返回后，而非测试直接调用 metric emitter。Adapter 的 resume 事务在 `CallWebSocketAdapter._commit_resume` 中先缓存 bridge 的业务输出、提交恢复 cursor、再释放缓存输出，所以 Stage 不能只在记录瞬间检查 `ACTIVE`；本修复以轮次跨断线标记排除该污染路径。

## 确定性红绿验证

新增回归覆盖：

1. 两个 `FakeRealtimeSpeechSession.emit(TurnCompleted(...))` 轮次分别在 125 ms、250 ms 后发送首个 PCM；每轮多个 Say、stream、chunk 时，准确得到两个且仅两个 `FIRST_AUDIO` 成功样本
2. `test_successful_text_only_response_does_not_record_first_audio`：成功 `TextFinal → MessageEnd(COMPLETED) → ActionResult(COMPLETED)` 而没有 `AudioChunk` 时不记录成功样本；按现有 Stage 生命周期，轮次维持 `NOT_STARTED` / unfinished，直到终止收敛
3. 已开始生成但用户打断、从未实际发送 PCM 的 response 不记录成功样本；旧 generation 的晚到输出被拒绝，新轮次仍可正常记录
4. `test_first_audio_excludes_turns_crossing_reconnect_and_accepts_new_turn_after_resume`：生成前跨 disconnect/resume 的轮次没有成功样本；恢复后的新轮次有一个正确样本
5. `test_first_audio_remains_excluded_when_inflight_pcm_returns_after_resume`：PCM 已进入并阻塞在 transport `send_pcm` 时断线；按正式 `stage.resume()` 恢复后才允许旧 `send_pcm` 返回，旧轮次仍无样本，恢复后新轮次正常且仅一次
6. 同一轮次的首次 Say 失败后重试，首个成功 PCM 仅记录一次且仍从原 `TurnCompleted` 起点计量
