# 认知维护迁移与验收

> 范围：F2 实现计划的 CL-1（AC-15）
>
> 状态：已实现，待非作者 spec 审核。分支 `feat/call-cognitive-maintenance` 从 `0014231e` 建立，依赖 PR #269 的骨架；本变更不扩大或改写 PR #269 的范围。

## 已实现边界

- 正式聊天回复之后由 Agent 追加阈值 `CognitiveMaintenance` 行动。未达到压缩阈值时，行动返回跳过，不提取或写入长期记忆、不更新画像、不推进维护进度。
- `InteractionEnding` 由 Agent 产生唯一的结束维护行动。ChatStage 在 `realize_action_plan` 后结算；维护在提交 SQL 事务前失败或取消时不推进进度。结束维护失败和超时都不会阻止 InteractionContext 关闭；若 owned SQL 事务已经启动，则事务可能完整提交后再向调用方传播取消，取消或 timeout 不构成数据库回滚保证。
- 一个维护批次由 `(user_id, character_id, predecessor)` 唯一确定。首次写入冻结候选、画像和压缩输入，并持久化随机 `maintenance_id`；后续重试或并发竞争者读取该胜者，而不是重新运行模型生成候选或画像。
- 记忆候选按 `(maintenance_id, candidate_index)` 建立稳定正本和向量身份。正本、向量 chunk 允许至少一次重试后收敛；这不是跨模型、数据库和向量库的 exactly-once 事务承诺。
- 聊天压缩与 marker 推进由一个 SQL 事务提交。只有记忆和画像投影成功后才会尝试该提交；提交冲突或失败保留原 marker，供之后的聊天生命周期重试。
- `Reflection` 类型、处理器和 `reflection` 部署配置读取仍是兼容残留，但未在生产 Agent 路由注册。此次没有宣称它们已全部重命名或移除。

## 数据库升级与运维注意

升级前请由数据库负责人完成可恢复备份，并在副本上先验证启动和迁移。本文只说明操作边界，不替任何环境执行数据库变更。

1. **新库**：建表会创建维护批次表、聊天上下文的可空维护 marker，以及 `memory_chunks.embedding_id IS NOT NULL` 的部分唯一索引。
2. **旧库幂等升级**：旧 `conversation_contexts` 增加 `maintenance_entry_id` 后保留 `NULL`。`NULL` 只表示没有可信的成功维护记录；历史 Reflection 是否曾产生记忆或画像不可由该值判断。不能把它手工改成任意历史对话 ID；升级重复运行不会为同一列重复变更。
3. **历史重复向量身份**：迁移在创建部分唯一索引前检测非空 `embedding_id` 重复。发现重复时启动会以 `RuntimeError` 明确失败，原始 `memory_chunks` 不会被删除、合并或改写。应停止升级、保留备份并由人工核对每条重复记录的正本、向量库和业务归属，再制定经过审查的修复/回滚方案；不要直接删除任一历史行来绕过门禁。
4. **回滚**：新增表、marker 和索引均涉及已写入的维护事实。代码回滚前必须确认旧版本能够容忍这些 schema 对象；若要回滚数据，先从升级前备份恢复或使用经审查的专用迁移，不要依据本说明手工删除维护批次、marker 或记忆历史。
5. **重置**：现有用户对话重置会删除该用户对话、上下文和维护批次，因此 marker 随上下文消失；重置后新的对话从尚未维护状态重新开始。
