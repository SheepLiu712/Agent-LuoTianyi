# CL-10 待决事项

## SQL 时间语义（已确定）

### 已选工程边界

`CallSessionRecord` 的 CL-2 既有契约同时允许 timezone-aware 和 naive `datetime`。SQLite `DateTime` 不保存时区；SQL repository 若自动调用 `astimezone()`，会把 naive 值按运行主机本地时区解释，同一账本在不同时区部署时可能得到不同结果。`list_stale(before=...)` 同样不能隐式把 cutoff 当成本地时间转换。

用户已确认服务端公开账本边界固定使用 UTC+8 北京时间。所有输入必须为 timezone-aware；其他 offset 表示的同一 instant 显式归一化到固定 `timezone(timedelta(hours=8))`。SQLite 保存 naive Beijing，读取时恢复固定 `+08:00`。naive 输入和 stale cutoff 一律拒绝，不依赖宿主时区。

### 兼容边界

该约束只深化新建的 `CallSessionRecord` / `CallSessionRepository`，不修改 CL-2 legacy naive datetime 接口。后续 Stage 接线负责把其时间事实显式转换到 aware 北京边界。持续时间仍应由单调时钟计算，不能通过 wall-clock datetime 相减替代。

## 并行结算边界

summary 与 maintenance 是两条独立 settlement lane，仅允许在 `ENDED` 账本执行，不得通过通用整行 lifecycle CAS 更新。repository 提供各自的窄 status CAS，只更新 lane-owned 字段，并以数据库原子 `max(current, candidate)` 语义维护共享 `updated_at`。`PENDING -> FAILED/SUCCEEDED` 与 `FAILED -> SUCCEEDED` 是当前允许的最小重试图；`SUCCEEDED` 不得回退。maintenance 失败不推进 turn seq，成功进度不得倒退；summary 成功只接受 UUID conversation identity，失败必须不带 conversation ID。后续结算应用仍待实现与非作者审核。

通用 lifecycle CAS 的实际更新要求数据库当前 `updated_at < candidate.updated_at`。未命中后读取当前记录：durable identity 冲突稳定拒绝；candidate 时间不晚于当前且 lifecycle-owned payload 完全一致时作为幂等成功，即使 expected state 已是旧状态；同时间不同 payload 或更旧不同 payload 返回 `False`。比较明确排除 summary/maintenance status、conversation ID、maintenance turn seq 及 settlement 独立推进的共享 `updated_at`，因此并行 settlement 不破坏 lifecycle 幂等。`False` 只表示本次 CAS 未执行，调用方后续读取账本判断是否已由其他 worker 完成。
