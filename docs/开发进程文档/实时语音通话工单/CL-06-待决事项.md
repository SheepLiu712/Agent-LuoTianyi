# CL-06 · 重连后的沉默计时策略

> 状态：待真实开发者确认；本文件不冻结产品行为。

Spec 已明确 `RECONNECTING` 期间不运行沉默时钟，但没有明确恢复为 `ACTIVE` 后如何处理断线前已经开始的五秒沉默窗口。

## 方案 A：保留断线前剩余时长

- 恢复后继续断线前尚未经过的有效沉默时间。
- 优点：成功恢复的网络波动对同一通话的交互节奏影响较小。
- 风险：需要可靠保存暂停前累计时长；若断线期间设备或播放状态不可证明，恢复后可能过快触发主动回应。

## 方案 B：恢复后重新开始完整五秒

- 恢复为 `ACTIVE` 且确认无待播放、生成、发言或未完成轮次后，从恢复时刻重新计五秒。
- 优点：更保守，不把不可观察的断线时间计入用户沉默。
- 风险：弱网环境下主动回应会被进一步延后。

## 当前组件边界

`CallPlaybackCoordinator` 在进入 `RECONNECTING` 时清除运行中的沉默起点，并在恢复 `ACTIVE` 后保持阻塞，不自动采用任一方案。未来 CallStage 必须在产品决策确定后显式提供恢复基准：

- 方案 A：提供按暂停累计量换算的基准。
- 方案 B：提供恢复时刻作为新基准。

在决策前，测试只锁定“RECONNECTING 不计时且恢复不隐式启动”，不锁定 A 或 B。

## 已固定的前置接口

- setup deadline 是 `StageManager` 首次合法 start 捕获的 monotonic 值，经 `CallStartClaim` 原样传给未来 CallStage；duplicate 不重置，且不持久化到 SQL。
- CL-2 `ContextFactory.create_call` 仍接受 legacy naive server time；未来 CallStage 必须将 ledger 的 aware Beijing `requested_at` 显式 `replace(tzinfo=None)` 后传入，不允许隐式宿主时区转换。
- 接听请求与 `CallStarted` 分离：Agent 接受后、状态进入 ACTIVE 时才产生一次 `CallStarted`。
