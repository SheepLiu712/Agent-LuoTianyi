> 状态：已完成——VM-1…VM-9 已实现并以堆叠 PR 合入 `feat/voice`（#214–#222，2026-10-01；工单 #205–#213 已关闭）；下一步集成 `dev`。

## 一、范围

手机客户端（Android 优先）录制、发送、历史展示与回放语音消息；服务端接收、保存、理解并投递给 Agent。

按《开发守则》：从 `feat/voice` 开工作分支，各工单 PR 合入 `feat/voice`；功能完成后以集成 PR 合入 `dev`；完成后关工单、新增清理 issue，并在 `dev` 删除已完成的 spec（持久约束由测试承载）。

## 二、当前基线（侦察结论，与 spec 预期的差异）

服务端：

- `VoiceMessage` 已是完整可构造的领域类型（`domain/agent/stimulus.py`），并注册为内容输入；仅 `ChatPreprocessingHandler`（`agent/handlers/stimulus/chat.py:116`）返回 `text=None`，无理解链路。
- `web/websocket` 事件表含 `user_voice`，但 `adapter/websocket/_input.py:65` 显式拒绝；入站无帧大小业务上限。
- 媒体库（`infrastructure/media`）图片专用：`persist_image`、强制 `image/*`、元数据仅 mime+owner；无音频存储/校验/解析。
- 模型层仅 llm/vlm；`QWEN_API_KEY` 已被使用但不在 `REQUIRED_SECRET_KEYS`；`client_model_types.model_kind` 白名单需扩展。
- `Conversation.type` 已允许 `audio`，但无元数据写入/出库解码路径；`add_conversations` 无幂等（重复 uuid 回滚返回 `[]`——本功能依赖的目标行为）。
- 历史接口仅投影图片；无 `/media` Bearer 下载端点；「完全重置用户」只在 CLI 脚本（`user_db_tool.py`），无幂等与失败报告。

客户端：

- app：无任何运行时权限与录音基础（`app.json` 仅 INTERNET）；图片是整包 Base64（无分片先例）；TTS 播放链路已有（expo-av + Live2D WebView `feedAudioChunk`）；`MessageType` 无 `audio`，未知类型按文本渲染；jest 可用但 `package.json` 无 `test` 脚本。
- 桌面端：`ConversationItem(**item)` 严格构造——服务端历史新增字段会抛 TypeError 并被外层吞掉，导致整页历史静默消失（AC-26 必须与历史字段同批处理）。
- cli-client：`submit_user_image`、`get_history`、Bearer 图片下载模板可直接复用。

## 三、执行标准（《开发守则》摘要）

1. 工单 = 可独立说明交付结果的单位；工作分支 PR 合入 `feat/voice`；集成 PR 入 `dev`。
2. 开工前完成 spec 非作者审核（spec 自带审核清单）；PR 前补齐并运行证明验收范围的测试；相关通过不得写成全量通过，跳过/未验证如实说明。
3. 模块归属以《代码地图》为准；深模块、单一职责。
4. 代码风格：black 120 + ruff（E4/E7/E9、F、I、W291-293、W605、E501、C901≤10）；app 用 Expo 默认。
5. 提交规范：工单内按逻辑单元**原子化提交**——每个提交自洽、可独立解释、配套其测试，不混入无关改动；工单 PR 由这组原子提交组成。

## 五、详细工单

### VM-1 上行协议与 VoiceUploadAssembler

交付：`user_voice` 四阶段 wire 完整落地；分片复杂度收敛在单一深模块中。

1. `messages.py`/`_input.py`：接上 `user_voice` 处理路径（去除 raise），校验信封与字段边界。
2. 新建 `VoiceUploadAssembler`（`adapter/websocket` 内）：乱序保存、幂等（同索引同字节→成功；不同→`VOICE_UPLOAD_CONFLICT`）、限额（≤1MiB、≤48KiB/片、1–32 片、每用户 1 条、全局 128 可配）、TTL 10 分钟清理。
3. finalize：索引完整覆盖、拼接字节、文件签名、容器/编码（M4A/AAC-LC）、服务端解析时长 0.5–30.5s → 服务端计算 SHA-256 → 原子落盘（VM-2）→ 恰好一次 `VoiceMessage` 投递。
4. `message_uuid` = UUIDv5(["conversation-audio", user, character, upload_id])；随 finalize ACK 返回 `message_uuid` + `duration_ms`。
5. ACK/NACK：阶段 ACK 语义；spec 表 8 个稳定 NACK 码；重复 finalize 重放 ACK 不重投；幂等表按 payload 摘要或由 assembler 判定，不能仅凭 ID 静默吞内容冲突。
6. 入站业务帧大小上限（不得依赖 Uvicorn 默认帧上限）。

验证（`tests/integration/websocket` 新增）：成功、乱序、缺片、重复同字节、同索引冲突、非法 Base64、MIME/容器/编码错误、大小/分片限制、拼接总长、实际时长、TTL、跨用户隔离、全局过载、断线续传、ACK 丢失、手工重试仍只有一条消息。

### VM-2 媒体库音频能力

交付：`PermanentMediaStore`/`MediaResolver` 扩展音频（不建平行仓库，外部保持统一 `MediaRef`）。

1. `persist_audio`：元数据增加 `media_kind`、`sha256`、`byte_length`、`duration_ms`、容器/编码；复用 staging→rename 原子发布与重放幂等/冲突。
2. `resolve(expected_kind)`；音频 M4A 校验器（纯 Python 解析，建议 `mutagen`，同步写入 pyproject）。
3. `delete_owned_by`：图片+音频统一删除，返回删除数量与失败项。

验证（`tests/unit/infrastructure` 扩展）：resolver 契约、owner/kind、原子性、幂等/冲突（当前 store 无专项测试，需补齐）。

### VM-3 音频理解链路

交付：从 `VoiceMessage` 到规范音频描述（`[音频]...`）的完整链路。

1. `infrastructure/models/audio/{interface,module}.py` 仿 vlm：qwen3.8-omni-flash、Data URI、客户端委托一致性、`record_llm_call` 观测。
2. 装配：`LLMService` 扩展（available_audios/register_audio_module 或同模式）；`client_model_types.model_kind` 白名单；`validation.py` 校验项 + `REQUIRED_SECRET_KEYS` 增加 `QWEN_API_KEY`；启动依赖检查。
3. `AudioUnderstandingSkill`（`agent/skills/cognitive/`，仿 image_understanding）：owner 解析 `expected_kind="audio"` → 调用 → 结构校验（三键约束）→ 20s×2 + 1s 间隔重试 → 降级 `[音频]听不清`。
4. `render_audio_context`（唯一拼接入口）、`AudioUnderstandingStatus`、`AudioContent`（枚举、不变量、text 派生）。
5. `ChatPreprocessingHandler`：理解/降级完成 → 构造 `ConversationEntry(entry_id=message_uuid)` → `PreprocessedInput(text)`。

验证（unit/agent）：清晰语音、情绪、纯声音、混合、缺键/错型/空白、超时重试、降级；逐项断言拼接文本与枚举组合。

### VM-4 Stage 时间线

交付：语音协调事件驱动的 pending 与回复时机（40/15/1s）。

1. 领域刺激：`VoiceRecordingStarted/Cancelled/Committed/UploadFailed`；`stage/_config.py` 新常量（40/15/1s）。
2. 可打断：复用 `agent.is_handle_interruptible`；可打断→取消回复尝试并恢复未消费输入；不可打断→不撤销副作用。
3. `ImageSelectionOpened` 改为可打断（AC-19/21）——先补锁定现有行为的回归测试再改。
4. 完整 `VoiceMessage` 阻塞等待预处理；完成后 1s 合批；降级也算完成。

验证（integration/stage）：各 deadline、可打断/不可打断、恢复 pending、阻塞、合批、图片语义回归。

### VM-5 对话持久化/历史/下载/重置

1. `add_conversations` 幂等：不存在→插入并计数；同身份（user/char/type/media_id）→成功不重复计数；冲突→稳定错误。
2. `_storage._decode_entry`：字符串重建枚举，`content` 与重派生文本一致，否则视为不一致。
3. `UserConversationHelper`：`type=audio` → `content="[语音消息]"`、`duration_ms`、`audio_available`；绝不返回理解字段。
4. `GET /media/audio/{message_uuid}`：Bearer → owner+kind 校验 → 流式 `audio/mp4`；越权/未知/删除不泄露存在性。
5. 完全重置（AC-25）：application 层编排（对话+向量+缓存+图片+音频），幂等、失败步骤报告，接入既有触发。

验证（integration/persistence + web）：幂等/冲突、出库一致、历史脱敏、越权、删除后不可访问、部分失败重试。

### VM-6 App 录音与发送

1. `VoiceRecorder`：expo-av，M4A/AAC-LC，metering；权限流（首次仅请求；永久拒绝→去设置）；`app.json` 增加 RECORD_AUDIO。
2. UI：模式切换（草稿保留）、按住说话、80dp 双向取消区（中性灰/单次触觉）、计时、波纹（约 80ms 平滑）、遮罩（55%）。
3. 发送项：begin/chunk/finalize（≤48KiB/片）、15s 预算、同 ID 重试、失败图标与手工重试（复用 ID）。
4. 乐观气泡：finalize ACK 关联 `message_uuid`/`duration_ms`；录音期间角色输出：文本照常、音频不播不补播、可打断则打断。

验证：jest（权限、阈值、0.5/30s、metering、乐观/重试、清理）+ 真机清单；建议补 `test` 脚本。

### VM-7 App 播放与缓存

1. 语音条：复用用户气泡右对齐；状态+播放控件在左；0.5–1.0s 显示 1''，其余上取整 ≤30''；宽度 76→200dp。
2. 下载：Bearer `GET /media/audio` → 临时文件 → 原子替换 `voice_cache/<message_uuid>.m4a`；并发合并；失败恢复。
3. 播放：单实例；播放中→停止方块；不自动播放；不预取。
4. 缓存：100MiB LRU，不删播放中/下载中；退出登录与本地重置清缓存。

验证：jest（下载合并、LRU、互斥）+ 真机清单。

### VM-8 兼容客户端（AC-26）

1. 桌面端：放宽 `ConversationItem` 构造（容忍新字段——否则整页历史静默消失）；`type=audio` → `[语音消息]` 占位、不自动下载。
2. cli-client 同占位。

验证：现有测试 + 手工（历史含音频时桌面端与 CLI 不崩、不空白）。

### VM-9 测试 CLI 驱动（AC-27）

1. `ws_transport.submit_user_voice`（仿 submit_user_image）；`network_client.send_voice` + Bearer 下载；`headless_session.send_voice` 与断言（ACK、单条消息、thinking/回复、历史元数据、SHA-256 一致）。
2. 离线 pytest + `manual_e2e` driver；不加用户可见 slash 命令。

验证：`cli-client/tests` 离线通过；任一条件不符非零退出。

## 七、风险与注意

1. 桌面端严格构造：新字段一上线可能「整页历史静默消失」，AC-26 必须与服务端历史字段同批交付。
2. app 从零开始：无权限/录音基础、无 `test` 脚本；注意 expo-av 录音 API 与插件配置。
3. `add_conversations` 幂等是 spec 的「目标行为」而非现状。
4. 入站帧上限需显式（48KiB 片经 Base64 后体积约 4/3，边界值要测）。
5. 新依赖：`mutagen`；`QWEN_API_KEY` 进必需密钥。
6. `ImageSelectionOpened` 打断语义改动要带回归。
7. `VoiceMessage` 已是完整类型，别重复造；重点是理解链路与配套。
8. 幂等表扩展：语音操作按 payload 摘要判定，重放 ACK 不重投。
