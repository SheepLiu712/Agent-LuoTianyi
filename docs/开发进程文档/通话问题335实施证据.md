## 范围与策略

- Issue：#335；基线：`e6ad5894877a149ebb7c196c0b8dd7817b7d9e94`；本 lane 只处理通话结算晚到后的历史可见性。
- 新增 `refreshLatestHistory(username, token)`：固定请求最新页 `end_index=-1`，不修改 older pagination cursor；同时接入聊天 `FlatList` 的 `refreshing/onRefresh`，用户可下拉刷新。
- 通话返回聊天时先尝试 `resumeChat()`，无论恢复结果如何再触发一次 latest refresh；没有无界轮询。
- history request 使用 generation + 完整 identity fence（username、characterId、token、resetEpoch）；提交响应和 finally 都同步比较捕获身份与 ref 当前身份，组件卸载、账号/token/角色/reset epoch 变化或新请求后，旧响应不再写入；旧 finally 不会清掉新 owner 的 loading。
- 消息合并按稳定 `uuid`：`unknown_id` 从不折叠。服务器的 call outcome、duration、timestamp 和 content 是持久事实；本机的 audio URI、播放/下载状态、availability、send status 优先保留，waiting live content 不被旧历史回退。latest 页维持 inverted newest-first：更晚的本地 waiting 前缀不被晚到历史抢前，有确定服务端时间的新增条目按时间插入、同时间保持响应顺序，无时间的本地条目保持相对位置。
- 页面级 `Index` 完整 render 未运行；用户可达入口由 `FlatList onRefresh` 静态接线核对，真实 history hook/API 与 production merge helper 分层验证。

### N2 顺序、字段所有权与本地消息保留

`app/__tests__/history_merge.test.ts`

- `history merge updates an existing summary and keeps one deterministic uuid`
- production consumer 使用 `mergeHistoryMessages`，重复 uuid 原位更新；本轮未重构完整消息模型。
- `mapHistoryMessage` 将服务端 SQLite 的 naïve `Asia/Shanghai` timestamp 以明确 UTC+08:00 规则转换成 epoch number，不使用设备 `Date.parse`；本机即时消息继续使用 number timestamp。
- 真实 `useChatLogic.addHistoryMessage` hook 测试覆盖 call `durationMs` 1000→2000 时只保留一条 uuid 并更新事实字段。
- 同一 history page 内稳定 UUID 按“最后一个 server fact 胜出、第一次出现的位置保留”归一化；该归一化同时驱动 existing 更新与 additions，latest 与 older 都不会因同批重复 UUID 产生两条记录。`unknown_id` 或缺失 UUID 不参与此去重。
- 服务器 timestamp 明确较旧时不会回退现有 content/timestamp；这覆盖真实 agent 消息（没有 `sendStatus`）先到、旧 history 后到的情况。timestamp 缺失时只在双方都缺失时接受 history 字段，若一方已有时间则保守保留已有消息，不猜测时间顺序；同 timestamp 的 settlement call 仍可用服务器 summary/duration 更新。
- 客户端瞬态字段（audio URI、audio play/download state、availability、send status）始终 existing 优先；服务器持久事实字段在不较旧时更新。
