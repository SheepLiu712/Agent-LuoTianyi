# PR 审查报告（格式、证据与提交流程）

本 Skill 规定项目 PR 审查报告的结构、证据标准与提交流程，让不同会话产出的审查报告可以直接对比、复用并落到 PR 评论。格式基线来自 PR #44 与 PR #186 的现行审查报告。

## 何时使用

- 需要审查一个 GitHub PR（本地 head 或远程 head）并产出报告；
- 需要复核既有审查结论（新增证据、推翻或降级某条发现）；
- 需要把报告提交为 GitHub review（`--request-changes` / `--comment` / `--approve`）。

不适用：修改被审代码（那是被审 PR 作者的工作）；纯 prompt/文档写作（除非要形成审查结论）。

## 审查过程（证据优先）

1. **固定被审对象**：取 PR 当前 head 的**完整 SHA**、base 分支与 SHA。堆叠 PR 使用增量 diff（`parent..head`）并注明堆叠关系；行号与链接一律基于该 head，head 更新后旧报告只描述旧 head。
2. **多专项并行**：按可分离领域拆分审查（Standards / Spec / 核心逻辑 / 平台与原生 / 测试与检查脚本 / UI）。每个专项只报自己轴的结论，逐条附 `文件:行` 证据；编排方负责交叉核对与去重。
3. **实测优先于阅读**：
   - 能跑的官方入口用**锁定版本**实际运行（如项目脚本、锁文件指定版本、`conda run -n <env>`），记录精确命令与原始摘要；
   - 无运行环境时只写静态可证结论，并明确标注「静态不可验证」；
   - 对高严重度指控做**最小实验复核**（例：用十几行脚本验证 `DirAccess.rename_absolute` 是否覆盖已有目标），复核不成立时在报告「已排除的指控」中撤回并说明依据。
4. **不得**：把未运行写成通过；把进程退出码 0 写成「检查通过」（若门禁按日志判定）；只读 AI 总结而不核对 diff；用旧 head 结论描述新 head；把单 lane 结论不经交叉核对直接当定论；把当前PR新增或修改的测试断言本身当作其正确性的依据，或因这些测试通过就默认其预期合理。

### 新增与修改测试的入库门槛

本节只审查当前PR新增或修改的关键测试预期。未修改的既有测试继续作为原有行为与契约的回归基线；若当前PR的交付目标未明确包含对应既有行为变更，不得改写、绕过或降低这些测试；若交付目标明确包含既有行为变更，须同步修改对应测试并说明契约变更依据，此时修改后的测试适用本节门槛。

测试结果只能证明实现是否满足断言；将新增或修改的测试作为交付证据前，先在测试之外确定应有行为，再核查断言是否准确、必要地承载该行为。

1. **预期来源合理**：关键断言须能追溯到经确认的产品目标、验收标准、稳定接口契约、领域不变量、适用的外部规范，或经独立确认的正确用户行为。当前实现、历史实现、其他测试或 mock 返回值不能单独作为预期来源；来源不明确时报告「契约待确认」，不得因测试已写成或已通过而默认正确。
2. **不固化错误行为**：行为正误须在测试之外独立判断。若依据产品目标、验收标准、稳定契约、领域不变量、适用的外部规范，或对真实入口与可复现实测的独立分析确认断言错误，将测试本身列入修改范围；测试通过、存在同类测试或变异后能够变红，都不能反证该行为正确。无法独立判定时如实报告「无法判定」，不得选择与现有测试一致的一方。
3. **不超出交付目标**：关键断言只固定本次目标及证明目标成立所必需的约束。逐项检查额外断言是否有独立依据；不得把未经确认的实现顺序、中间状态、提示时机、重试策略、错误分类等附带行为顺便提升为长期契约。超出目标的断言应删除、收窄，或补充其作为稳定契约的独立依据。

审查报告引用新增或修改的测试作为正面证据时，须说明其关键预期来源，并确认断言没有固化经独立判断为错误的行为，也没有超出本次交付目标。核心问题不是「测试是否通过」，而是「测试是否只承载已有独立依据的必要目标」。

## 报告格式（直接套用）

````markdown
# PR #<编号> 审查（head `<短SHA>`）：<PR 标题>

> 本评论由 AI 辅助核查生成（<方法：多专项审查 + 环境复跑 + 复核实验>）。最终合并决策仍应由项目维护者确认。
>
> 审查 head：`<完整 SHA>`
> base：`<base 分支>`（`<base SHA>`）
> 上一轮审查 head：`<完整 SHA>`（仅复审时写）
>
> 审查结论：**CHANGES REQUESTED / 当前不可合并**

## 一、审查范围

<PR 自述与提交构成、文件数/行数；本报告覆盖的维度；方法与限制（如：UI 视觉未覆盖、无 GPU、未跑真实网络）>

## 二、阻断问题

### [P1] N1. <一句话结论式标题>

#### 证据

<文件链接 + 行号 + 关键代码/报错引用；引用契约或规范原文（路径:行）。若引用新增或修改的测试，说明其关键预期来源及约束边界。>

#### 复现步骤

1. …

#### 影响

#### 修改方向

#### 测试缺口

- …

## 三、已确认与正面结论

<已修复项、已验证通过项、流程边界声明；避免只列问题>

## 四、其他问题

### [P2] N6. <简版：证据 + 建议>
### [P3] N15. <简版：证据 + 建议>

### 已排除的指控（复核修正）

<经实测证伪或降级的发现，明确撤回并给出依据，避免后续被引用>

## 五、验证结果

| 验证项 | 结果 |
|---|---|
| <命令 / 入口> | **通过 / 失败 / 未验证**（原因） |

## 六、最终结论

<阻断项编号汇总；判定；建议修复顺序（1…n）；修复后要求重跑哪些入口并重新请求 review>
````

## 编号与分级

| 标签 | 含义 |
|---|---|
| `[P1]` | 合并阻断：安全、数据损坏、门禁不满足、可复现的严重缺陷 |
| `[P2]` | 建议合并前处理：健壮性、测试可信度、体验缺陷 |
| `[P3]` | 低风险：一致性、文档、命名、可维护性 |
| `[P1 / Security]`、`[P1 · 流程]` | 安全类、流程门禁类补充标签 |

- 编号 `N1..Nn` 全文连续；复审沿用上一轮编号，新增项接续。
- 每条阻断必须包含全部五个小节（证据/复现步骤/影响/修改方向/测试缺口）；P2/P3 可只写「证据 + 建议」。

## 证据规范

- 文件引用一律链接到被审 head：`https://github.com/<owner>/<repo>/blob/<完整SHA>/<path>#Lx-Ly`（中文路径文档可直接写 `路径:行`，避免链接编码问题）。
- 代码与日志用引用块或 ```text 代码块，保留关键原文行。
- 规范引用写清出处与行号：`docs/开发进程文档/开发守则.md` §…、`skills/spec-tdd-pr-guard/SKILL.md` 行号、`接口文档/…` 行号。
- 区分「实测」「静态可证」「静态不可验证」；无法复现的声明写「无法判定」，不得默认通过。

## 提交口径

```powershell
gh pr review <编号> --repo <owner>/<repo> --request-changes --body-file <报告.md>
gh pr view <编号> --repo <owner>/<repo> --json number,state,reviewDecision   # 核验
```

- 报告即 review 正文，不另发摘要评论（避免两份口径）。
- 结论与 GitHub 状态一致：存在阻断 → `--request-changes`；仅建议 → `--comment`；通过 → `--approve`。
- AI 辅助审查必须在报告开头声明；是否采用由管理员决定（见 `开发守则.md` 其他开发者审核一节）。
- 未经授权不得推送、合并或对外发送其它消息；报告正文与证据材料应保留在本地工作目录，便于复审时复用。
