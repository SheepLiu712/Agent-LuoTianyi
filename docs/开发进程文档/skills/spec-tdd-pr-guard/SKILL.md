# Spec、TDD 与完整行为切片 PR 门禁

本 Skill 的目标是阻止 AI 跳过开发流程、一次生成过多代码或私自扩大公开 interface。

开始前读取：

- `docs/开发进程文档/开发守则.md`；
- 当前功能在 `docs/开发进程文档/需求说明（PRD）/` 下的需求文档；
- `docs/项目说明/项目架构与接口（spec）/接口文档/README.md` 及相关模块接口文档；
- `docs/开发进程文档/开发进度/` 下对应功能的进度文档；
- 与本次行为直接相关的现有测试。

以当前工作区为准。已有代码、测试或文档不等于流程已经满足，必须检查它们是否确实覆盖本次行为。

## 开始实现前的门禁审计

在修改产品代码前，先给出一份简短审计：

```text
功能：
本次可观察行为：
需求文档：存在 / 缺失 / 不足
相关公开 interface spec：存在 / 缺失 / 不足
对应测试：存在且已确认失败 / 已有回归测试 / 缺失
进度文档：存在 / 缺失
预计行为切片：
最早缺失步骤：
```

按以下顺序推进，同一行为切片内不得跳步：

1. 需求；
2. 模块归属和公开 interface 设计；
3. SPEC 检查；契约需要变化时提交 SPEC commit 并自审；
4. 通过公开 interface 建立 Red，提交测试 commit 并自审；
5. 最小 Green，提交实现 commit 并自审；
6. 回归、进度记录和完整行为切片 PR。

如果较早步骤缺失，不得用后面的代码、测试或用户要求“先做出来”作为跳过理由。补齐并自审较早步骤后，可以在同一分支继续下一阶段；阶段门禁默认是 commit 边界，不是 PR 边界。

## 同一分支内怎样补齐门禁

### 1. 缺少需求

先创建或补充 PRD，提交 SPEC commit 后停止进行作者自审。需求含义仍有实质歧义时请求用户决定；已经足够明确时继续 interface 和测试，不为普通切片自动创建文档 PR。PRD 只记录大目标、需求和验收标准，不写随时可能重新切分的实现计划。

Bug 可以使用写明复现步骤、期望结果、实际结果和修复边界的 Bug 需求文档，不得只用一句聊天描述代替可审核需求。

### 2. 缺少 interface 设计

先在 `docs/项目说明/项目架构与接口（spec）/接口文档/` 的对应模块文档中补充本切片要交付的类型和 interface，写明调用者、输入输出、副作用、正常行为、异常行为以及从哪个 interface 验证。不要把未来切片、暂定 PR 数量或未决定方案写进 interface 文档。提交 SPEC commit 后停止进行作者自审。只有跨模块 interface 尚有争议或需要多个团队先行采用时，才建议独立设计 PR；否则继续同一行为切片。

如果现有 interface 已能满足需求，应明确列出将使用的 interface，不为形式完整新增包装层、修改文档或创建空的 SPEC commit；在最终 PR 中引用现有 spec 并记录“SPEC 已满足”。

### 3. 缺少对应测试

为本切片增加通过已确认公开 interface 观察行为的测试。先运行并确认它因为功能尚未实现而失败，记录命令、失败测试和失败原因；提交 Red commit 后停止进行作者自审。确认 Red 有效后，在同一分支继续最小 Green，不默认创建 Red-only PR。

如果实现早已存在，新增测试第一次运行就通过，不得伪造 Red。应在 PR 中标为“补回归/契约测试，既有实现无 Red 证据”。不得删除或故意破坏现有代码来制造失败。

### 4. 可以实现

只有需求、interface spec 和对应失败测试都已确认后，才能修改产品代码。只写足以让当前切片测试通过的实现，不顺便增加 spec 没有要求的 fallback、配置、状态或兼容路径。

运行当前测试、受影响模块的回归测试和必要的静态检查。形成完整 Green 候选后，向对应大目标的进度文档追加本切片已经实现和实际验证的事实，再提交 Green commit 并停止进行作者自审。只有完整候选为 Green，才能请求其他开发者进行 PR 审核。

文档、流程配置、机械迁移或删除废弃自动化如果没有有意义的运行时 Red，应记录“不适用”，改用静态检查、前后状态或可重复人工验证；不得制造无价值测试。

## 拒绝巨型改动并拆分 PR

以下任一情况出现时，必须拒绝把请求作为一个 PR 实现：

- 包含两个或更多可以独立说明、测试或发布的可观察行为；
- 要求一次完成整个版本、多个独立模块或大范围“顺便重构”；
- 预计超过 500 行手写实现代码，或审核者无法用一个聚焦测试集理解和验证；
- 现有工作区已经堆积大量未拆分实现，继续编码会扩大混合 diff；
- 同一个 PR 同时包含无关重构、行为变化、协议迁移和旧路径清理。

拒绝的是**单次巨型执行**，不是拒绝用户目标。先说明为什么不能作为一个 PR 审核，再给出有顺序的 PR 列表。每个 PR 必须包含：

- 一个完整行为目标；
- 对应 spec/interface；
- 对应 Red、Green 和验证命令；
- 明确不包含什么；
- 对前后 PR 的依赖；
- 完成条件。

按顺序执行当前已获授权的行为切片。不要在用户要求“大量完成”时先生成全部代码，再事后把提交记录拆开。

如果工作区已有大量用户或其他 AI 的修改，保留它们，不删除、不覆盖。先冻结新增产品代码，盘点可独立行为和缺失门禁；无法安全分离时停止并请用户决定分支或 PR 边界。

## 锁定 spec 中的公开 interface

文档职责必须保持单一：

- PRD 记录大目标、需求和最终验收标准，只在需求改变时更新；
- 总体设计记录架构边界和跨切片不变量，只在相应决定改变时更新；
- `docs/项目说明/项目架构与接口（spec）/接口文档/` 是当前公开契约的权威来源，普通行为切片的 SPEC 增量写在这里；
- Issue 记录未完成工作、依赖和可调整的切片方案；
- 开发进度只追加已经完成的行为和验证事实，不保存未来清单或“下一步”。

历史设计文档可以保留为设计背景，但必须明确其状态并链接到权威 interface spec。任何仍被标为现行规范的文档都不得与 interface 文档冲突；发现冲突时先消除冲突再进入 Red。

实现前列出本切片允许使用或实现的公开 interface。公开 interface 包括：

- 被其他顶层模块调用的类、方法、函数和包导出；
- REST 路由、WebSocket 事件和跨客户端协议；
- 共享领域对象、持久化约定和跨模块配置字段；
- Fake Adapter 必须遵守的调用约定。

只实现 spec 已经写明的 interface。内部私有 helper 可以在模块内调整，但不能借“内部实现”之名让其他模块直接依赖。

如果发现必须新增、扩大或改变公开 interface，立即停止实现，并向用户说明：

1. 当前 interface 为什么无法满足需求；
2. 建议的新 interface、输入输出和失败行为；
3. 不新增 interface 的替代方案；
4. 对调用者、兼容性、测试和迁移的影响。

在用户确认前不得增加公开方法、导出、路由、事件字段或共享数据字段。确认后先更新 interface spec；发生文档变化时提交 SPEC commit 并自审，再进入测试和实现。只有 interface 本身需要独立多人决策时才先提交设计 PR。

## Commit 自审和 PR 提交条件

每个 SPEC、Red、Green 或 refactor commit 完成后，作者必须暂停后续开发并审查该 commit 相对父 commit 的 diff：确认阶段单一、范围没有扩大、事实记录准确，并运行该阶段需要的验证。发现问题先修正；自审通过后才能进入下一 commit。SPEC 检查未产生文档变化时仍要完成自审，但不创建空 commit。

PR 默认只在一个完整行为切片已经 Green 时提交，并引用或包含必要的 SPEC，同时包含测试、实现和一条完成进度记录。Red-only PR、纯实现子 PR 和堆叠 PR 不是默认流程；只有负责人为独立契约交付、多人并行、跨仓库依赖或高风险迁移明确批准时才使用。不得用 Draft PR 代替同一切片内部的 SPEC、Red 或 Green commit，也不能把未完成候选当成已经可审核或可合并。

其他开发者审核 PR 当前 head。作者自审不能替代他人审核，旧 head 的审查结论也不能证明更新后的候选。管理员在评审时自行决定是否手动调用 AI 辅助；不得因为 PR 创建、push、编辑、评论、Ready 或 review 事件自动启动 AI 审核或自动合并。

打开远程 PR、推送分支或发送外部消息仍需要当前任务具有相应授权。如果没有授权、远程不可用或凭据不足，则准备好分支/提交建议、PR 标题、PR 正文和验证证据，明确请求授权；不得因为无法打开 PR 就继续实现下一阶段。

最终回复必须说明：完成的是哪个行为切片、SPEC 检查结论、实际存在的 SPEC/Red/Green commit 和作者自审状态、进度文档中追加的完成记录、实际验证结果以及未验证范围。未来切片放入 Issue，不把“下一步”写入进度文档。
