# Spec、TDD 与小 PR 门禁

本 Skill 的目标是阻止 AI 跳过开发流程、一次生成过多代码或私自扩大公开 interface。

开始前读取：

- `docs/开发进程文档/开发守则.md`；
- 当前功能在 `docs/开发进程文档/需求说明（PRD）/` 下的需求文档；
- `docs/项目说明/项目架构与接口（spec）/接口文档/README.md` 及相关模块接口文档；
- `docs/开发进程文档/开发进度/` 下对应功能的进度文档；
- 与本次行为直接相关的现有测试。

以当前工作区为准。已有代码、测试或文档不等于流程已经满足，必须检查它们是否确实覆盖本次行为。

## 开始实现前的门禁审计

在修改产品代码前，先给出一份简短审计：

```text
功能：
本次可观察行为：
需求文档：存在 / 缺失 / 不足
相关公开 interface spec：存在 / 缺失 / 不足
对应测试：存在且已确认失败 / 已有回归测试 / 缺失
进度文档：存在 / 缺失
预计 PR 切片：
最早缺失步骤：
```

按以下顺序判断，**只处理最早缺失的一步**：

1. 需求；
2. 模块归属和公开 interface 设计；
3. 对应公开 interface 的测试；
4. 让一个失败测试通过的最小实现；
5. 验证、进度记录和 PR。

如果较早步骤缺失，不得用后面的代码、测试或用户要求“先做出来”作为跳过理由。

## 缺失步骤怎样处理

### 1. 缺少需求

只创建或补充 PRD，同步创建或更新进度文档，然后准备一个仅包含需求和进度记录的 PR。停止，不设计 interface，不写测试或实现。

Bug 可以使用写明复现步骤、期望结果、实际结果和修复边界的 Bug 需求文档，不得只用一句聊天描述代替可审核需求。

### 2. 缺少 interface 设计

只补充模块归属和 interface spec，写明调用者、输入输出、副作用、正常行为、异常行为以及从哪个 interface 验证。同步进度文档，然后准备一个仅包含设计和进度记录的 PR。停止，不写测试或实现。

如果现有 interface 已能满足需求，应明确列出将使用的 interface，不为形式完整新增包装层。

### 3. 缺少对应测试

只为一个最小可观察行为增加测试，通过 spec 已确认的公开 interface 验证。先运行并确认它因为功能尚未实现而失败，记录命令、失败测试和失败原因；同步进度文档，然后准备 Draft PR。停止，不写产品实现。

如果实现早已存在，新增测试第一次运行就通过，不得伪造 Red。应在进度文档和 PR 中标为“补回归/契约测试，既有实现无 Red 证据”。不得删除或故意破坏现有代码来制造失败。

### 4. 可以实现

只有需求、interface spec 和对应失败测试都已确认后，才能修改产品代码。只写足以让当前一个测试通过的实现，不顺便实现下一个场景，不增加 spec 没有要求的 fallback、配置、状态或兼容路径。

运行当前测试、受影响模块的回归测试和必要的静态检查。同步进度文档，然后准备本行为切片的 PR。停止，下一行为进入下一个 PR。

如果失败测试保存在一个已获批准但尚未合入的 Red-only Draft PR 中，实现切片可以建立在该 PR 的 head 分支上，作为堆叠子 PR 提交。子 PR 只证明相对该 Red seam 的最小 Green 增量；它通过后只合入父 PR 分支，再由已经变为完整 Green 候选的根 PR 重新审核并合入功能集成分支。不得先把必然失败的 Red-only PR 单独合入功能分支，也不得把子 PR 直接合入 `dev`、`main` 或 `master`。

## 拒绝巨型改动并拆分 PR

以下任一情况出现时，必须拒绝把请求作为一个 PR 实现：

- 包含两个或更多可以独立说明、测试或发布的可观察行为；
- 同时缺少需求、interface 或测试中的任一前置步骤；
- 要求一次完成整个版本、多个独立模块或大范围“顺便重构”；
- 预计超过 500 行手写实现代码，或审核者无法用一个聚焦测试集理解和验证；
- 现有工作区已经堆积大量未拆分实现，继续编码会扩大混合 diff；
- 同一个 PR 同时包含无关重构、行为变化、协议迁移和旧路径清理。

拒绝的是**单次巨型执行**，不是拒绝用户目标。先说明为什么不能作为一个 PR 审核，再给出有顺序的 PR 列表。每个 PR 必须包含：

- 一个目标或一个流程门禁；
- 对应 spec/interface；
- 对应测试和验证命令；
- 明确不包含什么；
- 对前后 PR 的依赖；
- 完成条件。

只执行最早且当前已获授权的 PR。不要在用户要求“大量完成”时先生成全部代码，再事后把提交记录拆开。

如果工作区已有大量用户或其他 AI 的修改，保留它们，不删除、不覆盖。先冻结新增产品代码，盘点可独立行为和缺失门禁；无法安全分离时停止并请用户决定分支或 PR 边界。

## 锁定 spec 中的公开 interface

实现前列出本切片允许使用或实现的公开 interface。公开 interface 包括：

- 被其他顶层模块调用的类、方法、函数和包导出；
- REST 路由、WebSocket 事件和跨客户端协议；
- 共享领域对象、持久化约定和跨模块配置字段；
- Fake Adapter 必须遵守的调用约定。

只实现 spec 已经写明的 interface。内部私有 helper 可以在模块内调整，但不能借“内部实现”之名让其他模块直接依赖。

如果发现必须新增、扩大或改变公开 interface，立即停止实现，并向用户说明：

1. 当前 interface 为什么无法满足需求；
2. 建议的新 interface、输入输出和失败行为；
3. 不新增 interface 的替代方案；
4. 对调用者、兼容性、测试和迁移的影响。

在用户确认前不得增加公开方法、导出、路由、事件字段或共享数据字段。确认后先更新 interface spec 并提交设计 PR；设计通过后再进入测试和实现。

## PR 提交和停止条件

完成一个门禁或行为切片后立即停止后续开发，并提交该范围的 PR。只有前一个 PR 已被用户确认可以继续，或用户明确批准堆叠 PR 时，才进入下一步。

### 堆叠 PR 门禁

默认创建直接指向功能集成分支的根 PR。使用堆叠 PR 时，开始下一层前必须记录父 PR、根 PR、最终集成分支和对应 Issue，并确认父 PR 的当前 head 已获批准可以继续：

- 根 PR 的 base 必须是规定的功能集成分支；
- 子 PR 的 base 必须是同仓库直接父 PR 的 head 分支，父链必须最终终止于该根 PR；
- 子 PR 以直接父 PR 为 fixed point 审核本层增量，只允许 squash merge 到父分支；
- 父 PR 吸收子 PR 后必须更新标题、正文、阶段和进度记录，并基于新 head 重新运行测试、重新审核；
- 只有根 PR 的完整 diff 为 Green 且所有门禁通过时，才能合入功能集成分支；旧 head 上的批准不能继承为最终批准。

Draft/Ready 由作者维护，Approve/Request changes 与合并由审核者负责。Red-only 门禁 PR 必须保持 Draft；实现子 PR 完成且自检通过后由作者转 Ready。PR 处于 Ready 只表示请求审核，不表示审核通过。

### 审核验证范围

实现阶段必须运行 focused tests 和受影响模块的可重复离线回归。默认跳过会连接真实外部服务或启动长耗时进程的 `slow`、`live`、`external`、`real_llm` 测试，以及尚未标记的真实学歌流程、B 站动态抓取、真实模型/TTS/GPU/设备测试；优先用精确 node ID 排除长测试，保留同文件内的 Fake/离线单元测试。每个跳过项都要记录为未验证，不能把跳过或环境不可用写成通过。

打开远程 PR、推送分支或发送外部消息仍需要当前任务具有相应授权。如果没有授权、远程不可用或凭据不足，则准备好分支/提交建议、PR 标题、PR 正文和验证证据，明确请求授权；不得因为无法打开 PR 就继续实现下一阶段。

最终回复必须说明：完成的是哪一个门禁或行为切片、哪些步骤尚未开始、进度文档位置、实际验证结果，以及下一 PR 应做什么。
