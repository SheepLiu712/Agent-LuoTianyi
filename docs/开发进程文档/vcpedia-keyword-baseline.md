# VCPedia 歌词关键词可用性基线

本文记录一次真实页面采样得到的量化事实，用于给"关键词可用性"设定验收基线。所有数字来自
2026-09-26 对 VCPedia 当日模板页前 12 首歌曲的实测，采样与统计脚本为一次性只读脚本，不修改产品代码。

## 下游实际需求

歌词只经一条链路到达消费者：

```text
wikitext_parser: lyrics + spaced_lyrics=spaced_from(lyrics)
  -> _extract_song_fields -> spaced_lyrics
  -> _split_spaced_lyrics: 按空白切分，只保留 6 <= 长度 <= 50 的片段
  -> NewSongCandidate.lyric_keywords
  -> song_acceptance: 写成 "{keyword}=>{keyword}是《{song_name}》的歌词"
  -> song_entity_linker: flashtext 在用户输入里做子串匹配，认出歌名
```

因此关键词的唯一用途是**在用户话里被匹配到**。它决定两件事：这首歌能不能被认出来（召回），以及
不相干的闲聊会不会认错歌（误命中）。格式保真（换行、括号、和声、原译分离）不进入这条链路。

## 实测事实

### 字段覆盖率

对当日列表前 20 首采样（同一实现、关闭模型）：

| 指标 | 实测 |
| --- | --- |
| 抓取成功 | 19 / 20 |
| `lyrics` 为空 | 0 |
| `summary` 为空 | 0 |
| `infobox` 为空 | 0 |
| 抓取失败 | 1（`谁是世界上最好的矿石？`，标题本身不是歌曲页） |

即字段非空率已接近满值。**但这是结构遍历实现的成绩**，与等价实现的对照见下。

### 与等价实现的对照（覆盖率增益的来源）

同一批 20 首、同一环境，分别用"行为等价实现"与"结构遍历实现"运行：

| 指标 | 行为等价实现 | 结构遍历实现 |
| --- | --- | --- |
| 抓取成功 | 19 / 20 | 19 / 20 |
| `lyrics` 为空 | **2**（`乐鸣东方`、`人是猫`） | **0** |
| `summary` 为空 | 0 | 0 |
| `infobox` 为空 | 0 | 0 |

两首歌在等价实现下没有歌词，在结构遍历实现下分别取到 437 与 118 字符。该差异已固化为
`tests/unit/world/test_vcpedia_lyrics_recovery.py`（含真实响应 fixture），并做过突变检验：同一用例
在等价实现上三条全部失败、在本实现上三条全部通过。

### 逐首歌词抽取对照（24 首）

同一批页面（当日列表前 24 首）上逐首比较 `lyrics` 字符数，只列有差异的：

| 歌曲 | 行为等价实现 | 结构遍历实现 | 说明 |
| --- | --- | --- | --- |
| `刹那芳华` | **64** | **723** | 等价实现只取到首个 `p` 内的片段，正文基本丢失 |
| `乐鸣东方` | **0** | **437** | 等价实现整页取不到歌词 |
| `人是猫` | **0** | **118** | 同上 |
| `微光` | 281（1 行） | 251（19 行） | 内容未丢失，但等价实现把整段拼成一行 |
| 其余 15 首 | — | — | 差异 1–12 字符，属句间拼接差异 |

只有结构遍历实现取到歌词的页面 **2 首**；只有等价实现取到歌词的页面 **0 首**。

### 单行形态对关键词的影响

`微光` 的差异值得单独说明：等价实现产出的是一整段（281 字，无换行），结构遍历实现产出 19 行。
由于关键词按空白切分，整段形态会把相邻句粘连成一条关键词：

| 形态 | 关键词样例 | 结果 |
| --- | --- | --- |
| 整段一行 | `凝望这寂静深夜`、`裂隙在蔓延旧世界的残篇` | 跨句粘连，长片段难以在用户输入里被匹配 |
| 真换行 | `凝望这寂静深夜`、`旧世界的残篇`、`正坠落到深渊` | 每句独立，可被匹配 |

因此等价实现**并未丢失歌词内容**，但它产出的关键词更粘连、更难被检索命中。这是"歌词保留原文行"
在下游唯一被观察到的实际影响——不是格式美观问题，而是检索粒度问题。

### 关键词片段：按当前生产口径重新测量

早期版本的本文件按"未去重的原始短语"统计，得出"因 `<6` 丢弃 46.2%"的结论，**该口径有误**
（它统计的是切分中间产物，不是进入索引的候选）。用当前生产路径（`spaced_from` -> `_split_spaced_lyrics`）
在固化的真实页面 fixture 上重新测量：

| 歌曲 | 行数 | 最短行 | 中位行 | `< 6` 字的行 |
| --- | --- | --- | --- | --- |
| 乐鸣东方 | 36 | 2 | 11 | 3（`乐鸣东方`×2、`咚咚`） |
| 人是猫 | 6 | 16 | 18 | 0 |

同一批数据上调整长度下界的收益：

| 下界 | 进入索引的行数 | 相对下界 6 |
| --- | --- | --- |
| 6 | 39 | - |
| 4 | 41 | +2 |
| 3 | 41 | +2 |

新增的两条都是歌名 `乐鸣东方`——而歌名索引里本来就有它，属于冗余。

### 三项被数据否决的改动

1. **降低长度下界（6 → 3）**：净收益为零（只多捞到歌名冗余），因此**不改**。降下界还会让
   `嘿`、`那个` 一类口语词进入索引，是纯粹的负向变更。
2. **改变切分单位（逗号不断句）**：分离实验显示只改切分是 **+0**（422 → 422）。中文歌词的逗号
   本就是句内停顿，把它当断句点并不丢内容。
3. **过滤纯拉丁片段**：真实链路上**已经是零**。`_split_spaced_lyrics` 按空白切分，英文整行必然被
   拆成单词，而 `you`(3)、`hello`(5)、`see`(3)、`go`(2) 都过不了 6 字下界；实测两首真实页面的
   关键词里纯拉丁片段为 0。因此不需要为该场景添加任何规则。

### 长度上界 50

真实片段最长 27 字，`> 50` 丢弃率 0.0%，该上界从未触发。它属于无效常量，但**删除它也没有实测收益**；
在没有其它改动需要触及该函数前，不做无收益的清理。

### 该机制的语言假设（结论）

关键词链路是**按汉字设计**的：`spaced_from` 用中文标点切句，`_split_spaced_lyrics` 按空白切分并
套用 6–50 字窗口。该窗口对中文近似"一个短语"，对英文则近似"一个单词"。由于采样语料中没有以英文
为主的歌曲，且英文单词在当前窗口下基本被自动挡掉，**本项不需要为英文做特殊处理**；若将来出现
英文为主的歌曲，需要重新评估该窗口的语义。

## 度量基线

| 指标 | 定义 | 实测 |
| --- | --- | --- |
| 字段非空率 | 采样 20 首中 `lyrics` / `summary` / `infobox` 非空 | 19/19 全部非空（1 首非歌曲页抓取失败） |
| 歌词覆盖率增益 | 与行为等价实现相比多取到歌词的页面 | 2/20（`乐鸣东方`、`人是猫`），已固化为回归用例 |
| 关键词片段 | 真实 fixture 上进入索引的片段 | 乐鸣东方 33 个；人是猫 6 个 |
| 污染片段 | 含 `=>` 或换行的关键词 | 0（由 `spaced_from` 分隔符保证） |

## 与现存知识库的形态差异

对 `server/res/knowledge/knowledge_db.db`（3414 行、3320 行有歌词）与关键词文件
`server/res/knowledge/song_lyric_keywords.txt`（59733 行）的核对结果：

| 事实 | 实测 |
| --- | --- |
| 检索数据来源 | 关键词文件（`SongEntityLinker` 读文件），**不是**数据库 |
| 关键词产生时机 | 入库时由当时的 `spaced_lyrics` 生成并追加写入文件 |
| 现存 `lyrics` 的形态 | **3292 / 3320 行（99.2%）为单行且标点已被去除**；仅 28 行保留换行 |
| 关键词长度分布 | 全部落在 6–50 窗口内（`<6` 为 0 个，`>50` 为 2 个） |
| 关键词中的纯 ASCII | 1304 个（2.2%），说明英文确实进入了索引 |
| 关键词中的纯数字 | 1013 个（1.7%），来自《圆周率10000》这类以数字为歌词的页面 |

由此得到两点结论：

1. **改变关键词派生逻辑不会影响已入库歌曲的检索行为**：老数据的关键词在入库时已经固化进文件，
   库里存的 `lyrics` 不参与派生。因此不存在"新逻辑读取旧数据导致检索变化"的兼容问题。
2. **"歌词保留原文行"不是现存数据的形态，也不是稳定契约**：现存数据以单行去标点为主。行结构
   只对尚未入库的新采集数据成立，且不影响索引。因此回归用例断言的是关键词（下游真正消费的产物），
   而不是行数——见 `tests/unit/world/test_vcpedia_lyrics_recovery.py`。

若将来需要**从数据库重建索引**（例如迁移或修复关键词文件），需要注意：现存单行去标点的歌词
在上述窗口下派生不出关键词，重建会让这批数据失去检索能力。该场景本次未验证，仅作为风险记录。

## 结论

经上述测量，**本次交付中没有"关键词可用性"方向的代码改动**：三项候选改动全部被数据否决或证明为
无效。真正被证明有价值的提取行为改进只有一项——**陌生格式页面的歌词覆盖率**（2/20 页面从"取不到"
变为"取得到"），它已由 `tests/unit/world/test_vcpedia_lyrics_recovery.py` 锁定。

## 采样与复现边界

- 只读真实站点，不写入生产数据；采样为当日列表前 20 首，样本量有限，结论以方向与量级为准。
- 本文早期版本的"46.2% 丢弃率""757 片段"等数字口径有误，已按生产路径重测并在此更正；被否决的
  候选改动保留在上文，以免后续重复提出。
- 结论仅覆盖"关键词检索可用性"；若将来需要角色朗读歌词原文，格式保真需要重新评估。

## 未决问题
