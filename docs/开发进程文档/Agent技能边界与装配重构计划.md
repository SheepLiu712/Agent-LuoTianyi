# Agent 技能边界与装配重构计划

日期：2026-11-03。

状态：设计与实施计划草案。能力划分遵循本轮已确认的讨论；本文提出的接口名称、数据结构和迁移次序是待实现设计，不代表当前代码已经具备这些接口。按照[开发守则](../开发守则.md)，完整设计须由非作者开发者审核，才能作为后续交付依据；审核可与实现 PR 一同进行。本文不要求立即实施全部步骤。

## 1. 目标与用户故事

1. 作为开发者，我希望 Handler（刺激或行动处理器）能够直接调用明确的认知和执行能力，而不必了解模型、提示词、存储和角色资源的内部装配。
2. 作为开发者，我希望修改一个技能的模型配置时，只修改统一技能配置节点，技能自行注册模型模块，不再修改运行时的一组模型创建参数。
3. 作为用户，我希望聊天、通话、动态互动中的记忆归属一致，明确要求记住的内容与已经成立的角色经历不会在重构中被遗漏或错误归属。
4. 作为用户，我希望流式回复继续提前输出，并在取消或关闭交互后停止剩余生成；不同用户、角色的并发请求互不干扰。
5. 作为后续 Agent 工具调用的开发者，我希望技能具有清晰的业务输入、结构化结果和副作用约定，可通过适配层暴露为工具。

工具调用指 Agent 通过结构化参数调用能力；MCP（模型上下文协议）是未来可选的接入形式。本计划不实现模型自动选工具、MCP 服务或动态插件注册。

## 3. 统一接口原则

### 3.1 深模块与单一功能

深模块是通过少量稳定接口隐藏完整实现复杂性的模块。单一功能按业务目标判断，不按方法数量或内部步骤数量判断。

1. Handler 可见的技能主要是认知能力和执行能力。认知能力产生理解、判断或内容；执行能力实施已确定的动作或状态变更。
2. 内部实现不注册到共享技能集合，不使用 `Skill` 后缀；Handler 不导入内部解析器、模型包装、存储写入器或资源构造器。
3. 刺激消费、行动计划身份、交付回执、交互打断和生命周期留在 Handler、processing 或 Stage。
4. 一个 Skill 可以调用另一个 Skill，也可以提供多个围绕同一业务目标的操作。禁止仅为减少 Handler 行数而把整段事件流程包装成新 Skill。
5. 一个 Skill 模块可以对应多个未来工具入口。采用明确的 `generate`、`publish`、`search` 等操作，不提供包含任意参数的通用 `execute`。
6. 生成与提交是不同操作。生成结果不等于持久化成功；提交结果必须携带实际业务身份。

### 3.2 模型、资源与构造

LLM（大语言模型）调用的提示词组织、模型模块注册、调用、响应解析及错误定位，全部归使用该模型的 Skill 内部。

```python
# 拟定构造形状；类型名表示职责，不是现有代码。
ReplySkill(config, *, llm_service, characters)
MemoryWriteSkill(config, *, llm_service, memory_store, vector_store)
DynamicSkill(config, *, llm_service, dynamic_store, characters)
```

- 需要模型的 Skill 接收 `llm_service`，在构造阶段或明确的技能初始化阶段自行注册私有 `llm_module`。Handler、AgentRuntime 和共享技能装配器不得替技能创建模型模块。
- “只传入 llm_service”针对模型依赖，不排斥显式传入配置、角色资料、存储、媒体解析器或另一个 Skill。
- 技能内部辅助实现可以使用该技能创建的模型模块；外部不得注入预构造的模型字典、生成器或提示词组装器作为生产接口。
- 对图片、音频理解使用的相应模型模块采用同样规则，仍通过统一模型服务注册。
- 构造阶段校验启用能力的必需配置、角色资源和引用；缺失时定位到配置路径并立即失败。不得选择任意供应商、任意角色或空模型继续启动。
- 模型注册名称应同时标识技能、操作及必要的角色，避免角色间配置覆盖。不得在每次业务调用时重复注册。
- 所有角色共用技能实例；角色资源可在创建时绑定为只读映射。当前用户、当前角色、解析状态和生成缓冲不得写入共享实例。
- 模型服务拥有连接与通用模型资源生命周期；技能只释放自己创建并拥有的任务或专用资源。复合技能不得重复关闭其借用的其他技能。
- 仅组合其他技能而不直接调用模型的 Skill 不必接收 `llm_service`。例如 DiarySkill 通过 DynamicSkill 生成内容时，不再创建第二套日记生成模型模块。

### 3.3 调用、返回值和副作用

身份沿用 [SkillInvocation](../../server/src/agent/skills/contracts.py)（一次调用的角色、用户、交互身份与取消上下文）或等价的最小受信调用上下文，由运行时提供。领域中已存在的角色标识可继续使用 `character_id`；未来工具参数不得自行扩大身份与数据访问范围。

| 接口类型 | 行为约束 |
| --- | --- |
| 读取与检索 | 返回结构化业务结果，不写入聊天记录或改变交互状态；无结果与系统失败必须可区分 |
| 内容生成 | 返回内容、决策或草稿流；不隐式发布，不修改调用方上下文 |
| 提交与发布 | 返回提交身份、是否新建等结果；去重依据和部分失败语义在接口中声明 |
| 流式生成 | 只输出已完成解析的业务草稿；调用方提前停止时关闭异步流，技能取消并等待内部任务 |
| 复合维护 | 可以有内部副作用，但必须隐藏步骤顺序与进度一致性，不要求 Handler 手动执行内部阶段 |

使用业务值对象表达输入与输出；不接收完整 `HandleStimulusRequest`、`PlanEmitter`、`OutputEmitter` 或整个运行时作为技能参数。维护类技能如确需更新上下文，只接收专门的维护接口或明确的领域上下文，不取得 Stage 或网络对象。

未规定的依赖错误、非法配置和模型输出错误在发生处记录并向上抛出，不新增吞错、空结果降级或重试。既有 spec 明确规定的失败处理只能保留在其责任位置。每步实施前核对受影响的现有失败契约；发现与本计划冲突时单独列明，不以重构名义暗改行为。

## 4. 目标能力集合

本表中的新名称为拟定名称，避免将名称误认为已经存在的类。

| 对外能力 | 单一业务目标 | 迁移与内部实现归属 |
| --- | --- | --- |
| ReplySkill | 生成角色回复草稿流 | 保留，模型注册和角色生成资源构造迁入内部 |
| ImageUnderstandingSkill、AudioUnderstandingSkill | 理解受控媒体 | 保留；可以依赖术语识别能力 |

| DiarySkill | 组织指定日期的日记材料并生成、发布日记 | 组合 DynamicSkill，保留日记的私密性、日期范围和来源身份规则 |

## 5. 分步实施计划

### 步骤一：统一技能配置与模型创建责任

**目的**：把技能装配变成配置与资源的显式连接，移除运行时对提示词和模型模块构造的了解。

**接口设计**：

```python
SharedSkills(config: SkillsConfig, *, resources: SkillResources)
```

`SkillsConfig` 是经校验的技能配置；`SkillResources` 是具名、类型明确的模型服务、存储、媒体和角色资源集合。仅共享装配器接收该集合，并为各技能传递最小依赖；具体 Skill 不接收可任意查找依赖的大字典。

实现位置以现有 `agent/skills/facade.py` 为装配入口。配置解析属于既有配置加载流程，Skill 不自行读取 `config.json`。内部模块可以按单一功能分文件，但不额外对 Handler 暴露。

**配置迁移**：

| 当前节点，均相对于 agent_runtime | 目标节点，均相对于 agent_runtime.skills |
| --- | --- |
| agent.main_chat | reply |
| agent.preprocessing | jargon_recognition |
| agent.topic_extractor | topic_extraction |
| agent.memory.explicit_intent | explicit_memory_intent |
| agent.memory 中的写入模型与写入策略 | memory_write |
| agent.memory 中的检索策略 | memory_retrieval |
| agent.memory.user_profile、对话压缩及通话维护模型配置 | cognitive_maintenance 的内部配置 |
| agent.call_summary | call_summary |
| skills.dynamic、skills.diary | dynamic、diary，后续按新接口整理内部字段 |
| prepared_speech | prepared_speech 资源配置；不是新 Skill |
| reply_composition | 暂入 response_composition，步骤九删除其场景编排配置入口 |
| agent.song_knowledge | knowledge 资源配置；不是新认知 Skill |

已有 speaking、singing、image_understanding、audio_understanding 配置保留在统一节点。触摸反应策略归 `skills.touch_reaction`；角色身份、人设资源定义仍归角色注册，只在技能配置中引用角色标识。模型供应商连接、数据库连接和向量存储连接分别归对应基础设施配置；技能配置只引用资源并声明自身策略。

一次交付内同步修改配置读取方、默认配置、配置模板与相关管理界面消费者，不长期保留新旧节点优先级逻辑。旧节点遗留时提供明确迁移错误，不能静默忽略。后续技能改名时同步调整统一节点，不重新产生散落配置。

**验收标准**：

- A1：使用迁移后的完整配置启动，聊天、图片及音频理解、动态生成等已启用能力可以初始化；改变一个技能的模型引用只影响该技能，其他技能仍使用各自配置。
- A2：启用回复能力但缺少模型引用时，初始化失败并指出具体配置路径；不得启动到首次聊天才发现无模型。
- A3：两个角色使用不同人设及模型配置并发生成，结果分别使用对应角色资源；增加角色无需在 AgentRuntime 新增模型创建分支。
- A4：使用旧配置节点时明确报告迁移需求；配置读取与管理界面不会覆盖或丢失已迁移的技能配置。
- A5：关闭或初始化中途失败时，已创建的技能专用资源完成释放；共享模型服务不被多个技能重复关闭。

### 步骤二：建立统一记忆写入深模块

**前置**：步骤一。

**职责**：MemoryWriteSkill 负责记忆形成和提交，内部封装模型提取、规范化、作用域、去重、规范存储和检索索引协作。用户画像维护仍属于认知维护，不并入通用记忆写入入口。

**拟定接口**：

```python
await memory_write.remember_event(invocation, *, event: MemoryEvent) -> MemoryWriteResult
await memory_write.commit_fact(invocation, *, fact: MemoryFact) -> MemoryWriteResult
```

- `MemoryEvent`：来源类型、稳定事件标识、发生时间、结构化正文、必要背景、记忆作用域。用于从经历中提取值得长期保留的记忆；可以正常返回“没有候选”。
- `MemoryFact`：来源身份、已确认正文、作用域和提交依据。依据至少区分“已确认业务事实”和“用户明确要求”。不得重新以提取模型判断是否值得记住。
- 作用域明确区分角色自身经历与该角色对指定用户的记忆；不得以角色标识冒充用户标识实现路由。
- 已有存量记录必须有显式的作用域迁移或受控读取适配方案：旧角色经历可继续读取，用户记忆不能因标识相同而被迁入角色公共范围。适配仅封装在记忆内部，并说明移除条件；不得要求 Handler 判断新旧存储格式。
- `MemoryWriteResult`：区分新建、重复、无候选，返回真实记忆标识和源事件标识；失败抛出明确错误，不能返回成功布尔值掩盖部分提交。
- 去重以来源身份和候选身份为依据，重复处理同一事件不得生成第二份业务事实。多候选提交失败后不得声称整个事件已完成；重试收敛范围与存储机制一起验证，不承诺跨存储的恰好一次执行。

Handler 决定何时提交；明确记忆提交成功后才组织确认回复。学歌 Handler 构造已确认事实并调用 `commit_fact`，不把事实重新交给模型提取。动态 Handler 提供事件及作者归属，不拼接存储格式。

**迁移与删除**：迁移 DynamicTopicMemorySkill、LearnedSongExperienceSkill 和 IntentionalMemoryCommit 的调用方，随后删除旧对外入口。当前底层写入实现按职责保留为内部模块。

**验收标准**：

- B1：用户说“请记住我不吃香菜”，提交返回真实记忆标识后才生成保存确认；提交失败时不产生“已记住”的确认。
- B2：重复投递同一学歌任务完成事实，只得到一条角色经历；不得写入任意用户的记忆范围。
- B3：动态事件的作者为用户甲，形成的用户记忆归属甲；用户乙检索时不能得到该私有记忆。
- B4：模型判断普通事件没有可保留内容时返回无候选；模型调用失败则失败，不能伪装成无候选。
- B5：已确认事实和明确用户要求不因提取模型不可用而被重新裁定为“不值得记忆”；底层必要的存储或索引失败仍必须明确失败。
- B6：注入候选提交中途失败，再处理同一源事件，已提交候选不重复，未完成部分不能被错误标为已完成。
- B7：加载改造前的角色经历和用户记忆样本，迁移后内容仍可读取且归属正确；不能因作用域改造丢失或扩大原有数据的访问范围。

### 步骤三：建立通用检索与权威资料查询接口

**前置**：步骤一；与步骤二对齐身份及作用域契约后完成集成。

**职责**：MemoryRetrievalSkill 隐藏查询规范化、存储选择、向量召回、规范记录回查、排序去重和来源解释。是否需要检索由调用方或其他决策技能决定，不能把场景决策隐藏在检索中。

**拟定接口**：

```python
await memory_retrieval.search(invocation, *, query: MemoryQuery) -> MemorySearchResult
await memory_retrieval.list_songs(invocation, *, cursor=None, limit=20) -> SongPage
await memory_retrieval.get_song(invocation, *, song_id, segment_id=None) -> SongKnowledgeResult
```

- `MemoryQuery` 明确查询线索、范围与结果上限；范围包括角色自身记忆、授权的用户记忆及允许查询的公共知识，不能跨用户任意搜索。
- `MemorySearchResult` 返回稳定记录标识、来源、正文及相关性信息；不只返回拼接后的提示词字符串。
- 歌曲目录与指定歌曲查询采用权威资料源，结果包含当前是否可唱、片段及可用歌词。不存在的歌曲返回明确未找到，不以相似歌曲冒充。
- 歌曲查询是检索模块中的明确操作，与语义记忆搜索分开。目录和音频资源的实际持有者仍是歌曲能力内部实现，不复制第二套可唱状态。
- 查询不自动更新通话记忆池。Handler 将命中结果交给当前交互的上下文管理接口；共享技能不持有会话缓存。
- 已知演唱意图到有效唱段的选择规则留在歌曲能力内部，提供明确选择接口；Handler 不调用 `singing.backend` 或角色管理器。音频渲染仍由 SingingSkill 执行。

**迁移**：替换普通回复与通话的直接记忆适配器调用；把 SongLearningDispatchSkill 的材料读取迁入权威查询入口。学歌愿望清单提交改为具名任务提交接口，由请求学歌行动处理器调用；不在单次行动中等待完整学歌流程。

**验收标准**：

- C1：同一事实经多个查询命中时，结果去重且保留来源；结果上限生效。
- C2：角色甲与角色乙、用户甲与用户乙的私有记忆互不泄露；无授权的范围请求失败。
- C3：查询不存在的记忆得到空集合；后端不可用得到错误，两者可区分。
- C4：查询“会唱哪些歌”和指定唱段时反映当前目录；缺失唱段不能由向量相似结果替代。
- C5：通话结束后记忆池释放；同一共享检索实例仍可服务其他通话，且不残留上次会话状态。
- C6：重复提交同一学歌请求不新增重复任务；资料查询不会意外派发学歌任务。

### 步骤四：整合 DynamicSkill，并建立 DiarySkill 组合接口

**前置**：步骤一；动态记忆调用迁移依赖步骤二。

**职责**：DynamicSkill 围绕动态内容及其线程提供完整能力，内部隐藏记录格式、模型选择、角色资料及原帖与评论分支。DiarySkill 只负责日期范围、材料组织、日记表达和私密发布约束，通过 DynamicSkill 复用生成与发布能力。

**拟定接口**：

```python
await dynamic.read_thread(invocation, *, target: DynamicTarget) -> DynamicThread
await dynamic.generate(invocation, *, request: DynamicWritingRequest) -> DynamicDraft
await dynamic.generate_reply(invocation, *, thread: DynamicThread, target_id) -> DynamicReplyDecision
await dynamic.publish(invocation, *, draft: DynamicDraft, publication: DynamicPublication) -> PublishReceipt
await dynamic.publish_reply(invocation, *, draft: DynamicReplyDraft, publication: ReplyPublication) -> PublishReceipt
await diary.generate(invocation, *, local_date) -> DiaryDraft
await diary.publish(invocation, *, draft: DiaryDraft) -> PublishReceipt
```

- 读取只返回调用身份有权访问的线程，包含稳定消息标识、作者、父消息关系和顺序。
- 生成动态的请求包含明确写作要求、结构化材料和必要文体约束；模型注册、提示词与解析全部在 DynamicSkill 内部。
- 回复决策包含“回复草稿”或“明确忽略及原因”；已回复目标、无回复意图和依赖失败不得混成空字符串。
- `DynamicPublication`、`ReplyPublication` 声明来源身份、发布目标、可见性和业务归属。发布不重新生成，返回真实动态或评论标识。
- 现有来源去重语义迁入模块内部；对评论发布是否具备相同去重能力按实际存储验证，不从动态发布机制推断。若需补齐，作为本步显式交付项完成。
- DiarySkill 收集指定日期的授权材料，向 DynamicSkill 提供日记写作要求。私密、不可评论和角色／用户／日期来源身份由日记能力约束，调用方不能无意改为公开。
- Handler 保留记忆与回复的先后关系、计划构造和刺激结算，不再调用 `build_item`、区分生成器分支或解释旧字典格式。

**迁移与删除**：迁移动态观察、散步、学歌和日记处理器；删除 DynamicPublishingSkill、DynamicReplySkill、DiaryWritingSkill 旧对外入口。动态和日记的旧生成实现不得作为平行生产路径继续存在。

**验收标准**：

- D1：给定原帖和评论线程，分别针对原帖与评论生成正确回复目标；Handler 不需要构造内部条目字典。
- D2：目标已存在角色回复时返回明确忽略；生成模型失败时报告错误，不返回“决定忽略”。
- D3：只调用生成接口时，动态与评论存储均不增加记录；发布已生成草稿时不再次调用生成模型。
- D4：重复发布同一业务来源得到同一提交身份或明确已存在结果，不生成第二份业务内容。
- D5：读取无权访问的私密线程失败；日记发布后只有授权用户可见，且不可评论。
- D6：生成某日期日记只使用其允许的材料范围，保持日记表达约束；重复发布同一角色、用户、日期的日记不重复建档。
- D7：散步和学歌动态继续使用各自的事实与表达要求；知识或经验记忆的提交结果不被动态发布结果覆盖。

### 步骤五：清理通话回复包装与未启用决策路径

**前置**：步骤三；共享 ReplySkill 的模型归属已在步骤一完成。

**职责**：通话 Handler 编排“检索、准备上下文、生成、交付”，调用 MemoryRetrievalSkill 和 ReplySkill。删除 CallReplySkill；原草稿筛选和通话输出转换留在处理器侧的内部函数或 processing 模块，不另建 Skill。

删除 CallRecallDecisionSkill 的未启用快速模型路径及配置装配；原召回操作使用通用检索。保留通话记忆池的业务作用，但通过上下文接口管理。

每个有效正式回复请求以本轮待回复内容形成查询并执行一次检索能力调用；不得因已有记忆池而跳过该策略。“一次调用”不要求底层多查询只能执行一次数据库请求。

沉默 Handler 对有效沉默刺激采用 SPEAK，明确要求开启新话题。没有快速决策模型时不保留 WAIT／END_CALL 的虚假决策入口。用户挂断、通话期限等既有结束机制不变。既有回忆过渡语如需保留，由 Handler 按通话约定组织，不为此恢复决策模型。

**验收标准**：

- E1：未配置快速模型时，每个有效正式回复请求都会检索；既有记忆池非空也不跳过检索。
- E2：收到有效沉默刺激时，生成并交付新话题回复；不会只返回 WAIT，也不会仅因沉默次数产生挂断行动。
- E3：Stage 已判断沉默刺激失效、用户开始说话或已有不允许并行的回复时，不额外生成重复主动回复。
- E4：首段回复在模型完整结束前进入语音合成；取消后关闭草稿流及内部任务，不继续交付剩余内容。
- E5：未确认播放的通话草稿不进入正式对话记录；已确认文本按现有确认事实入库。

### 步骤六：将概要生成与概要提交分离

**前置**：步骤一；可与步骤五独立实施。

CallSummarySkill 只拥有通话概要生成目标。初始化接收配置及模型服务，自行注册模型；调用输入改为明确的通话材料快照，不接收可写交互上下文。

```python
await call_summary.generate(invocation, *, material: CallSummaryMaterial) -> CallSummaryResult
```

`CallSummaryMaterial` 包含已有工作摘要、剩余正式记录和终态中已接纳但尚未写入的输入事实；同时携带范围或来源标识，避免重复计入。只纳入已确认角色回复，不能把未播放完成的草稿当成已发生事实。材料合并与去重规则属于技能内部。

结果区分生成概要与无可总结材料；生成失败按既有通话 spec 的失败契约向调用方明确表达。Handler 决定提交生成概要或执行既有的概要回退，并将概要来源写入结束结果。不得新增无依据的兜底概要。

**验收标准**：

- F1：只调用概要生成时，交互工作摘要和正式历史均不改变。
- F2：Handler 接收到成功结果后才更新工作摘要；提交失败不能声称概要已经保存。
- F3：混合输入已有压缩摘要、剩余记录及结束快照时，同一输入不重复总结，未确认回复不计入。
- F4：概要生成失败时，原有明确规定的结束回退仍可执行，结束结果准确标记概要来源。

### 步骤七：把 CognitiveMaintenanceSkill 做成唯一维护入口

**前置**：步骤二；与步骤六对齐结束提交时序。

**职责**：统一维护能力内部处理压缩、记忆候选、画像更新、批次冻结和进度提交。ConversationCompactionSkill、CallMaintenanceSkill 改为维护包内部模块，不注册到 SharedSkills，也不让 Handler 导入。

```python
await cognitive_maintenance.maintain(invocation, *, request: MaintenanceRequest) -> MaintenanceResult
```

`MaintenanceRequest` 明确维护原因、授权的维护上下文及输入范围；通话事实需要专用快照时显式提供。阈值是否满足、使用哪种内部维护策略由技能决定。返回跳过、完成或已有契约中的冲突结果，以及实际处理范围；不把冲突伪装成完成。

Handler 不再直接调用“通话维护实现”，也不手动推进内部批次。内部可以调用 MemoryWriteSkill 的事实提交能力；但冻结批次、候选身份和进度一致性仍由维护模块负责，不能重新提取已冻结批次或无条件重复写入。

**验收标准**：

- G1：低于压缩阈值时返回跳过，不新增长期记忆、画像变更或维护进度。
- G2：同一冻结批次恢复或重复处理时，不重新调用模型生成不同候选；已提交事实不重复生成。
- G3：注入部分写入失败后，进度不提前宣称整批完成；后续处理能够按已有机制收敛。
- G4：普通聊天与通话结束均只调用统一维护能力，且原有压缩、用户画像和通话进度行为保持正确。
- G5：结束维护失败时，Handler 仍按既有约定处理概要与结束结果，Stage 能完成资源关闭；维护技能不接管交互生命周期。

### 步骤八：术语识别改名与保留能力的接口整理

**前置**：步骤一；其余能力按各自前置步骤接入。

TextPreprocessingSkill 改为 JargonRecognitionSkill，提供 `recognize(text)`，返回规范化术语集合。先保持当前歌曲实体识别行为，迁移所有调用与配置名称，不新增未经验证的词库或模型推断。

TopicExtractionSkill 与 ExplicitMemoryIntentSkill 保持现有业务行为。图片、音频理解可以接收 JargonRecognitionSkill 依赖，但本步不强制改变其返回契约，也不重复识别同一份文本。

保留 TouchReactionSkill、SpeakingSkill、SingingSkill。触摸策略与资源选择封装在触摸能力中；语音合成和歌曲渲染不取得计划接收器。预制语音目录保持资源接口。对外不暴露 TTS 后端、唱歌管理器或歌曲能力的 `backend` 属性供 Handler 操作。

**验收标准**：

- H1：给定已知歌名、歌词线索及无关文本，改名前后的规范术语结果一致；无关文本不被升级为确定演唱意图。
- H2：明确记忆短语识别、主题提取行为不因改名改变。
- H3：两个角色采用各自触摸、语音和演唱资源；输出内容与角色对应，资源缺失不会串用其他角色资源。
- H4：说话和演唱仍输出原有文字、表情、音频及结束事实，Handler 不需要调用内部后端。

### 步骤九：最后拆除回复场景编排，并完成配置收口

**前置**：步骤二至八中相关能力已迁移；优先级低于独立能力接口建设。

拆除 ResponseCompositionSkill，普通聊天和主动提醒 Handler 显式组合：主题提取、记忆检索、歌曲资料与唱段选择、回复生成。步骤之间传递结构化结果，Handler 不创建模型或读取后端目录。

Handler 根据触发事件组织本轮回复指令，ReplySkill 根据准备好的资料输出草稿流。回复记录、打断控制和计划交付继续使用现有 [ReplyDelivery](../../server/src/agent/processing/reply_dispatch.py)（处理器侧回复交付流程）与计划封装模块。

可复用的纯材料转换函数留在 processing，不注册为 Skill。慢召回的计时、是否先交付过渡语等场景规则若仍有有效用途，应进入明确的 Handler／交互配置；无生产消费者的旧配置及延迟包装一并删除，不迁入 ReplySkill。

最终删除旧技能导出、旧模型注册辅助方法、旧配置节点和生产兼容分支。同步更新代码地图、配置说明及受影响接口文档；不保留两个同业务含义的生成入口。

**验收标准**：

- I1：普通消息、明确记忆提交后的确认、主动提醒均正常生成回复，记忆与演唱信息来自已定义的能力接口。
- I2：有有效唱段时生成正确歌曲计划，无有效唱段时不得仅凭模型输出执行演唱；歌词与可唱片段保持一致。
- I3：长回复仍增量输出且无重复前缀；生成中途失败时不把未生成部分记为已经回复。
- I4：先追加普通聊天记录再交付计划、通话确认后记录等既有语义不被重构暗改；不宣称记录写入与计划交付已具有原子性。
- I5：新增一个角色只需角色资源及相应配置；新增使用已有能力的 Handler 不需要新增模型模块装配代码。
- I6：最终技能配置只有统一来源，Handler 不依赖内部实现；未迁移旧配置会明确失败，不静默使用另一套默认值。

## 6. 实施次序与交付约束

建议顺序：步骤一 → 步骤二 → 步骤三 → 步骤四 → 步骤五 → 步骤六 → 步骤七 → 步骤八 → 步骤九。步骤六、步骤八可在其前置条件满足后提前实施；不通过并行保留旧生成实现来规避迁移。

每一步按一个可独立验收的功能交付组织，必要时拆为多个明确工单，不按目录机械拆分。配置与消费者必须在同一可运行交付中完成对应迁移。未完成的后续步骤不妨碍已完成能力使用，但阶段性遗留必须记录，不能提前宣布最终技能目录已收口。

每步交付包含：

1. 最终接口、调用方迁移与旧入口删除清单。
2. 对应验收标准的执行证据，包含失败与取消路径。
3. 受影响配置的迁移样例和配置校验结果。
4. 当步必要的代码地图与接口说明更新。

## 7. 验证方式与完成判定

测试只增加开发者或用户可感知的行为：角色隔离、配置错误定位、生成与提交分离、记忆归属、重复提交、流式提前输出、取消清理、通话沉默行为和可访问范围。不为每个内部类建立镜像测试，不用“某私有方法被调用几次”替代业务验收。

- 技能接口测试使用假的模型服务，由 Skill 自己注册模型；测试替身实现真实模型服务所需的最小契约，不通过生产接口注入已创建模型。
- 记忆和动态提交使用现有临时存储或真实存储适配器的集成测试，验证提交身份、读取结果和重复处理行为。
- 普通聊天、通话、图片和语音链路按受影响范围运行现有单元、集成及离线端到端测试，参考[代码地图的测试入口](../代码地图.md#6-server-测试管理与运行)。
- 运行受影响文件的 Ruff、Black 及差异检查；模块导出或路径改变时检查打包与正式装配。
- 模型内容质量、真实供应商或设备行为只有经过对应真实验证才可声明；离线测试通过不等于真实模型效果已经验证。

所有步骤对应标准通过，生产调用方和配置迁移完成，旧入口清理完成后，才能宣布本次重构完成。本文不承诺额外的事务一致性、重放恢复、跨进程恰好一次执行或新失败回退策略。
