# 慢召回多计划规格（提案，未实现）

- 状态：**设计提案，待评审**。只记录触发条件与计划契约，不实现。
- 关联工单：Issue [#70](https://github.com/SheepLiu712/Agent-LuoTianyi/issues/70)（11 接入慢 Recall 的多计划回复策略）
- 相关规范：总 SPEC 第 4.5、6.8 节；现状 `agent/skills/cognitive/response_composition.py`（召回与生成在同一次 `compose` 内）

## 1. 要解决的问题

SPEC 6.8 要求：一次 handle 内可以先交付一个**完整的临时计划**（例如「让我想想……」），再在 deep recall 完成后交付**完整的正式计划**；临时计划不是半成品，后续计划不修改前者。

现状：`ChatReplyHandler` 的召回与生成在同一个 `ResponseCompositionSkill.compose` 调用内完成，**没有中间信号**表明「需要等一次慢召回」，因此无法决定何时先交付临时计划。

需要先定义：**什么条件触发临时计划、临时内容从哪里来、取消/修订如何生效**。

## 2. 触发条件备选

| 方案 | 触发 | 评价 |
| --- | --- | --- |
| A. 认知技能显式信号 | `compose` 分两段：先返回「已发起 deep recall + 一个临时草稿」，handler 先 emit，再 await 正式结果 | 与 SPEC 6.8 最贴合；需要技能接口扩展（内部） |
| B. 时间阈值 | `compose` 超过 N 毫秒未完成则先 emit 临时计划 | 需在处理中并发等待与取消，复杂度高；阈值难定 |
| C. 暂缓 | 等真实 deep recall 能力存在再实现 | 不阻塞其它切片，但 11 长期悬空 |

倾向 **A**：由认知技能显式报告「需要慢召回」，handler 据此先交付临时计划；临时内容来自角色配置（不是硬编码），并标注为**完整可独立实现**的 `Say`。

## 3. 建议契约（目标，未实现）

- 认知技能新增一个内部分段结果：`(临时计划草稿 | None, 是否需要等待正式结果)`；
- handler 若拿到临时草稿：先 `plans.emit(临时计划)`，再 `await` 正式结果；`await` 返回后检查 `request.cancellation` 与 `basis_interaction_revision`，未取消才 emit 正式计划；
- 临时与正式计划携带**同一** `basis_interaction_revision`；Stage 的 sink 按当前修订接受或拒绝；
- 取消时临时计划已交付的事实保留，正式计划不再交付；
- Recall 完成只唤醒当前 coroutine，**不产生 `RecallCompleted` 刺激**、不递归调用公开接口。

## 4. 影响面与未决问题

- 影响：`ResponseCompositionSkill` 内部接口分段；`ChatReplyHandler` 交付两次计划；测试需覆盖「临时 + 正式」与取消。
- 未决：
  1. 是否采用方案 A（技能显式信号）？
  2. 临时文案放配置还是角色人设文件？由谁决定「值得先说一句」？
  3. 正式结果晚到时旧临时计划是否需要在客户端被替换（沿用现有正常顺序机制即可）？

## 5. 明确不包含

- 本提案不实现分段召回、临时计划或阈值逻辑。
- 不新增公开 Stimulus/Action；不改 Stage 的取消与结算语义。
