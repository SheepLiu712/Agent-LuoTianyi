## 1. 要解决的问题

目标链路是：`world 唤醒 → ChatStage 判断当前聊天是否适合 → 构造 ProactivePromptDue → handle → 计划 → realize`。其中：

- `world_clock` 只做唤醒（每 300 秒），**不再**直接调用旧 `ProactiveTopicMaker`/`TopicReplier`；
- ChatStage 拥有「活跃流、空闲阈值（默认 30 秒）、通知 claim」；
- 到期事件来自 `EventStore`，需要按 `(event_id, user_id, character_id, trigger_key)` 去重。

现状缺口：`ProactivePromptDue` 已可构造，但**没有生产者**；ChatStage 也**没有到期事件来源**。因此需要定义 Stage 侧的事件来源与 claim 契约。

## 2. 事件来源的取舍

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| A. 注入窄端口 `DueEventProvider` | Stage 依赖一个只读端口，返回候选到期事件并支持原子 claim/release | 与「world 拥有权威事实、stage 只做交互」一致；端口属新 interface 需评审 |
| B. Stage 直接依赖 `EventStore` | 少一层抽象 | 把存储细节带进 stage，违反分层 |
| C. world 侧把候选事件作为 Stimulus 投递给 Stage | 复用既有投递形态 | 需要 world→stage 的新投递 seam（与 19 WorldStage 重叠） |

倾向 **A**：定义最小端口（列候选 + 原子 claim + release），由 `SystemRuntime` 装配 `EventStore` 适配；Stage 只做空闲判断与提醒构造。

## 3. 建议端口（目标，未实现）

```python
class DueEventProvider(Protocol):
    def list_due(self, *, character_id: str, user_id: str, now: datetime) -> tuple[DueEvent, ...]: ...
    def claim(self, event_id: str, *, user_id: str, character_id: str, trigger_key: str) -> bool: ...
    def release(self, event_id: str, *, user_id: str, character_id: str, trigger_key: str) -> None: ...

@dataclass(frozen=True)
class DueEvent:
    event_id: str
    trigger_key: str
    reason: str        # holiday / travel / new_song / birthday / anniversary ...
```

- **Stage 行为**：仅对「活跃且空闲 ≥ 阈值」的流检查；对每个流从候选中随机取一；claim 成功后构造 `ProactivePromptDue(reason, due_at, dedup_key, fact_refs)` → `handle`；
- **失败**：claim 后入队失败或取消 → `release`，保证后续登录/周期仍可重试；
- **去重**：成功 claim 保证当天登录路径与周期检查不重复提醒；
- **归属**：过滤 personal/已通知项在 Stage 侧（拥有用户与流上下文）。
