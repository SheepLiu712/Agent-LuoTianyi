# 用户实时语音通话 · 实现计划

> 状态：骨架验证与独立风险核验已完成；非完整 F2 交付。骨架只提供可独立测试的值对象、端口、纯状态与存储契约，未接入生产消息链，不代表任一完整 AC 已达成。
> 依据：本目录《用户实时语音通话-spec.md》（19 条 AC）、基线 `upstream/dev` @ `62c0bd73`、[骨架范围矩阵](用户实时语音通话-骨架范围.md)
> 分支：fork `origin` 的 `feat/realtime-call-skeleton`（从 `upstream/dev` @ `62c0bd73` 建立；已确认）

## 一、范围

Android 端实时语音通话（`call.v1`）：独立 `call_ws`、CallStage、RealtimeSpeechSession（阿里云首个实现）、Agent 主导决策、TTS CALL 路由、呼叫账本与结算、认知维护迁移。

非目标与未来目标见 spec；本计划只覆盖 spec 声明的第一版。

本骨架按 CL-1…CL-12 覆盖各模块的最小边界，采用原子提交并推送 fork；集成前仍需按《开发守则》补齐受影响范围验证与非作者审核。F1 已由 PR #244 合入 `dev`，并合入 `master`、打 `v0.5.0` 标签；截至 2026-10-09，标签存在但尚无 GitHub Release。该历史事实仅说明可从 `dev` 基线复用既有语音消息能力，不把 `feat/voice` 后续提交当作本骨架基线。

## 二、当前基线（侦察结论，与 spec 预期的差异）

- 服务端生产链仍只有 `/chat_ws`（`web/websocket/endpoint.py`）；使用 `receive_json`，没有 `call_ws`、二进制帧收发或 CallStage 接线。现有入站 JSON 默认上限为 128 KiB，图片路径为 8 MiB 加 128 KiB；CALL 二进制帧上限仍待实现。
- Stage 的生产路径仍为 ChatStage + StageManager（进程内 `_stages`、60s 离线保留）。本分支新增的 `InteractionLeaseRegistry` 与 `CallLifecycle` 是独立、进程内的纯骨架，前者实现 10 秒一次性切换 intent，二者尚未接入 StageManager 或 CallStage。
- CL-1 已在独立 `feat/call-cognitive-maintenance` 分支实现，基线为 `0014231e`，依赖 PR #269 的骨架但不改变 #269 的范围；实现尚待非作者 spec 审核。生产聊天链已改为在每次正式回复后排入阈值维护行动、并在 `InteractionEnding` 经 Agent 行动执行结束维护，结束维护失败或超时仍关闭 context。CallStage、turn sequence、`SWITCH_TO_CALL` 的生产切换仍是后续工单范围。
- Context Store 已完成组合重构：聊天默认使用 `DatabaseConversationStore`，测试或后续 CallStage 可显式注入 `EphemeralCallConversationStore`；本骨架没有实现三分钟 base snapshot 查询，也没有让生产 Stage 创建通话 Context。
- TTS：`speaking` 已有流式取消；输出链路为 JSON Base64（48 KiB/包），无 CALL 的 `audio_route`、`stream_id`、`response_id` 或 `seq` 字段。
- 幂等表（adapter）与投递队列（256/16MiB/64）均为进程内内存态；单 worker 仅是事实约定，无检查。
- App 已有 F1 权限、录音生命周期与文件播放基础；本分支新增 headless call reducer、effects 与技术中立音频端口，未新增 UI、网络、PCM、AEC 或播放实现。音频能力默认 `unresolved`，Spike-B 仍待结论。
- 本分支新增供应商中立 RealtimeSpeechSession 端口与 fake、默认容量为 10 的通话记忆池、隐私白名单 ledger record/repository 协议及 fake。它们均无供应商实现、SQL、概要、历史投影或生产装配；UUIDv5 namespace 由调用方显式提供，项目常量尚未选定。
- 新建的 `docs/adr/` 只存 Proposed ADR；`call.v1` wire 格式未冻结。

1. 工单 = 可独立说明交付结果的单位；本骨架从 fork `origin` 的 `feat/realtime-call-skeleton` 向 `upstream/dev` 提交跨仓库 PR，不使用旧的 `feat/voice` 集成口径。

3. 模块归属以《代码地图》为准；深模块、单一职责；新增转发接口要有真实第二实现才建。
4. 代码风格：black 120 + ruff（含 C901≤10）；app 用 Expo 默认。
5. 提交规范：工单内按逻辑单元**原子化提交**——每个提交自洽、可独立解释、配套其测试，不混入无关改动；工单 PR 由这组原子提交组成。

## 五、详细工单

### CL-1 认知维护迁移（前置，AC-15）

状态：已实现，待非作者 spec 审核；不是完整 F2 交付，且不表示 CL-2…CL-12 已完成。

1. `CognitiveMaintenanceSkill` 在压缩阈值用 `maintain_if_compaction_needed`，在 `InteractionEnding` 用 `maintain(reason=...)`；阈值以下行动没有长期记忆、画像或进度副作用。
2. ChatStage 只调度：正式回复后的阈值维护与结束维护均为 Agent 行动。结束路径等待 `realize_action_plan`，维护失败或超时也关闭 context；结束维护不产生用户可见输出。维护在最终 SQL 提交前失败或取消时不推进进度；owned SQL 事务一旦启动可能完整提交后再传播取消，因此 timeout/取消不承诺回滚。
3. 聊天维护进度以 `(user_id, character_id, predecessor)` 作为唯一批次键。候选和画像先被冻结并持久化，竞争写入使用随机持久化胜者 `maintenance_id`；候选/profile/compaction 输入不会在重试或竞争者中重新生成。该设计是 at-least-once 的幂等收敛，不是 exactly-once。
4. 压缩与进度在单个 SQL 事务中提交；旧库升级新增可空 marker，保留 `NULL` 表示「没有可信的成功维护记录」，不能据此判断历史 Reflection 是否曾产生记忆或画像。重置用户对话时删除该用户的维护批次和上下文，因而重置进度。`memory_chunks.embedding_id` 建立部分唯一索引；历史非空重复值使启动显式以 `RuntimeError` 失败，绝不自动删除或重写历史。
5. 旧 Reflection 类型、处理器和配置读取暂作兼容残留，未在生产 Agent 路由注册；本工单不声称完成全量重命名/删除。通话 `maintenance_turn_seq`、CallStage、`SWITCH_TO_CALL` 和生产切换仍留给后续工单。

验证与迁移、未验证项见 [认知维护迁移与验收](../../server/docs/dev/认知维护迁移与验收.md)。

### CL-2 上下文 Store 拆分

### CL-4 web/adapter 信道扩展

骨架状态：仅记录 Web/Adapter 边界；没有 `/call_ws` 端点、二进制接收、Adapter 解析或投递实现。

1. `/call_ws` 端点：鉴权复用、`receive()` 分派 text/binary、入站帧上限。
2. Adapter：控制帧解析、`call_id` 与 CallStage 绑定、统一连续游标 ACK、缺口 NACK、30s/4MiB 重放缓冲、取消范围替换、有序背压投递、resume 重放。
3. `_protocol` 增加 CALL 路由字段（audio_route/stream_id/response_id/seq/final）。

验证（integration/websocket）：帧协议、游标推进、缺口、重放、协议冲突断连。

### CL-5 StageManager 切换与租约

骨架状态：独立 `InteractionLeaseRegistry` 提供单进程租约与 10 秒一次性 intent；未接入 StageManager，未创建或回收任何 Stage。

1. `InteractionLeaseRegistry`：同用户同角色原子所有权；`CallTransitionIntent`（一次性、10s、绑定 user/char/interaction/client_request_id）。
2. `switch_prepare` → `switch_ready`；`call.start` 消费意图 → 建 `PREPARING` 账本 → 旧 ChatStage 以 `SWITCH_TO_CALL` 终止（先回收、关旧 Context 后才交权）。
3. 多 worker 启动闸门（配置为多 worker 时禁用/拒绝通话能力）。
4. 普通意外断线仍保留 60s 与重连（回归锁定）。

验证（integration/stage）：意图消费、竞态、其他设备拒绝、超时、两个 Context 不同时存在、普通断线回归。

### CL-6 CallStage

骨架状态：`CallLifecycle` 仅验证纯生命周期状态迁移，不是 CallStage；不存在 PCM、播放结算、沉默、打断或恢复编排。

1. 状态机 PREPARING→RINGING→ACTIVE→RECONNECTING→ENDING/DECLINED/FAILED。
2. PCM 顺序/背压/去重；`audio.stream_started` 先登记待播放项；播放完成按 `(response_id, stream_id)` 幂等结算。
3. 沉默时钟：5s、重复完成不重置、RECONNECTING 暂停。
4. 打断：`playback.stop`（范围校验）+ 200ms 停发 + tombstone + `UserInterrupted` 事实。
5. 3s 恢复：快照、缓冲重放（30s/4MiB/回复、不淘汰最旧未确认）、计时口径。
6. 终态快照冻结；与 Agent 的刺激接口（CallStarted/CallTurnCompleted/CallSilenceElapsed/CallEnding）。

验证：stage 集成测试按 spec AC-19 清单逐条。

验证：unit/agent：决策、降级、池行为、开场、结束。

## 七、风险与注意

1. App 实时音频链路（Spike-B）是全计划最大不确定性；不通过会影响 CL-12 排期。
2. 认知维护迁移触及现有聊天行为——先锁定、后迁移。
3. 二进制帧/入站帧上限、统一 seq 与取消语义尚未实现；Proposed ADR 不可当作冻结协议。
4. 切换链路影响聊天体验：`SWITCH_TO_CALL` 只允许经准备信号的绑定客户端触发；普通断线行为不变（需回归）。
5. 单 worker 只是事实约定——启动闸门不做会悄悄坏。
6. 内存态扩展（重放缓冲、幂等表、租约）在通话规模下的上限与清理策略要显式。
7. 供应商选型与降级口径（Spike-A）；成本与用量观测纳入 AC-18。
8. 隐私约束（临时转录/记忆池只存内存、日志无内容）要测试化，不靠自觉。
9. 通话历史投影、结构化字段和各端渲染仍未实现或验证；ledger 白名单不等于历史兼容。
10. `call_sessions` 建表与数据库迁移说明同步更新。
