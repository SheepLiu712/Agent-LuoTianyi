# 通话问题 #334 实施证据

## 范围与语义

- Issue：#334；目标分支：`feat/call`；实现基线：`653ed507a6afdd41b4d214f001f22723e14bd6e3`
- `call.active.connected_at_ms` 由服务端 `stage_binding.py` 的 `connected.timestamp() * 1000` 产生，语义为 UTC 墙钟 epoch 毫秒，不是客户端单调时钟
- transport 保留该服务端锚点，并在收到 `call.active` 的瞬间以本地墙钟估计已过时长，转换为本地单调锚点；之后时长只使用本地单调时钟计算
- 同一锚点的重复 `call.active` 不重置时长或重复启动采集；恢复握手只恢复状态，不改写锚点。结束和未恢复的三秒断线仍沿用既有冻结策略
- 协议没有 `server_now` 或往返校准字段，因此无法区分单程网络延迟与客户端/服务端墙钟偏差。未来服务端时间戳按零已过时长处理；结构校验仍拒绝缺失、非整数、负数或超出安全整数的字段

当前新增具名测试 `call clock production composition › runs FakeSocket → transport → CallSession → useCallSession/reducer → CallScreen on one default clock`，真实调用链为：FakeSocket → `CallTransportSession` → `CallSession` → `useCallSession` → `reduceCallState` → `CallScreen`。仅 socket/native 是 fake 端口；没有手工调用 UI listener 或伪造 transport snapshot。

输入：server epoch `1700000000000`、receipt wall `1700000001000`、receipt monotonic `10000`；derived anchor `9000`；tick monotonic `10500`，期望 duration `1500 ms`，UI `00:01`。测试还验证 transport lost 冻结 `1500 ms`、resume 保留 `9000` anchor，以及 hangup 后 UI 返回 idle、transport 进入终止路径。共享默认 clock 由 mock 的 `performance.now` 提供 `10000/10500`，同时 mock `Date.now` 为 epoch 数量级，证明默认 hook/Screen 没有绕过共享实现。
