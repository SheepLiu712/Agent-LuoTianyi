# 开发守则

本文档规定项目开发时必须遵守的架构和流程。我们的目标不是增加文档工作量，而是让人和 AI 在写代码前先对“要做什么、代码放在哪里、怎样证明它正确”达成一致。

本项目采用 **spec（行为约定）先行 + 测试驱动开发（TDD）**：先确定需求、模块归属和公开 interface（其他模块可以使用的调用方式），再通过失败测试逐步实现。架构的详细现状以[项目架构](../项目说明/项目架构与接口（spec）/项目架构.md)为准；本守则只规定开发时必须遵守的规则，不要求为了目录名称立即搬迁现有代码。

## Server 模块设计原则

### 1. 核心架构

我们的核心设计理念是：以角色心智为中心，不断扩展外部刺激源和角色与外部世界的交互方式。

目前主要交互是聊天，未来还会有电话、具身实体和游戏世界。无论刺激来自哪里，都应先转换为项目内部能够理解的对象，再交给交互流程和角色处理。新的交互方式不应把具体协议、硬件 SDK 或供应商事件直接写进角色心智。

项目使用以下模块。这里的模块表示一组明确职责，不一定要求每个模块立刻对应一个新的顶层目录。

| 模块 | 通俗解释 | 当前主要位置 |
| --- | --- | --- |
| `domain` | 项目的共同语言，例如刺激、角色、回复、记忆和动作等对象 | `server/src/domain` |
| `agent` | 角色的表意识，决定角色怎样思考、回应和行动，并向外提供少量公开调用方式 | `server/src/agent` |
| `subconscious` | 角色的潜意识，负责记忆、学习、画像、知识、注意力和情绪等 | `server/src/subconscious` |
| `capabilities` | 角色可以使用的能力，例如语音合成、唱歌、图像理解和动作执行 | `server/src/capabilities` |
| `agent_runtime` | 角色工厂和注册处，根据角色 ID 创建、缓存并返回对应的 Agent | `server/src/agent_runtime` |
| `stage` | 管理一次持续交互的流程和状态，例如一个聊天流中的排队、打断、重连、超时和结束等流程 | 当前由 `server/src/chat_session` 承担，暂不要求改名 |
| Adapter（适配器） | 翻译外部协议和内部对象，例如把 WebSocket、电话或机器人事件转换成 `Stimulus` | 当前分布在 `system/user_interface` 和兼容 Adapter 中，暂不要求新建顶层目录 |
| `world` | 角色生活的箱庭世界、世界时钟、外部事件和周期任务 | `server/src/world` |
| `system` | 系统运行和基础设施，包括顶层组装、数据库、用户接口、管理员工具和观测 | `server/src/system` |
| `utils` | 不理解角色、记忆、会话等业务含义的通用工具 | `server/src/utils` |
| `legacy` | 迁移期间保留的兼容实现；新功能不得默认写入这里 | `server/src/legacy` |

暂时不创建用于支撑架构运行的`base` 模块。数据库、LLM、网络等现有代码先留在当前目录；只有出现真实的替换需求时，才为具体依赖设计范围很小的 interface 和 Adapter，不能先建立一个什么都能放的公共目录。

### 2. 调用关系原则

新的交互链路原则上遵循：

```text
外部事件
  -> Adapter：把外部格式转换成内部对象
  -> stage：管理这次交互的状态和流程
  -> agent_runtime.get_agent(character_id)
  -> Agent 的公开 interface
  -> agent 内部调用 subconscious 和 capabilities
```

例如，电话供应商发来“用户开始说话”事件时：

1. 电话 Adapter 把供应商事件转换成项目内部事件；
2. `CallStream` 处理打断、播放停止和通话状态；
3. 需要角色思考时，通过 `agent_runtime.get_agent(character_id)` 取得 Agent；
4. stage 只能调用 Agent 公开的有限 interface，不能直接操作角色的记忆对象、提示词、LLM 模块或能力管理器。

必须遵守以下依赖规则：

1. `SystemRuntime` 是顶层组装位置，负责创建模块、注入依赖和关闭资源；具体业务逻辑不能写进 `server_main.py` 或 `SystemRuntime`。
2. `domain` 可以被其他模块使用，但不依赖具体业务模块、数据库、FastAPI 或外部供应商。
3. Adapter 只负责校验和转换外部格式，不负责角色思考和长期业务状态。
4. `stage` 负责交互流程，不理解供应商的原生协议，也不直接访问 Agent 内部实现。
5. `world` 如果只是产生一次刺激，应通过内部对象唤起角色；如果需要维护一段持续交互，再交给 stage 管理。
6. `utils` 不应依赖 `system/user_interface`，也不应出现“角色记忆”“通话状态”等业务规则。
7. 新代码优先由创建者明确传入所需依赖，不得新增“从任意位置全局取服务”的函数（service locator）。现有全局入口按功能改造逐步移除，不要求一次性重写。

#### 2.1 Agent 的有限 interface

`agent`、`subconscious` 和 `capabilities` 保持为不同目录，但对外把 Agent 当成一个深模块使用。外部模块不需要知道一次回复内部经过了记忆检索、提示词组装、LLM 调用、解析还是能力执行。

推荐的调用形态是：

```python
agent = agent_runtime.get_agent(character_id)
result = await agent.handle_stimulus(stimulus, interaction_context)
```

如果一个agent绑定在一个stage上了，例如聊天流有固定的agent，则也可以是：
```python
# stage 内部代码
agent = self.agent  # stage 在初始化时通过 agent_runtime.get_agent() 取得 agent
result = await agent.handle_stimulus(stimulus, interaction_context)
```
上面的名称用于说明设计方向，最终参数和返回值由对应模块 spec 确定。关键规则是：

- `AgentRuntime` 主要负责角色的创建、注册、缓存、查找和生命周期，不继续增加对话、记忆等业务方法；
- `get_agent(character_id)` 返回一个只暴露少量公开 interface 的 Agent 门面；
- 可以在现有 `LuoTianyiAgent` 外再封一层门面，第一版只做委托，不要求立即重写内部实现；
- stage、world 和用户接口不得绕过门面直接取得 `CharacterSubconscious`、`CapabilityManager`、数据库或提示词对象；
- 只有出现第二个真实调用场景时才增加新的公开方法，不能为了“以后可能有用”提前暴露内部能力。

当前 `AgentRuntime` 和聊天管线中已经存在的额外方法属于渐进治理对象。新功能不得继续扩大这些 interface；旧调用在相关功能修改时逐步迁移，不为了本守则进行一次性大重构。

### 3 深模块原则

深模块就是：外部只需要学习少量、稳定的 interface，复杂工作都留在模块内部。

不推荐的做法：`ChatStream` 自己依次调用预处理、记忆检索、提示词组装、LLM、回复解析和角色能力。这样每增加一种交互方式，都要重新复制整条链路。

推荐的做法：stage 把内部刺激交给 Agent 的一个公开 interface，由 Agent 在内部完成上述工作并返回结果。这样电话、聊天和游戏不需要理解角色心智的内部结构。

设计 interface 时只问三个问题：

1. 调用者真正需要完成什么事情？
2. 能否减少调用方法和参数？
3. 哪些复杂规则可以藏在模块内部？

外部依赖也不需要全部提前抽象。只有确实需要两个 Adapter 时才建立 seam（能够替换实现而不用修改调用者的位置），例如生产环境使用 Qwen Adapter、测试使用 Fake Adapter（假实现）。只有一个固定实现且测试可以直接运行时，不要增加纯转发层。

### 4. 子模块设计模板

每个模块都需要写设计文档。设计文档内，对子模块和模块提供的功能都需要进行详细描述。

撰写模块设计文档时，要求思考下面五个问题。

#### 1. 这个模块要解决什么问题？

说明用户或系统遇到了什么情况，以及这次明确不做什么。

例：实现语音电话中的实时交互；本次不支持多人通话，也不支持视频。

#### 2. 代码放在哪里？为什么？

说明由哪个模块负责，并写一句理由。如果涉及多个模块，分别说明各自只负责哪一段。

例：`CallStream` 放在 stage，因为它管理通话状态；Qwen 协议转换放在 Adapter，因为它只负责翻译供应商事件；角色回复仍由 Agent 完成。

#### 3. 其他代码怎样使用它？

写出最重要的调用方式、输入和返回结果。可以使用简短伪代码，不需要先写完整类图。

例：`start_call(user_id, character_id)` 成功时返回 `call_id`，并在并发已满时返回明确的拒绝结果。

#### 4. 调用后会发生什么？失败时怎么办？

只写与本功能有关的变化，例如是否写数据库、调用外部模型、改变角色或世界状态，以及超时、重复调用、断线时的结果。

例：用户在接通前挂断，系统记录一次未接通电话但不写入角色记忆；Qwen 超时则结束通话并返回可识别的退出原因。

#### 5. 怎样证明它做对了？

列出几个可以实际执行的场景，每个场景之后都应有测试或人工验收记录。

例：第 6 路并发电话被拒绝；用户说话时正在播放的回复在 1 秒内停止；5 秒内重连仍回到原通话。

对于普通小功能，回答完这五项即可。撰写的设计文档应该包括：
- 模块名称；
- 模块的职责和边界；
- 提供的公开接口；
  - 接口的输入和输出
  - 接口的副作用，例如写数据库、输出、发送网络请求；
  - 接口的正常行为；
  - 接口的异常行为，例如超时、重复调用、断线等；
- 主要的调用场景，调用流程；



涉及并发、持续状态、数据库事务、隐私数据或外部供应商时，需要回答：

- 同一请求重复、取消或中断会怎样？
- 依赖超时或不可用会怎样？
- 是否有数据安全、资源上限或性能要求？

如果文档是由AI撰写的，需要在撰写完成后，要求AI使用者回答类似于以下的问题：

> 用户发起电话后立刻挂断、外部模型超时、网络断开后重新连接，系统分别应该发生什么？应该从哪个公开 interface 写测试？

如果使用者能够基于文档直接回答，就已经足够；如果必须阅读内部代码才能猜出结果，就需要补充。

### 5. spec 与架构同步

所有暴露给其他模块的 interface 都必须有 spec。spec 可以写在模块设计文档中，不要求重复建立多份文档。

如果开发引入新模块、改变模块职责、改变依赖方向或废弃旧路径，必须同时更新[项目架构](../项目说明/项目架构与接口（spec）/项目架构.md)。不确定的方案应放在设计讨论或架构决策记录（ADR）中，不能以“可能合并”“暂时不确定”的形式写成强制守则。

## tests 目录管理

测试目录采用“**模块归属优先，跨模块流程单独存放，运行环境用标记区分**”的混合方式。

只按 `unit/integration/e2e` 分目录，会让同一模块的测试散落在多处；完全照抄 `src` 的文件树，又会让测试依赖内部文件怎样拆分。按顶层模块组织可以明确责任和对应 spec，同时保留 `integration`、`e2e` 等目录处理真正跨模块的行为。

### 1. 各子项目分别管理测试

- Server 测试放在 `server/tests`，按照本守则定义的 Server 顶层模块归属。
- 桌面客户端测试放在 `client/tests`，按照客户端自己的顶层模块或用户流程归属。
- App 测试保留在 `app/__tests__`，按照 App 自己的顶层模块或用户流程归属。
- 不把三个子项目的普通测试全部移动到仓库根目录。跨项目协议以接口 spec 为共同约定，各项目分别从自己的公开 interface 验证；只有出现确实能被多种语言共同读取的 schema 或样例数据时，才建立共享的 contract fixtures（契约样例），不提前创建空目录。

### 2. Server 推荐目录

目录只在出现真实测试时创建，不要求先建立一批空目录。

```text
server/tests/
  domain/
  agent/
  subconscious/
  capabilities/
  agent_runtime/
  stage/
  adapter/
  world/
  system/
  utils/
  legacy/
  integration/
    chat/
    account/
    lifecycle/
  e2e/
  support/
  conftest.py
```

各目录的含义：

- 顶层模块目录：通过该模块的公开 interface 验证它承诺的行为。可以使用外部依赖的 Fake Adapter，但不 mock 本项目内部的实现步骤。
- 顶层模块目录测试较多时，可以继续按照公开能力分组，例如 `capabilities/speech/`、`capabilities/singing/`、`system/database/`，但不要照着私有类和源文件逐层复制目录。
- `integration/<流程>`：必须同时连接两个或更多顶层模块才能观察的行为，按照聊天、账户、生命周期等业务流程分组，不按某个内部类命名。
- `e2e/<流程>`：必须从 HTTP、WebSocket 或真实客户端入口走完整系统链路才能验证的少量核心场景。e2e 不重复模块测试已经充分覆盖的所有边界组合。
- `support/`：可复用的 Fake Adapter、对象工厂和测试数据构造器。这里不能放以 `test_` 开头的测试，也不能演变成另一套业务实现。
- 根 `conftest.py`：只放整个 Server 测试集共同需要的 pytest 配置和 fixture。只服务某个模块的 fixture 放在对应模块目录的 `conftest.py`；不要从测试代码直接 import `conftest.py`。

例如：

- ChatStream 的重连行为属于 `stage/test_chat_stream_reconnect.py`；
- WebSocket 消息幂等属于 `adapter/test_websocket_idempotency.py`；
- SystemRuntime 启动失败回滚属于 `system/test_runtime_initialization_rollback.py`；
- 从 Adapter 接收消息、经过 stage 和 Agent、最终发出响应的行为属于 `integration/chat/`；
- world 单个任务的行为属于 `world/`，world 与 Agent、stage 联动的完整流程属于 `integration/`。

### 3. 放置测试的判断顺序

写测试前先在 spec 中确认要观察的公开 interface，然后依次判断：

1. 只通过一个顶层模块的公开 interface 就能证明行为：放入该模块目录。
2. 必须使用两个或更多顶层模块的真实连接才能证明行为：放入 `integration/<流程>`。
3. 必须经过外部协议入口和完整运行时才能证明行为：放入 `e2e/<流程>`。
4. 文件本身不是测试，只是多个测试共用的 Fake、工厂或数据：放入 `support/`，或者只在单个模块使用时放在该模块目录下。

测试放在哪里由“从哪个 interface 观察结果”决定，不由本次修改了哪个私有文件决定。一个 Bug 如果在 stage 的公开 interface 上表现出来，即使根因在内部 helper，回归测试仍放在 `stage/`，不为 helper 建立对应目录。

### 4. 命名和测试内容

- 测试文件按可观察能力命名，例如 `test_chat_stream_reconnect.py`，不按私有方法命名。
- 同一个测试根目录下的测试文件名应保持全局唯一，避免 pytest 默认导入方式把不同目录中的同名文件当成同一个模块。若要切换为 `--import-mode=importlib`，应单独修改配置并运行完整收集和回归测试。
- 测试函数名描述前提和结果，例如 `test_reconnect_within_grace_period_keeps_original_stream`。
- 一个测试只证明一个主要行为；同一场景需要多个断言时，这些断言应共同证明一个结果，而不是无关结果的集合。
- 期望值来自 spec、固定样例或人工算出的明确结果，不能在测试中复写一遍实现算法再与实现比较。
- 不测试私有方法、内部调用次数和内部对象怎样协作。只在外部系统 seam 使用 Mock/Fake，例如模型供应商、网络、时间、文件系统和必要时的数据库；项目自己的模块优先使用真实实现连接。
- 数据库测试优先使用隔离的临时数据库或事务，不连接生产数据库。测试结束后必须释放数据库、任务、端口、临时文件和模型资源。

### 5. 目录不表示运行环境

目录表示模块归属或业务流程；是否需要真实 LLM、TTS、GPU、外部网络或较长运行时间，应由 pytest/Jest 标记和测试命令区分，不能靠文件放在哪个目录猜测。

- 默认测试必须可重复、可离线运行，并且不得使用生产密钥和生产数据。
- 真实 LLM、真实 TTS、GPU、外部网络和慢测试必须使用明确标记，并默认跳过或在专用 CI/人工验收环境运行。
- 已有 `real_llm` 标记继续保留；新增标记时必须同时在 pytest/Jest 配置中注册并写明启用命令，不能只在文件名中写 `real` 或 `slow`。
- `integration` 不等于“必须访问真实外部服务”。集成测试应尽量连接本项目真实模块，并在最外层供应商 seam 使用 Fake Adapter。

常用的 Server 测试范围示例：

```powershell
# 一个模块
python -m pytest tests/stage -q

# 一条跨模块流程
python -m pytest tests/integration/chat -q

# 仅当外部/长耗时测试已全部正确标记或由 conftest 默认跳过时，才运行默认 Server 回归
python -m pytest tests -q -m "not slow and not live and not external and not real_llm"
```

若当前分支仍有未标记的真实外部测试，上述命令不构成安全的默认回归命令；必须先按“2.2 审核测试范围”使用精确 node ID 排除已知外部节点，并继续运行同文件内使用 Fake 的快速测试。

### 6. 旧测试迁移

- 新测试必须按上述规则放置。
- 当前平铺在测试根目录的旧文件不要求为了整理目录一次性全部搬迁。修改相关功能时再把对应测试移入正确目录，或者单独提交一次只改变路径、不改变行为的机械迁移。
- 移动测试时必须同步更新 CI、脚本、文档和按文件运行的命令，并先后运行移动前后的同一测试集，确认收集数量和结果一致。
- 不为追求目录整齐复制测试。新目录中的接口测试覆盖旧测试行为后，应删除被替代的实现细节测试和重复测试。
- 每次迁移后应运行 `pytest --collect-only` 或 Jest 的测试列表命令，确认没有因为目录、包名或配置变化漏收测试。

## 开发流程

AI 执行功能、Bug 修复或重构任务时，必须先读取并遵守 [Spec、TDD 与小 PR 门禁 Skill](skills/spec-tdd-pr-guard/SKILL.md)。缺少需求、interface 设计或对应测试时，只补最早缺失步骤并提交该步骤的 PR，不得继续实现后续阶段。

所有开发遵循“小提交，勤合并”原则。功能分支是最终集成位置，每位开发者或 AI 从功能分支再拉出小分支，不直接把大量代码推到同一个共享分支。默认由一个根 PR 直接合回功能分支；需要先独立评审 Red 测试门禁或其他前置切片时，可以使用下文规定的堆叠 PR，但整条堆叠链最终仍只能由根 PR 合回该功能分支。

### 1. 大版本和新功能

1. **提出需求**：开发群决定是否开发该功能，并指定负责人。
2. **建立功能分支**：从 `dev` 拉出 `feat/xxx`，作为该功能的集成分支。
3. **明确需求**：从 `feat/xxx` 拉出文档分支，编写 PRD，至少说明功能、用户使用路径、功能清单、页面行为和必要的埋点。
4. **审核需求**：文档分支向 `feat/xxx` 提交 PR；至少两人审核并签署承诺书后合并。
5. **设计模块**：从最新的 `feat/xxx` 拉出新的文档分支，按照上面的五个问题编写模块设计。
6. **审核模块设计和测试入口**：至少两人确认模块归属、公开 interface，以及测试从哪个 interface 观察行为；签署承诺书后合并。
7. **列出测试场景**：记录正常、失败和关键边界场景，但不要一次把全部测试和实现分成两个大批次。
8. **按 TDD 小步实现**：每次只完成一个可观察行为：
   1. 先写一个测试并运行，确认它因为功能尚未实现而失败，而不是因为语法、环境或测试本身错误；
   2. 只写足够让该测试通过的实现；
   3. 运行相关测试，确认新测试和已有测试通过；
   4. 提交这个小切片，再开始下一个测试场景；
   5. 一个行为切片完成后再集中检查重复代码、命名和结构，并在测试保护下整理。
9. **提交实现 PR**：开发者从 `feat/xxx` 拉出 `test/xxx`、`impl/xxx-part-n` 等小分支，向 `feat/xxx` 提交 PR。PR 必须说明：
   - 对应 spec 中的哪个行为；
   - 先失败的测试及失败原因；
   - 实现后运行了哪些测试以及结果；
   - 是否存在未验证的真机、外部服务或生产环境风险。
10. **最终验收**：全部场景通过后，删除已被替代的旧路径，提交 `feat/xxx` 合并到 `dev` 的 PR；至少两人审核并签署承诺书。
11. **发布**：`dev` 达到阶段目标后，提交合并到 `main` 的 PR；至少两人审核并签署承诺书，然后发布。

TDD 测试应通过已经确认的公开 interface 验证可观察结果，不测试私有方法，也不因为内部重构而失败。数据库、第三方模型等外部依赖可以使用本地实现或 Fake Adapter（假实现），但 Fake 必须遵守与生产 Adapter 相同的调用约定。

#### 开发进度文档

每个功能使用一个文件：

```text
docs/开发进程文档/开发进度/<版本号或功能短名>.md
```

尽量与 PRD 使用相同的功能名。目录或文件不存在时创建。每次需求、设计、测试或实现 PR 都必须在提交前更新该文件，至少包含：

```markdown
# 功能名称

- PRD：
- interface spec：
- 当前阶段：需求 / interface / 测试 / 实现 / 验收
- 总体状态：未开始 / 进行中 / 阻塞 / 已完成
- 最后更新：YYYY-MM-DD

## 本 PR

- 目标：
- 范围：
- 明确不包含：
- 验证及结果：

## 已完成

## 阻塞和未验证项

## 下一 PR
```

只记录已经发生的事实。没有运行的测试不能写“通过”，Draft PR 不能写“已合并”，本地验证不能写成真实外部服务或真机已验收。PR 编号未知时记录分支或写“待创建”，不得编造编号。

没有更新对应进度文档，不得宣告完成或提交本次 PR。

### 2. PR 大小和审核

- 一个 PR 只解决一个能够独立说明和验证的问题。
- 普通手写代码建议不超过 500 行；超过时必须解释为什么不能继续拆分。生成文件、锁文件、资源和测试快照单独统计，不能为了行数拆坏一个完整行为。
- 审核者必须对照 spec、测试场景和实际 diff，不能只阅读 AI 总结或只看测试显示绿色。
- PR 不得同时夹带无关重构。需要重构时，优先单独提交，并说明哪些行为保持不变。
- 发现旧实现已被替代时应明确删除；不能长期保留没有调用者的兼容路径和两套同功能实现。

#### 2.1 根 PR 与堆叠 PR

根 PR 是整条交付链最终合入功能分支的 PR，其 base 必须是该功能规定的集成分支。堆叠子 PR 是以上一层开放 PR 的 head 分支为 base、只评审相对父 PR 增量的 PR。堆叠只改变评审和合并拓扑，不改变需求、interface、TDD、小 PR 或最终目标分支。

只有同时满足以下条件才允许使用堆叠 PR：

- 子 PR 依赖一个尚未合入、但已获批准可以继续的前置门禁或行为切片；
- 子 PR 的 base 恰好是同仓库父 PR 的 head 分支，父 PR 链能够明确追溯到规定的功能集成分支；
- 子 PR 与父 PR 标明共同的功能、对应 Issue、根 PR 和合并顺序，不把无关工作借堆叠关系带入；
- 子 PR 只合入父 PR 分支，不直接合入 `dev`、`main`、`master` 或其他旁路分支。

审核与合并必须按以下顺序执行：

1. 子 PR 以直接父 PR 为 fixed point，只审核和测试本层新增的增量；根 PR 以功能集成分支为 fixed point，审核整条交付链的完整 diff。
2. 子 PR 通过后可以 squash merge 到父 PR 分支；该步骤不表示功能已经进入集成分支。
3. 父 PR 接收子 PR 后 head 已改变，旧批准和旧测试证据不得作为最终合并依据。作者必须更新标题、正文、阶段和开发进度，重新运行完整候选所需的验证并重新请求审核。
4. 只有根 PR 的完整候选为 Green、所有门禁通过且 base 仍为规定功能分支时，才能 squash merge 根 PR。

PR 的 Draft/Ready 状态原则上由作者维护：未完成、自知仍有门禁或仅用于保存 Red 证据时保持 Draft；认为当前层已可审核时转 Ready。审核者负责 `Approve`、`Request changes` 和是否合并，不因 PR 转 Ready 就推定其已经通过。

#### 2.2 审核测试范围

审核实现 PR 时优先运行对应 Issue 的 focused tests、受影响模块的离线回归和必要静态检查。不得为了“全量”而默认启动真实学歌流水线、B 站实时抓取、真实 LLM/TTS/GPU/设备或其他长耗时外部过程；标记为 `slow`、`live`、`external`、`real_llm` 的测试默认跳过。尚未正确标记的已知外部测试应使用精确 node ID 排除，不能因此跳过同文件内使用 Fake 的快速单元测试。

所有跳过项必须逐项记录为“未验证”，不能写成通过。只有对应 Issue、最终验收或人工验收明确要求真实依赖时，才在具备隔离配置和凭据的专用环境运行这些测试。

### 3. Bug 修复

1. **确认 Bug**：记录复现步骤、期望结果和实际结果，并判断是否需要热修复。
2. **选择分支**：
   - 需要热修复：从 `main` 拉出 `hotfix/xxx`；
   - 不需要热修复：从 `dev` 拉出 `bugfix/xxx`。
3. **先复现再修复**：先增加一个能够稳定复现 Bug 的失败测试，并确认失败原因就是该 Bug。
4. **最小修复**：只修改与 Bug 有关的实现，使复现测试通过，并运行受影响模块的回归测试。
5. **审核合并**：PR 说明复现方式、根因、修复点、失败测试和最终结果。
6. **同步其他分支**：
   - 热修复合入 `main` 后，同步到仍包含该 Bug 的 `dev` 和活跃 `feat/xxx`；
   - 普通修复合入 `dev` 后，同步到仍包含该 Bug 的活跃 `feat/xxx`。

如果某个 Bug 无法通过自动测试复现，PR 必须说明原因，并给出可重复的人工、真机或外部服务验证步骤，不能只写“已测试”。

### 4. 环境管理

生产环境和开发环境必须使用不同配置、不同密钥和不同数据库，不能互相连接。

- **生产环境**：使用 `main` 分支，部署给用户使用，不提供开发调试接口。
- **开发环境**：使用 `dev` 分支，供开发者调试和验收，可以启用经过控制的调试能力。
- **生产数据库**：应用程序可以执行业务正常运行所必需的读写；开发者不得直接手工修改。数据修复和迁移必须使用经过审核的脚本，执行前备份，并保留执行和验证记录。
- **开发数据库**：与生产数据库完全隔离，开发者可以按开发需要读写和重建，但不得复制不必要的生产敏感数据。

开发环境通过不代表生产发布已经验证。涉及真机、GPU、外部模型、签名包、网络隧道或真实硬件的功能，必须明确记录哪些只做了本地测试，哪些已经完成真实环境验收。

### 5. 代码规范

目前AI的代码风格其实还可以，但需要注意以下几点：
- 变量命名应清晰表达含义，避免使用模糊或过于简短的名称；
- 函数和方法应尽量保持单一职责，避免过长或过复杂的函数；
- 对于重要接口应该写明注释，包括参数、返回值和异常情况；
- 避免过长的文件和类，超过500行的文件应考虑拆分。
