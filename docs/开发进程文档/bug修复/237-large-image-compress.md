## 背景
#230 路线 A（PR #236）已实现「发送前预检 + 超限明确提示」作为兜底；仓库主建议客户端再做一次压缩，使超限图片多数可正常发送。

## 目标行为
- 原图未超限：不压缩，直接发送（避免无谓重编码）；
- 超限：压缩后发送（目标产物 ≤5–5.5 MiB 安全余量）；
- 压缩后仍超限或压缩失败：回落「图片过大」明确提示（依赖 #236 合入）。

## 方案要点（据 #230 评估）
- 新增 `expo-image-manipulator`（`npx expo install` 选定匹配版本）；
- 策略：超限才压缩；按「最大边 ≤2560、JPEG 质量 0.8」→「最大边 ≤2048、JPEG 质量 0.6」两档处理；PNG 仅降尺寸并保持 PNG；产物达到 ≤5.5 MiB 即发送；
- 产物 URI / MIME 同步更新；实现位点 `app/utils/network_client.ts` 的 `sendImage`（避开 #229 改动面）；失败可见化沿用 #236 的 `message_processor` 分支；
- 参数以真机实测为准。

## 改动范围
`app/utils/network_client.ts`（+ 压缩工具模块）、`app/package.json`、测试；文档。

## 验收标准（拟）
- 3 / 5 / 7 / 20+ MiB 样本：超限图片压缩后成功发送；不可压缩者得到明确提示；
- 未超限不产生无谓重编码；`tsc` / jest 通过；真机实测记录参数。

## 验证计划
- 单测（mock 压缩器）：超限→压缩→发送；压缩后仍超限→提示；压缩异常→提示；未超限→直发；
- 真机：样本矩阵（照片/截图/透明 PNG）+ 时延与峰值内存观察。

## 依赖与前置
- #236（路线 A）建议先合入（提示兜底）；
- expo-image-manipulator 新增依赖需重构建真机包。
