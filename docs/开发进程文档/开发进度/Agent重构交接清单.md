## ① ChatStream 的输入行为与迁移不变量

旧链路源码已在 #88 删除；本节是删除前行为归档，当前实现以 Stage、handler 与 skill 为准。

| 输入或场景 | 当前旧链路行为 | 交接验收项 |
|---|---|---|
| 文本 | 提取歌曲实体等线索；保存用户消息；加入未读集合；重置普通等待，默认 1 秒 | 预处理和落库完成后才允许进入正式回复；预处理不等于消费 |
| 图片 | 保存图片文件，经 VLM 生成描述，再提取线索、保存对话、加入未读集合 | 保留媒体身份和理解文本；慢图片不能被后来的快文本越过，导致回复材料乱序 |
| 连续多条内容 | 同一聊天流中已预处理、已落库且尚未结算的文本和图片进入未读集合；处理循环在期限到达或已取消等待时取出当时全部未读作为一次提取快照。具体消费规则见下节 | 新链路等待全部内容准备完成，再固定有序批次；按回复报告 consumed ID 消费，不因预处理完成或一次调用结束而清空全部 pending |
| 正在打字，长度大于 0 | 有未读或正在提取时，等待延长为 10 秒 | 无待回复内容时不凭空产生回复；不能绕过内容尚未准备完成的条件 |
| 清空输入，长度为 0 | 撤销期限并唤醒处理循环；循环空闲且有未读时，不再等待 1／10／60 秒，下一次调度直接开始提取，force_complete=False；正在提取时不会启动第二次提取 | 新链路全部内容就绪且无在途回复时，安排零延迟的期限回调启动回复；仍有预处理则等其完成，不再追加普通等待；无 pending 不创建回复。开始处理不等于立刻产出回复 |
| 打开图片选择 | 有未读或正在提取时，等待延长为 **60 秒** | 保留选图等待语义；代码注释中的“30 秒”不是实际值 |
| 取消图片选择 | 有未读时恢复普通等待；否则清除期限 | 不产生正文，不消费消息 |
| 等待超时 | 固定未读快照，以 `force_complete=True` 提取话题，再进入注意力选择和回复生成 | 超时触发完整批次处理；旧期限失效后不能再启动重复回复 |
| 触摸快速分支 | 优先尝试预制音频；无文字、不进入聊天展示、标记临时消息；成功后绕过普通话题处理 | 用瞬时投递表达；不生成聊天记录；按触发读取音频 |
| 触摸降级分支 | 快速资源不可用或未命中时，直接生成触摸话题，绕过普通聚合等待；排队中的触摸会合并，处理中的新触摸会忽略 | 不保留降级链；快速资源缺失、读取失败或未命中时，报告失败、记录错误并丢弃本次触摸，不转普通话题或调用 LLM 兜底。旧降级分支的合并／忽略规则不作为迁移要求 |
| 首次登录 | 延迟约 1 秒，保存欢迎语并按配置顺序发送预制文字、音频和表情 | 与历史消息加载协调；欢迎语属于正常对话投递 |
| 当日首次普通登录 | 检查到期事件，过滤用户和角色，领取通知标记后派发提醒 | 登录提醒与周期提醒共享已通知事实，不能重复提醒 |
| 长时间未登录后回来 | 当前 `RETURN_LOGIN` 自动派发被明确关闭 | 不因迁移时看到枚举或旧代码而重新启用 |
| 系统事件 | 枚举存在；进入 planner 时没有独立认知分支，会按一般未读转换 | 必须逐个核实实际生产者，不能将任意系统事件直接当用户正文 |
| 语音 | 当前 ChatInputEvent 没有独立语音输入分支 | 新领域已有 `VoiceMessage`，不代表旧链路已有完整语音行为 |
| 断线与重连 | 旧流标记连接丢失，保留期内重新绑定；旧连接的迟到断线不能拆掉新连接 | 保留连接身份检查、重连复用与最终回收；具体取消策略见下文 |

### 聚合、提取与消费的具体时序

**旧 ChatStream 的事实：**

1. 聚合范围是同一聊天流内已完成预处理及落库、尚未结算的文本和图片。typing、选图信号不进入正文集合；触摸绕过普通集合。若 SYSTEM_EVENT 被送入 planner，它当前也会按一般未读转换，必须另行核实生产者。
2. 每条内容到达 planner 后追加到集合末尾，并把普通期限设置为此刻加配置等待时长（默认 1 秒）。期限前继续到达的内容一起参与下一次提取；每次追加都会重新计时。旧 ingress 串行，因此还在预处理的图片不在这个集合里，旧 planner 也不会因为它尚未完成而自动阻止提取。
3. 期限到达且有未读时，处理循环取出当时全部未读，形成固定快照并暂时清空等待集合，以 force_complete=True 调用提取器。无期限但有未读时直接提取，force_complete=False。提取期间的新内容进入另一个等待集合，不修改正在使用的快照。
4. 提取器返回一个话题和剩余消息。当前实际规则是：话题来源取模型选中的消息；剩余消息只保留最大选中下标之后的尾部。因此选中下标 0、2 时，下标 1 即使未被选中，也不会留在剩余集合。这是旧实现的消费风险，不能作为新链路按 ID 消费的要求。无有效提取结果，或非强制提取判定内容不完整时，整批保留。
5. 提取返回后再次检查：如果已有新内容或新的等待期限，旧提取结果作废，原快照整批放回新内容之前；否则只把返回的剩余部分放回，其余从未读集合移除，有效话题交给 replier。旧链路在话题交给 replier 前就完成这次未读结算，不等待最终回复或播放。
6. 仍有未读时继续安排普通等待；没有未读时清除期限。例如 A、B 正在提取时 C 到达，旧结果失效后下一批顺序为 A、B、C；若没有新输入且结果有效、仅 B 被保留，则下一批从 B 开始。

**新 ChatStage 的交接要求：**

1. 内容接收时就登记顺序和 PREPROCESSING 状态。每条 handler 完成预处理及落库后返回类型化结果，标记 READY；触摸、打字、选图不进入普通回复批次。
2. 尚有内容预处理时不开始批量回复。全部 READY 后，普通期限从最后一条准备完成时起算；有效期限触发时冻结当前有序批次，用 InteractionDeadline 调用批量回复 handler。
3. 回复期间产生的 ActionPlan 立即投递；有效回复报告返回时，只删除明确列入 consumed_pending_stimulus_ids 的输入及其召回记忆。未消费项继续保留；取消请求的晚报告不参与结算。不能沿用旧提取器“最大选中下标之前全部移除”的做法。
4. 新内容取消在途回复尝试及其计划；原批次尚未消费项保留预处理结果，与新内容按接收顺序重新聚合。已经消费的输入不会因后续音频执行取消而重新加入。

### 清空输入的确定含义

“立即”只表示取消额外等待，不表示同步完成模型调用或客户端立即收到回复。

- 旧链路空闲且有未读：remove_deadline 后唤醒处理循环，在循环下一次运行时提取，不再等待原期限；这次不是超时触发，force_complete=False，因此仍可能判定不完整、保留消息并重新安排普通等待。
- 旧链路正在提取：只移除期限并设置唤醒信号，不取消当前提取，也不并行开启另一次；当前结果返回后按有效性检查结算。
- 新链路全部输入 READY 且没有在途回复：安排零延迟 InteractionDeadline，启动完整回复尝试。
- 新链路还有输入 PREPROCESSING：等待最后一个完成后安排零延迟回调，不再附加 1 秒；若之后又有新内容、打字或选图，则以最新事件更新等待策略。
- 新链路已有回复在进行：清空信号不取消它，也不重复启动；若该回复完成后仍 retained 内容，当前实现重新采用普通等待。没有 pending 时不创建回复。

### 触摸失败与表情恢复的迁移约定

- 快速分支失败或未命中：报告失败并记录错误，结束本次触摸，不进入普通话题、不追加 LLM 回复，不自动重试。
- 成功触摸：handler 先交付包含瞬时 SAY 的计划，再交付独立的恢复表情 ActionPlan。恢复目标为 normal；它不是 SAY 的隐含副作用。
- Stage 按计划顺序执行，先完成触摸 SAY 的投递及消息结束标志，再执行恢复计划；无需等待客户端播放确认，客户端沿用结束包决定播放和后续表情的顺序。
- 当前触摸 handler 仍占位，恢复表情行动的真实处理器也需接入；上述为明确的迁移验收要求，不宣称已实现。

回复及收尾还需要逐项检查：

- [ ] 正式回复使用当前对话、话题检索结果和注意力选择结果；不能用预处理关键词候选直接代替完整检索流程。
- [ ] 展示文本与朗读文本分别保留，不能把 `content` 和 `sound_content` 合并。
- [ ] 旧回复先保存对话，再进入说话队列；新链路必须补齐回复落库职责，不能只验证客户端听到了声音。
- [ ] 唱歌保留歌曲片段选择、最近已唱片段排除、歌词记录和不可用片段处理；目前新行动处理器只实现 SAY。
- [ ] 触摸成功后有独立的恢复表情 ActionPlan；SAY 不默认恢复；触摸失败不再降级到普通回复。
- [ ] 一句话的表情、音频和结束标志保持关联及顺序；相同内容的合法音频块不能被客户端误去重。
- [ ] 开始思考与结束思考仍有对应信号；并行触摸结束不能关闭另一请求的思考提示。
- [ ] reflection 保留日期识别、记忆写入、上下文压缩及画像更新。旧日期识别还可能生成确认话题，迁移时不能遗漏这条用户可见分支。
- [ ] 旧画像更新目前发生在压缩实际发生之后；改变触发条件属于行为变更。

**已经确认的变化，不能误当成旧行为原样复刻：**

| 项目 | 旧链路 | 当前新设计 |
|---|---|---|
| 预处理并行性 | ingress 单 worker 串行，慢图片可能阻塞后续触摸 | 单刺激 handle 并行，Stage 保持回复批次顺序 |
| 新内容打断 | 提取结束时检查新消息或等待信号，丢弃过时提取结果；并非普遍取消完整回复 | 新内容取消完整回复尝试及关联排队、执行计划 |
| 打字与选图 | 可以使正在提取的话题结果失效 | 调整等待，不取消正在进行的回复 |
| 表情恢复 | 旧触摸非 normal 表情后追加 normal 包 | 触摸 handler 必须安排后续独立 ActionPlan 将表情恢复为 normal，按序在触摸 SAY 之后执行；SAY 本身不自动恢复，不能省略触摸恢复步骤 |
| reflection 时机 | 旧链路在说话任务入队后提交反思 | 新 Stage 等回复报告和关联计划结束后触发；不等待客户端播放 |
| 断线 | 旧 `lost_connection` 本身主要解除连接 | 新 Stage 取消并等待任务清理，保留已准备且未消费内容 |

## ② World 行为到 WorldStage 的映射

**不是所有 world task 都应该进入 WorldStage。**需要角色判断的事实进入它；抓取、凭据和数据库维护继续留在外部。

下列时间来自当前仓库配置；迁移时应读取生效配置，不能写死。注册入口是 [WorldRuntime](../../../server/src/world/world_runtime.py)，基线测试在 [tests/world](../../../server/tests/world)。

| 当前行为 | 必须保持的结果 | 迁移后的归属与调用 |
|---|---|---|
| Citywalk：每日 04:00，按角色和概率执行 | 环境推进、报告、`travel` 事件、动态及报告回写；动态失败不抹掉已完成散步 | 地图、环境事实留 world；角色路线选择或表达通过 `WorldObservation → WorldStage → handle`；对外发布经 ActionPlan/realize |
| VCPedia 新歌知识：每日 04:00 | 跳过已有歌曲；规范化资料；形成可查询歌曲知识及关键词索引；统计成功失败 | 抓取解析留 world；稳定候选成为 `SongKnowledgeDiscovered`，Agent 决定知识接纳；发现歌曲不自动等于请求学唱 |
| 自动学歌：每日 04:00，按角色 | 凭据检查、wishlist 状态、工件校验、唱歌库刷新；新学会歌曲的通知、事件和动态；already learned 不重复产生这些效果 | 下载、模型处理和工件管理留 world/capability；验证成功才发 `SongLearned`，经 WorldStage 记录角色经验并决定发布 |
| QQ 音乐凭据刷新：每 6 小时，启动立即执行 | 相同凭据文件只处理一次；失败明确报告；影响后续学歌准入 | 基础设施维护，**不进入 WorldStage，不产生认知刺激** |
| B 站官方事件更新：每 6 小时，启动立即执行 | Cookie、抓取、图片/文本解析、EventStore 更新及计数 | 外部事实维护留 world；使用 LLM/VLM 不自动意味着属于 Agent。后续到提醒时再产生提醒刺激 |
| 周期主动提醒：每 300 秒 | 活跃聊天流空闲至少配置阈值，默认 30 秒；过滤个人事件与已通知项；随机选候选；领取失败或入队失败正确处理 | world/clock 唤醒扫描；**ChatStage** 决定当前聊天是否适合提醒，生成 `ProactivePromptDue`；不是强塞进 WorldStage |
| 动态互动：每 600 秒，当前默认角色一份 | 正文和评论分别处理；回复、忽略、失败状态准确；记忆处理独立于回复 LLM 是否可用 | world 提供 `DynamicObserved`；WorldStage 调 handle；评论通过 `ReplyDynamic`/realize，记忆由内部技能处理；按真实结果更新业务状态 |
| 日记：每日 00:00，按角色 | 当前当日至少 50 条对话、当天无日记；最多随机选 20 用户；发布 private dynamic，保持用户隔离和每日唯一性 | world 负责筛选；每用户 `DiaryPlanningDue → WorldStage → handle → WriteDiary → realize` |
| 过期事件清理：每日 00:00 | 仅清理符合条件的过期事件；保留 recurring、用户事件及无年份日期；失效查询缓存 | EventStore 维护，**不进入 WorldStage** |
| 启动节日初始化 | 初始化节日事实 | 启动生命周期任务，不是周期 action，也不调用 Agent |

World 共同验收项：

- [ ] WorldStage 按角色和 world 管理持续交互，不用每次临时 runner 丢失连续状态。
- [ ] WorldClock 只负责时间唤醒；world 的周期任务与 Stage 的交互计时分开。
- [ ] 不把下载进度、凭据刷新、模型中间结果包装成角色刺激。
- [ ] 单任务失败不终止其他任务或后续周期；关闭时等待已拥有工作的清理。
- [ ] 保留业务去重，例如“同一天只发一篇日记”“同一提醒只通知一次”；这与恢复 Agent Ledger 重投机制是两回事。
- [ ] `DailyPlanningDue`、活动生命周期等已有领域类型，不能据此宣称当前已经有对应生产行为。

## ③ 当前模块分工与架构检查

| 模块 | 应负责 | 不应承担／当前迁移状态 |
|---|---|---|
| FastAPI、WebSocketService、WebSocketConnection | 认证、协议校验、连接、心跳、ACK、接入限流与连接发送 | 不做角色认知；网络维护包不进入 adapter 的刺激转换 |
| adapter | 共享实例；连接绑定、事件转刺激、StageOutput 转包、异步投递 | 不管理 pending、回复期限或提示词；主要接口为 `bind/disconnect/receive_event/submit_output` |
| StageManager | 按用户与角色创建、复用和回收 Stage；离线保留期 | 不生成回复或运行 reflection 算法 |
| ChatStage | context 所有权、预处理状态、有序批次、计时、取消、计划队列、长期持有的两个 sink | 不直接调用模型和认知技能；不重复执行 handler 的落库 |
| WorldStage | 角色与 world 的长期交互、世界刺激编排、计划执行与结算 | **尚未实现**；不接管所有 world 基础设施 |
| Agent façade、Handling、Execution、emitter | 两个业务入口、路由、单次契约、计划和输出身份、失败与取消清理 | 不保存跨调用 pending、计时器或 context 注册表；不恢复 Ledger 重投 |
| Stimulus handler | 单条预处理及落库、期限批次的完整回复生成、reflection 具体逻辑 | 聊天三类 handler 当前占位；不能将其“返回成功”视为完整业务完成 |
| Action handler | 执行既定行动，调用技能，组织领域输出 | 当前 SAY 已实现 TTS／预制音频及 Delivery；其他行动仍需迁移 |
| Skills | 可复用的认知与表达能力；类型化输入输出 | 不反向调用 Stage，不拥有交互计时；角色共享，由运行时统一装配 |
| ContextFactory / InteractionContext | 创建上下文；保存画像、对话、召回记忆；提供类型化读写 | Factory 不缓存交互；Stage 持有并关闭；压缩内容由外部技能生成 |
| capabilities / resources | TTS 等技术能力、资源目录与读取、重型处理适配 | 不决定何时回复、消费什么输入 |
| database_service | 查询、存储、事务和数据约束 | 不决定角色反应及回复时机 |
| world / WorldClock | 外部事实、任务状态、环境推进、周期唤醒 | 当前仍存在直调旧角色能力的路径，需逐项迁移 |
| SystemRuntime / AgentRuntime | 顶层依赖和生命周期装配／角色 Agent、handler、skill 装配 | 旧业务代理与动态 locator 已删除，不得重新引入 |

接手者尤其需要守住这几条：

- [ ] 外部认知调用最终经过 Agent 两个入口，不新增 `get_character_runtime(...).conscious` 旁路。
- [ ] handler 可以经 `context` 完成落库，不直接取得整个 SystemRuntime。
- [ ] 同一交互的 context 和待回复状态由 Stage 一起持有、一起结束。
- [ ] 一次 realize 清理完成后才开始下一次；不把网络 Future 完成或客户端播放完成当作这个条件。
- [ ] 只清理实际消费刺激关联的召回记忆，不用全量清空误删并行工作。
- [ ] **并行预处理的数据库写入顺序仍待真实 handler 实现时验证**；当前测试只证明回复材料有序。
- [ ] 交付按完整行为链验收：输入 → 预处理与落库 → 聚合 → 认知 → 行动 → 客户端效果 → reflection／清理，不能只验类型或占位返回值。
