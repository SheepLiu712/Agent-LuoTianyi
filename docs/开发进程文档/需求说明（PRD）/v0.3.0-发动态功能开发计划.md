本文档根据 `docs/PRDs/v0.3.0-发动态功能.md` 拆分开发任务。目标是先完成P0闭环：用户可以发布和评论动态，天依可以发布world动态并延迟回复，管理员可以在控制台查看所有动态。

## 1. 开发目标
v0.3.0的开发目标不是做完整社交平台，而是完成一个“聊天之外的慢交流通道”：

1. 用户能在App和PC客户端看到动态流。
2. 用户能发布文字动态、评论可见动态。
3. 用户只能看到自己的动态、天依动态和系统通知。
4. 天依能在后台回复用户动态和评论。
5. citywalk和自动学歌完成后能发布天依动态。
6. 用户动态和评论会作为记忆候选交给现有memory_writer。
7. 管理员能在控制台查看所有动态和评论。

## 2. 总体开发顺序
建议按以下顺序推进：

1. 数据模型和数据库服务。
2. 用户侧REST接口。
3. 管理员侧查看接口。
4. Agent动态生成和评论生成能力。
5. 动态发布capability。
6. world任务接入和定时回复任务。
7. memory_writer接入。
8. App动态流。
9. PC动态窗口。
10. 管理控制台动态管理页。
11. 联调、测试和验收。

这个顺序的原则是：先把服务端核心闭环跑通，再接客户端和控制台；先做文字动态，再考虑图片动态。

## 3. 阶段一：数据模型与数据库服务
### 3.1 目标
建立动态、评论、未读状态的持久化能力，并在数据库服务层提供统一读写接口。

### 3.2 任务
- [x] 在SQL数据库中增加动态表。
- [x] 在SQL数据库中增加动态评论表。
- [x] 增加动态已读状态表，或实现基于已读游标的未读计算。
- [x] 在database service中增加dynamic相关服务。
- [x] 支持按当前用户过滤可见动态。
- [x] 支持按当前用户过滤可见评论。
- [x] 支持写入用户动态、天依动态、系统通知。
- [x] 支持写入用户评论和天依回复。
- [x] 支持标记动态或评论已读。
- [x] 保留`status`字段，为未来隐藏、删除和风控预留空间。

### 3.3 注意点
- 用户动态必须绑定`owner_user_id`。
- 天依动态和系统通知是全局可见，但评论仍然按用户隔离。
- 查询评论时，不能把其他用户对同一条天依动态的评论返回给当前用户。
- 系统通知默认不可评论。

### 3.4 验收
- [x] 可以创建用户动态，并只被该用户查询到。
- [x] 可以创建天依动态，并被所有用户查询到。
- [x] 用户A评论天依动态后，用户B看不到这条评论。
- [x] 管理员接口可以看到全部动态和评论。
- [x] 未读数量或未读状态可以正确计算。

## 4. 阶段二：用户侧接口
### 4.1 目标
为App和PC客户端提供动态读写能力。

### 4.2 任务
- [x] 增加`GET /dynamics`，获取当前用户可见动态列表。
- [x] 增加`POST /dynamics`，发布用户文字动态。
- [x] 增加`GET /dynamics/{dynamic_id}/comments`，获取当前用户可见评论。
- [x] 增加`POST /dynamics/{dynamic_id}/comments`，发表评论。
- [x] 增加`GET /dynamics/unread`，获取动态入口红点状态。
- [x] 增加`POST /dynamics/read`，标记动态已读。
- [x] 增加分页参数，例如`limit`和`cursor`。
- [x] 增加请求参数和返回对象的Pydantic模型。

### 4.3 注意点
- 所有接口必须走用户鉴权。
- 用户只能操作自己可见的动态。
- P0只支持文字动态，图片字段可以保留但不开放上传。
- 发布动态后应标记为待天依处理。
- 发表评论后应标记为待天依处理。

### 4.4 验收
- [x] 未登录请求被拒绝。
- [x] 用户不能读取其他用户私有动态。
- [x] 用户不能评论不可见动态。
- [x] 分页加载不会重复或漏掉动态。
- [x] 用户自己发布动态不会给自己制造未读红点。

## 6. 阶段四：Agent与capability接入
### 6.1 目标
让天依能够生成动态文案、生成评论回复，并通过统一能力发布动态或评论。

### 6.2 任务
- [x] 在agent层增加生成天依动态文案的接口。
- [x] 在agent层增加生成动态评论回复的接口。
- [x] 在agent层增加判断是否回复评论的接口。
- [x] 增加动态相关prompt模板。
- [x] 在capabilities中增加动态发布能力。
- [x] 在capabilities中增加动态评论发布能力。
- [x] 动态capability调用database service完成写入，不直接实现复杂SQL逻辑。

### 6.3 注意点
- 动态文案应比聊天回复更完整、更像“认真写过的一段文字”。
- 评论回复应避免变成即时聊天，应体现慢交流。
- 对用户主动态默认尝试回复；对评论由LLM判断是否回复。
- LLM失败时应记录失败状态，而不是阻塞任务。

### 6.4 验收
- [x] 给定citywalk事件，可以生成天依动态文案。
- [x] 给定学歌事件，可以生成天依动态文案。
- [x] 给定用户动态，可以生成天依回复。
- [x] 给定用户评论，可以判断是否需要回复。
- [x] capability能写入天依动态和天依评论。

## 7. 阶段五：world任务接入
### 7.1 目标
让world中的事件真正进入动态流。

### 7.2 任务
- [x] 在citywalk完成后触发天依动态发布。
- [x] 在自动学歌成功后触发天依动态发布。
- [x] 增加动态回复后台任务，每30分钟扫描待处理动态和评论。
- [x] 后台任务调用agent生成回复。
- [x] 后台任务调用capability写入天依评论。
- [x] 处理成功、忽略、失败三类状态。

### 7.3 注意点
- world负责“什么时候发生”，agent负责“写什么”，capability负责“发布出去”。
- 自动学歌动态需要包含歌曲信息和基于歌词/歌曲内容的评价。
- 批处理应限制单次处理数量，避免积压时一次性调用过多LLM。
- 同一条动态或评论不能被重复回复。

### 7.4 验收
- [x] citywalk完成后可以生成一条全局可见天依动态。
- [x] 自动学歌成功后可以生成一条全局可见天依动态。
- [x] 用户发布动态后，后台任务能在下一轮处理并回复。
- [x] 已处理动态不会重复回复。
- [x] 失败任务会记录原因，后续可排查。

## 8. 阶段六：memory_writer接入
### 8.1 目标
用户动态和用户评论进入记忆候选，系统通知不进入记忆。

### 8.2 任务
- [x] 用户发布动态后触发或排队memory_writer。
- [x] 用户发表评论后触发或排队memory_writer。
- [x] 记录动态记忆处理状态。
- [x] 记录评论记忆处理状态。
- [x] 给记忆写入传入来源信息，例如`dynamic_post`或`dynamic_comment`。
- [x] 系统通知跳过memory_writer。

### 8.3 注意点
- 复用现有memory_writer标准，不在v0.3.0单独设计记忆策略。
- 动态文本可能比聊天消息更长，需要确认上下文拼装不会污染聊天上下文。
- 后续控制台需要能看到哪些动态进入了记忆候选，以及处理结果。

### 8.4 验收
- [x] 用户动态会进入memory_writer候选。
- [x] 用户评论会进入memory_writer候选。
- [x] 系统通知不会进入memory_writer。
- [x] memory_writer失败不会影响动态发布成功。

## 14. 风险与控制
1. 可见性风险：所有查询必须严格按用户过滤，尤其是天依全局动态下的用户评论。
2. 记忆污染风险：先复用memory_writer，但必须记录来源和处理结果，方便后续观察。
3. LLM成本风险：动态回复任务需要限制单轮处理数量。
4. 客户端范围膨胀风险：P0不做图片上传、不做点赞、不做公开广场。
5. 任务重复处理风险：动态和评论必须有处理状态，后台任务要幂等。

## 15. 暂缓任务
以下任务不进入P0开发：
- 图片动态。
- 用户删除或编辑动态。
- 管理员删除、审核或发布系统通知。
- 公开动态广场。
- 点赞、转发、收藏。
- 复杂二级评论。
- 内容风控系统。
