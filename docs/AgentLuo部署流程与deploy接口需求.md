# AgentLuo 部署流程与 deploy 接口需求

状态：需求草案，待审核后实施。本文描述期望行为，不表示相关命令已经实现。

## 用户故事

1. 作为开发者，我希望从一个明确的 Git commit 构建服务端发布包，以便追踪线上代码，同时继续在同一仓库协同修改服务端和各客户端。
2. 作为运维人员，我希望将同一个发布包先部署到测试实例，再部署到生产实例，以便验证的内容与实际上线的内容一致。
3. 作为运维人员，我希望在执行前看到具体部署计划，以便确认代码、配置、模型和数据分别会发生什么变化，以及是否可以回退。
4. 作为运维人员，我希望用一条命令执行已检查的计划，以便完成准备、停服、备份、迁移、切换、启动和验收，并缩短停服时间。
5. 作为运维人员，我希望发布时保留实例配置和用户数据，并复用未变化的模型和运行环境，以便避免误覆盖和重复复制大文件。
6. 作为运维人员，我希望查询当前实例版本和最近的部署结果，并在兼容条件满足时回退版本，以便定位和恢复发布故障。

## 验收标准

| 编号 | 状态与输入 | 预期输出或行为 |
| --- | --- | --- |
| A01 | 仓库工作区存在未提交修改，执行 `build --ref <commit>` | 仅从指定 commit 构建，未提交修改不进入发布包；记录完整 commit SHA |
| A02 | 指定包含四个子项目的仓库 commit 构建 | 发布包只包含服务端运行所需代码、小资源、部署工具及清单，不包含客户端、生产密钥、用户数据、模型权重或本机虚拟环境 |
| A03 | 同一发布包分别生成测试和生产计划 | 发布包哈希保持一致，实例路径、端口和密钥从各自实例配置取得 |
| A04 | 对运行中的生产实例执行 `plan` | 生成计划文件与可读摘要，不停服、不执行迁移、不改写生产文件 |
| A05 | 发布包损坏、资产缺失、配置不兼容或空间不足 | 在计划中明确阻断原因，命令返回非零状态；不得输出可执行的成功计划 |
| A06 | 生成计划后发布包、目标部署版本、实例映射或关键配置发生变化，再执行 `apply` | 在停服前拒绝执行并要求重新生成计划；正常业务数据写入不会单独导致计划失效 |
| A07 | 两个进程同时对同一实例执行部署或回退 | 只允许一个修改流程持有部署锁，另一个明确失败；不同实例可独立操作 |
| A08 | Python 依赖和模型版本均未变化 | 复用已经验证的环境和资产；不重新安装依赖，不全量复制模型或用户媒体 |
| A09 | 依赖或模型版本变化 | 在停服前准备并验证新版本，不原地修改旧服务正在使用的环境或资产 |
| A10 | 停服失败或仍有实例写入进程 | 不执行离线数据迁移，不切换发布版本，记录失败原因 |
| A11 | 发布只修改代码和 Prompt | 更新发布文件，保留实例业务配置、密钥和数据；执行适用于本次变更的备份与检查 |
| A12 | 发布包含歌曲路径、配置结构或数据库结构迁移 | 计划列出迁移步骤、备份范围和兼容条件；停服后按顺序执行，验证完成后才切换启动 |
| A13 | 迁移或启动验收失败 | 返回非零状态，保留阶段记录和备份；仅在已证明安全时恢复旧服务，否则保持停止并给出恢复步骤 |
| A14 | 正式服务启动完成 | systemd 正常、健康接口返回成功、运行时为 running 且无错误、管理页面可访问；相关功能检查通过后才记录部署成功 |
| A15 | 变更涉及 TTS 代码、语音依赖或模型 | 额外完成实际语音合成，验证音频可解码、非空且非静音；测试进程不得与正式实例重复占用模型资源 |
| A16 | 对正常、停止或部署失败的实例执行 `status` | 分别输出实际服务状态、当前版本、最近操作阶段和健康状态，不把“命令执行过”视为“部署成功” |
| A17 | 旧版本与当前数据格式兼容，执行 `rollback` | 保留上线后新增业务数据，切回指定发布版本及匹配环境、资产，并重新验收 |
| A18 | 当前数据或配置与旧版本不兼容，执行 `rollback` | 在修改实例前拒绝直接回退，说明不兼容项及恢复所需步骤，不自动覆盖新数据 |
| A19 | 当前为既有平铺式生产目录，尚无发布记录 | 计划明确标记首次接管，列出目录调整、服务配置、环境处理与备份步骤；不假定已采用新布局 |
| A20 | 仓库暂时不可用，但实例和历史发布仍在 | 使用已归档的部署工具可以执行 `status` 和满足兼容条件的 `rollback` |
| A21 | 用户缺少必要的服务管理权限，执行 `apply` | 在停服和修改生产前说明缺少的具体权限；不要求将整个构建和部署过程作为 root 执行 |
| A22 | 部署中断后再次执行同一计划 | 检测未完成操作，不盲目重跑迁移；第一版允许明确拒绝并提供恢复步骤，不要求自动续跑 |

## 模块与架构

### 模块划分

部署工具源代码统一放在仓库 `server/scripts/deploy/`，建议入口为 `deploy.py`。生产端保存工具的已发布副本，不另行维护一套生产专用实现。

| 模块 | 职责 |
| --- | --- |
| 构建 | 从指定 commit 导出发布范围，生成文件校验清单和发布元数据 |
| 实例配置读取 | 将实例名称映射到根目录、systemd 服务和本机环境设置 |
| 计划与预检 | 比较目标发布和实例状态，计算准备、迁移、备份、验收及回退步骤 |
| 执行协调 | 管理实例部署锁、服务启停、阶段记录、发布切换和失败处理 |
| 迁移 | 通过版本化步骤更新配置、数据结构或目录布局 |
| 验收 | 检查资源、配置、依赖、数据库、健康接口和受影响业务能力 |
| 状态与回退 | 查询发布记录及实际运行状态，执行兼容条件满足的版本回退 |

可以复用现有 `ServerPaths`、统一启动入口、资源清单、资源校验和离线布局迁移脚本，但需检查其是否满足本规范。不能仅因为已有脚本执行成功，就视为满足所有部署验收条件。

### 文件归属与目录规范

| 类别 | 代表内容 | 规范 |
| --- | --- | --- |
| 发布文件 | 服务端代码、Prompt、人设、预制语音、管理页面、算法小资源 | 随发布包更新，完成发布后不原地修改 |
| 模型资产 | TTS 模型、学歌模型、参考音频、模型配套配置 | 使用独立版本和校验清单，按需准备并复用 |
| 实例配置 | config.json、密钥、管理员认证、第三方凭据 | 独立保存，不被仓库默认配置覆盖 |
| 可变数据 | 数据库、歌曲库、知识库、用户图片和音频、监控数据 | 独立持久保存，只有明确迁移步骤可以改变其布局或结构 |
| 运行目录 | 日志、缓存、临时文件、学歌中间产物、进程锁 | 每个实例独立，不写入发布目录或共享模型目录 |
| Python 环境 | 解释器和已安装依赖 | 按环境标识管理；新依赖使用新环境，旧版本环境保留用于回退 |

目标实例布局：

```text
agentluo-production/
├── releases/
│   ├── <release-id>/          # 代码、小资源、清单、工具副本
│   └── <previous-release-id>/
├── current -> releases/<release-id>
├── assets/<asset-version>/
├── environments/<environment-id>/
├── config/
├── data/
├── .runtime/
└── deployments/
    ├── operations/<operation-id>/  # 计划、阶段日志、验收结果
    └── backups/<operation-id>/     # 本次需要的恢复材料
```

具体目录通过现有 `AGENTLUO_CONFIG_DIR`、`AGENTLUO_RESOURCE_DIR`、`AGENTLUO_ASSET_DIR`、`AGENTLUO_DATA_DIR`、`AGENTLUO_RUNTIME_DIR` 及解释器设置连接。每次操作应记录实际使用的发布、资产和环境组合。`current` 的切换必须是同一文件系统内的原子替换；这种切换保证目录指向完整，不代表服务零停机。

生产和测试实例必须有独立配置、数据、运行目录、服务名称及端口。确认运行中不会写入的资产可以共享；不能假定所有第三方模型目录天然只读。凭据刷新、模型缓存等写入应迁至实例目录，或明确保持实例隔离。

现有虚拟环境可能包含绝对路径。首次接管时需要验证复用方式，必要时重新建立环境，禁止直接移动后假定仍然可用。

### 期望部署流程

#### 1. 构建发布包

1. 将分支、标签或 commit 参数解析为完整 commit SHA，后续构建只使用这个提交。
2. 按明确的发布范围导出服务端运行文件；不能复制整个工作区，也不能依靠“排除几个大目录”代替发布文件定义。
3. 生成发布清单，记录代码版本、文件哈希、依赖标识、资产版本、配置及数据兼容范围、迁移步骤和验收要求。
4. 校验小资源完整性，输出发布包及包哈希。

当前允许从 `dev` 发布；发布记录必须使用 commit SHA，不能仅记作“dev 最新版”。分支合并和推送由代码管理流程负责，`build` 不自动提交、合并或推送。

#### 2. 生成部署计划

1. 读取实例映射，确认目标目录、当前发布和服务身份。
2. 核验发布包、实例关键配置、模型资产和环境兼容性。
3. 列出要新建或复用的发布目录、模型版本和 Python 环境。
4. 列出配置或数据迁移、备份范围、停服要求、验收项目和回退限制。
5. 检查可用空间、必要权限和服务控制能力，输出可读摘要与机器可读计划。

`plan` 允许写入用户指定的计划文件，但不得创建生产发布目录、下载生产资产、安装生产依赖、停服或运行迁移。环境准备属于 `apply` 的在线阶段。

#### 3. 在线准备

1. `apply` 获取该实例的部署锁，检查计划是否仍适用。
2. 在独立位置解包新发布，拒绝不合法的归档路径，核验全部发布文件。
3. 准备缺失的资产和环境，验证完整性及依赖约束；不得改写正在使用的旧版本。
4. 执行不启动业务写入者的启动预检，并确认后续备份空间及服务管理权限。

任一步失败时，旧服务继续运行，记录失败并停止部署。重复应用当前已成功部署的同一发布包，应返回无需变更，而非再次停服。

#### 4. 停服、备份和迁移

1. 停止目标服务，等待退出，并确认相关子进程及维护写入者已停止。
2. 备份现有配置、发布组合及迁移涉及的数据，生成备份清单并验证其可读性。纯代码发布至少保留旧发布组合和实例配置快照。
3. 按版本顺序执行迁移，验证结果，记录已完成的迁移编号。
4. 迁移通过后更新发布、资产和环境选择，并切换 `current`。

首次目录迁移可以做完整离线备份；日常发布依据受影响范围备份，不要求每次复制全部图片、音频和模型。普通文件复制不能代替运行中 SQLite 数据库的一致性备份。

迁移脚本必须声明前置状态、目标状态、影响范围、验证方式及回退兼容性。涉及可重复执行的步骤必须具备幂等性；不具备幂等性的步骤必须通过状态记录拒绝重复执行。配置迁移应保留原有自定义值，只执行已声明的新增、转换或移除，不用默认模板覆盖实例配置。

#### 5. 启动和验收

1. 使用统一入口启动服务，并在有限超时内等待健康状态。
2. 检查 systemd 状态、异常退出或重启、健康接口、业务运行时及管理页面。
3. 执行计划要求的功能验收。离线 GPU 测试应安排在正式实例停止期间，测试结束后释放进程再启动正式服务。
4. 所有必需检查通过后记录部署成功，更新当前部署记录。

验收失败不能返回成功。应保存失败阶段、原因、实际运行状态和可执行恢复步骤。已经恢复旧服务的操作仍应记录“新版本部署失败，旧版本恢复成功”。

### 回退与保留规范

- `rollback` 回退的是发布版本及其环境、资产组合，默认保留当前业务数据。
- 已经接收用户写入后，不得自动恢复部署前数据库快照或恢复会绕开新数据的旧资源路径。
- 配置回退只处理版本不兼容的必要部分，不能无条件覆盖上线后更新的密钥、凭据或管理员设置。
- 只有兼容性明确、不会丢失新写入数据的逆向迁移才允许自动执行；其余情况拒绝自动回退，进入人工恢复流程。
- 第一版不自动清理历史发布、环境、资产及备份。后续增加保留策略时，必须保护当前版本、指定回退版本及其依赖。
- 应将使用的部署工具及接口版本归档。仓库不可用时，运维人员仍能从保留的发布目录调用工具查询和回退。

### 接口规范

#### 通用调用方式

```bash
python server/scripts/deploy/deploy.py [--config <部署配置>] <子命令> ...
```

默认部署配置路径为 `~/.config/agentluo/deploy.toml`；显式 `--config` 覆盖默认值。部署配置位于仓库之外，不包含业务密钥，不进入发布包。例如：

```toml
[instances.production]
root = "/data/projects/agentluo-production"
service = "agentluo.service"
health_url = "http://127.0.0.1:15673/admin/api/health"
admin_url = "http://127.0.0.1:15673/admin"
startup_timeout_seconds = 180

[instances.test]
root = "/data/projects/agentluo-test"
service = "agentluo-test.service"
health_url = "http://127.0.0.1:24523/admin/api/health"
admin_url = "http://127.0.0.1:24523/admin"
startup_timeout_seconds = 180
```

以上测试实例是配置示例，不表示当前机器已创建该服务。实例根目录要求使用绝对路径，执行前解析真实路径并校验目标身份，不能静默部署到另一个实例。

所有命令提供可读输出，并支持 `--json` 输出结果摘要；进度日志与 JSON 结果分流。日志和计划不能包含密钥、凭据正文、聊天内容或原始用户媒体。

#### `build`：构建发布包

```bash
deploy.py build --ref <commit|tag|branch> [--output-dir <目录>] [--json]
```

- 输入：必填代码引用；输出目录默认当前目录的 `dist/`。
- 行为：构建运行所需文件及清单；不访问生产配置和用户数据，不执行部署。
- 输出：发布标识、commit SHA、包路径、包哈希、资产和环境要求、验证结果。
- 约束：已有不同内容的同名产物不得被静默覆盖。发布内容不得依赖构建时工作区的未提交文件。

#### `plan`：检查并生成部署计划

```bash
deploy.py plan --package <发布包> --instance <名称> --out <计划文件> [--json]
```

- 输入：发布包、目标实例和计划输出路径，均必填。
- 行为：只读检查生产状态，比较版本和兼容性，生成具体执行步骤。
- 输出：计划标识、目标实例及真实路径、当前版本、目标包哈希、变更范围、准备步骤、备份、迁移、停服、验收和回退条件。
- 阻断项：未知实例、包损坏、不兼容、未声明迁移、必要资源来源缺失、权限不足或空间不足等。
- 约束：有阻断项时返回非零状态；诊断输出可以保留，但必须标记计划不可执行。

#### `apply`：执行已生成的计划

```bash
deploy.py apply --plan <计划文件> [--json]
```

- 输入：可执行的部署计划，不接受另一个目标目录或发布包覆盖计划中的目标。
- 行为：获取锁，复核计划，依次执行在线准备、停服、备份、迁移、切换、启动、验收。
- 输出：操作标识、逐阶段状态、实际发布版本、备份与日志位置、验收结果；失败时给出当前服务状态及恢复建议。
- 约束：调用 `apply` 表示执行该计划，不再插入重复的业务确认；操作系统权限需求应在修改生产前明确检查。
- 计划复核：检查工具兼容版本、包哈希、实例映射、当前发布、配置及迁移版本。对密钥文件只保存实例本地的受限核验信息；敏感凭据正文不得进入计划。凭据或配置变化后要求重新生成计划。不能对整个 `data/` 做哈希并把正常写入判为计划失效。

#### `status`：查询实际部署与运行状态

```bash
deploy.py status --instance <名称> [--json]
```

- 输入：实例名称。
- 行为：读取部署记录，查询 systemd 和健康接口，不启动服务、不执行迁移。
- 输出：当前发布和 commit、资产版本、环境标识、服务状态、运行时健康状态、最近操作及其阶段、最近成功部署、可回退候选版本。
- 约束：区分“部署记录指向的版本”与“实际运行的版本”。发现手工改动或不一致时明确报告，不依据目录名猜测版本。

#### `rollback`：回退到指定历史发布

```bash
deploy.py rollback --instance <名称> --to <release-id> [--json]
```

- 输入：实例名称和明确的历史发布标识，不支持含糊的“上一个目录”。
- 行为：先验证历史文件、环境、资产及当前配置和数据兼容性，再获取锁并复核状态；满足条件后停服、执行已声明的必要逆向迁移、切换并重新验收。
- 输出：回退操作记录、源版本、目标版本、迁移及验收结果、当前服务状态。
- 约束：回退计划需要在执行记录中留存；不兼容时必须在修改实例前拒绝。不得以自动恢复整个备份目录实现通用回退。

#### 返回状态约定

| 退出码 | 含义 |
| --- | --- |
| 0 | 命令成功；`status` 表示查询完成，不单独代表服务健康 |
| 2 | 参数或部署配置错误 |
| 3 | 预检阻断、计划失效或回退不兼容 |
| 4 | 实例部署锁冲突 |
| 5 | 执行、迁移、启动或验收失败 |

`status --json` 必须提供独立的健康字段，供自动化判断。发生未预期异常时返回非零状态，并保留可定位的错误信息。

#### 清单与记录要求

| 产物 | 必需信息 |
| --- | --- |
| 发布清单 | schema 版本、发布标识、commit SHA、发布文件路径/大小/哈希、资产版本、环境标识、配置/数据兼容范围、迁移清单、验收要求、工具版本 |
| 部署计划 | schema 版本、计划标识、实例身份、包哈希、预期当前版本、配置核验信息、迁移前置条件、准备/备份/切换/验收/回退步骤、阻断项 |
| 操作记录 | 操作标识、时间、源/目标版本、实际路径、阶段与结果、备份位置、迁移结果、健康结果、错误及恢复建议 |

发布标识必须唯一且可定位到包哈希，不只依赖短 commit。环境标识至少包含 Python 版本、平台、已解析依赖版本和 PyTorch/CUDA 选择；资产版本不能仅依赖目录名称，必须关联内容校验清单。记录中出现不支持的 schema 版本时应拒绝执行，而非忽略未知字段继续修改实例。

## 备注

### 关键技术选型

- 保留现有单仓库，构建阶段裁剪服务端发布范围；生产目录不要求存在 Git 仓库。
- 第一版面向 Linux 本机和 systemd，使用文件系统发布目录及原子链接切换。
- 优先使用 Python 实现部署协调，复用现有 Python 校验和迁移逻辑。构建器可使用独立解释器；运行环境版本由发布要求确定。
- 日常部署只对服务控制等必要操作使用提升权限。构建、解包和业务文件写入使用实例所属用户，避免生成 root 所有的业务文件。
- 实施前应按仓库开发规范审核完整需求，并为各验收项安排对应验证；本文不构成已经完成审核或实现的证明。

### 非目标

- 第一版不实现跨机器 SSH 部署、多节点滚动发布、零停机切换或容器编排。
- 不自动合并 PR、发布客户端、轮换密钥、重新登录第三方账号或修复歌曲内容。
- 不默认复制生产用户数据供开发测试，不允许测试实例写入生产数据目录。
- 不提供无条件数据降级，不以覆盖上线后的用户数据换取自动回退。
- 不把本次一次性迁移脚本直接当作可重复使用的标准部署工具。

### 未来目标

- 接入 CI 构建和测试环境验收，生产继续使用同一发布包。
- 增加远程部署、多实例管理、备份恢复演练和历史版本保留策略。
- 在需求明确后增加中断恢复、分阶段审批或零停机能力。


## 2026-11-11 实施约定调整

本节按项目维护者确认的简化规则调整前文对应要求：

- 主业务库和歌曲知识库使用独立的 SQLite schema 版本。plan 检查实际版本与结构，
  从发布携带的迁移定义生成适用步骤；不即时生成或猜测修改生产数据的 SQL。
