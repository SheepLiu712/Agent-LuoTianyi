# 产品需求文档 - v0.4.0 电话功能

## 更新日志

- 2026-07-15：创建第一版产品需求文档。
- 2026-07-15：补充完整产品边界、状态机、实时协议、Qwen Audio Realtime 接入、记忆规则、TTS 调度、数据模型、埋点、风险和验收标准。

## 1. 功能背景

目前 AgentLuo 的主要交互方式是聊天窗口。随着角色能力和 world 行为增加，仅依赖文字聊天难以覆盖更亲密、更实时的陪伴体验，也无法为未来机器人形态中的持续语音交互提供基础设施。

电话功能用于提供一个独立于聊天窗口的实时语音通道。用户主动发起电话后，可以直接与洛天依进行连续语音交流，允许用户打断、允许天依在沉默时主动接话，并在通话结束后形成可用于后续聊天的通话记录、摘要和记忆。

v0.4.0 的重点是完成从客户端采集、服务端实时转发、Qwen 对话、GPT-SoVITS 合成、客户端播放，到通话记录和记忆结算的完整闭环，并为后续机器人语音交互、客户端回声消除和更复杂的通话策略打下基础。

## 2. 产品目标

1. 在 PC 和 App 客户端提供独立电话界面，展示洛天依 Live2D、通话状态和通话时长。
2. 支持用户主动发起、挂断和在 5 秒内重连电话；P0 不支持天依主动呼叫用户。
3. 使用 Qwen Audio Realtime 完成用户语音识别和主要通话回复生成，并始终使用本地 GPT-SoVITS 生成洛天依声音。
4. 支持实时打断：用户开始说话后，停止当前回复、停止客户端播放并继续处理用户的新一轮输入。
5. 支持沉默 2 秒后由洛天依主动发起话题。
6. 支持电话中的记忆检索、分段记忆写入、通话摘要、事件记忆和用户画像更新。
7. 将通话记录写入专用通话表，并在现有 conversations 中形成可展示、可进入后续上下文的电话记录。
8. 提供覆盖延迟、错误、API 用量、播放确认、结算一致性和并发 TTS 的可观测能力。

## 3. 产品原则与边界

1. 电话是聊天、动态之外的实时交流通道，不替代现有聊天窗口。
2. 电话只能由用户主动发起。P0 不存在来电、响铃、接听超时或天依主动呼叫用户。
3. P0 默认接听所有电话，但保留从用户发起请求开始计算的 2 秒接听延迟，为未来增加“天依决定是否接听”预留空间。
4. 通话处于 `REQUESTING`、`ACTIVE` 或 `RECONNECTING` 时，用户不能通过聊天窗口发送新消息；客户端和服务端均需强制限制。
5. 同一用户原则上只能存在一个电话流。多设备同时登录问题不在电话功能中解决，后续可通过登录互斥处理。
6. P0 最多允许 5 个占用电话资源的流；第 6 个请求直接拒绝。
7. P0 使用耳机作为可靠打断的前提。扬声器外放可能产生回声并误触发打断，客户端 AEC 放入后续版本。
8. 用户和洛天依的原始音频均不持久化。通话文本永久保存，账号删除时级联删除。
9. P0 为内部测试版本，不在电话界面额外展示通话文本保存提示；相关规则写入用户协议。
10. v0.4.0 优先完成基础设施和可用闭环，不以达到成熟电话产品的音质和弱网体验为目标。

## 5. 通话状态机

### 5.1 状态定义

| 状态 | 含义 | 允许的主要操作 |
| --- | --- | --- |
| `IDLE` | 当前没有电话 | 发起电话 |
| `REQUESTING` | 已生成 `call_id`，等待固定 2 秒并准备上游资源 | 用户取消 |
| `ACTIVE` | Qwen、TTS、上下文和 WebSocket 均可用 | 发送音频、打断、挂断 |
| `RECONNECTING` | 客户端 WebSocket 已断开，服务端最多保留 5 秒 | 使用原 `call_id` 恢复 |
| `ENDING` | 正在停止资源并进行幂等结算 | 不接收新音频 |
| `ENDED` | 通话已结束 | 返回聊天界面 |

状态主流程：

```text
IDLE
  → 用户发起请求并生成 call_id
REQUESTING
  → 等待2秒并成功建立Qwen连接
ACTIVE
  → 用户挂断或发生终止错误
ENDING
  → 记录和异步后处理已启动
ENDED
```

断线恢复流程：

```text
ACTIVE
  → 客户端WebSocket断开
RECONNECTING
  → 5秒内call.resume验证成功
ACTIVE

RECONNECTING
  → 超过5秒
ENDING(exit_code=-1)
```

### 5.2 退出码

| 退出码 | 含义 | 是否写通话表 | 是否写 conversation |
| --- | --- | --- | --- |
| `0` | 已接通后正常挂断 | 是 | 是 |
| `1` | 用户在接通前挂断 | 是，摘要固定为“未接通就挂断” | 是 |
| `-1` | 客户端 WebSocket 重连超时 | 是 | 是 |
| `-2` | Qwen 建连或运行中连接失败 | 接通前失败不写；接通后失败写 | 接通前失败不写；接通后失败写 |
| `-3` | GPT-SoVITS 重试后仍失败 | 是 | 是 |
| `-4` | 其他服务端内部错误 | 已进入通话则写 | 已进入通话则写 |
| `-5` | 达到最大电话并发数 | 否 | 否 |

`call_id` 在用户发起请求时生成。通话时长从进入 `ACTIVE` 开始计算；接通前挂断的时长为 0。

## 6. 核心用户流程

### 6.1 用户发起电话

1. 用户点击“呼叫天依”，客户端提示 P0 建议使用耳机并进入电话界面。
2. 客户端连接 `/call_ws`、完成现有登录认证并发送 `call.start`。
3. 服务端检查用户当前电话状态和全局电话并发数，生成 `call_id` 并进入 `REQUESTING`。
4. 从请求到达服务端开始等待 2 秒。
5. 服务端创建 Qwen 连接、CallStream 内存状态和初始上下文。
6. Qwen 连接成功后进入 `ACTIVE`，服务端发送 `call.connected`。
7. Qwen 首次建连失败时返回 `exit_code=-2`，只写 observability，不写通话表和 conversation。

### 6.2 用户和天依对话

1. 客户端持续采集 PCM 音频，通过 JSON Base64 事件发送给服务端。
2. 服务端代理音频到 Qwen Audio Realtime。
3. Qwen 负责 ASR、VAD 和主要对话回复生成，输出模态固定为文本。
4. 服务端按换行解析 Qwen 文本，每个完整行形成一个 TTS 任务。
5. GPT-SoVITS 流式生成洛天依音频，服务端发送到客户端播放。
6. 客户端逐句发送 `call.playback_completed`，确认用户已完整听到该句。
7. 用户最终 ASR 文本和已播放完成的洛天依文本写入 `call_turns`。

### 6.3 用户挂断

1. 用户点击挂断，客户端发送 `call.hangup`。
2. 服务端停止接收新音频，取消或丢弃未完成回复，进入 `ENDING`。
3. 服务端幂等写入通话结束状态和 conversation，并启动摘要、记忆和画像异步任务。
4. 服务端返回 `call.ended`，客户端释放音频资源并返回聊天界面。
5. 正常结束仍使用 `exit_code=0`；摘要、记忆或画像失败不会改变通话退出码。

### 6.4 接通前挂断

1. 用户可在 `REQUESTING` 的 2 秒等待期间挂断。
2. 服务端使用原 `call_id` 创建通话记录，退出码为 `1`，摘要固定为“未接通就挂断”。
3. 同时写入一条 conversation，内容为“语音通话0秒”，并在 `meta_data` 中保存固定摘要。
4. 不执行通话记忆写入和用户画像更新。

### 6.5 WebSocket 断线和重连

1. `/call_ws` 断开后，CallStream 进入 `RECONNECTING` 并保留 5 秒。
2. 保留 Qwen 连接和 `call_id`；停止向客户端发送音频，并丢弃断线期间产生的回复和 TTS 结果。
3. 客户端断线期间不缓存麦克风音频。
4. 客户端重新认证后发送 `call.resume`，服务端校验当前用户与 `call_id` 的归属。
5. 5 秒内恢复成功则复用原 CallStream，从新的用户音频继续通话。
6. 超时则按网络异常结束，退出码为 `-1`，并结算已有通话记录。

## 7. `/call_ws` 协议

### 7.1 协议原则

1. 新建独立 `/call_ws`，不复用 `/chat_ws` 的消息循环。
2. 认证、心跳、错误结构和 JSON 风格参考现有 `/chat_ws`。
3. 控制消息和音频消息全部使用 JSON；音频放入 Base64 字段，P0 接受相应带宽和 CPU 开销。
4. Qwen API Key 始终只保留在服务端，客户端不能直连 Qwen。
5. 所有与播放相关的事件携带 `call_id`、`response_id` 和 `audio_id`，避免旧回复和新回复串流。

### 7.2 客户端事件

| 事件 | 作用 | 关键字段 |
| --- | --- | --- |
| `call.start` | 发起电话 | 客户端请求 ID |
| `call.resume` | 恢复 5 秒内断开的电话 | `call_id`、现有登录认证 |
| `call.audio.append` | 发送用户 PCM 音频 | `call_id`、`seq`、`audio` |
| `call.hangup` | 用户主动挂断 | `call_id` |
| `call.playback_completed` | 一句音频已完整播放 | `call_id`、`response_id`、`audio_id` |
| `call.playback_stopped` | 客户端已因打断停止播放 | `call_id`、`response_id`、`audio_id`、`reason` |
| 心跳事件 | 保持 WebSocket 活跃 | 复用现有协议风格 |

### 7.3 服务端事件

| 事件 | 作用 | 关键字段 |
| --- | --- | --- |
| `call.requested` | 已生成电话请求 | `call_id`、请求时间 |
| `call.connected` | 已进入通话中 | `call_id`、连接时间 |
| `call.audio.chunk` | 返回 GPT-SoVITS 音频 | `call_id`、`response_id`、`audio_id`、`seq`、音频字段 |
| `call.stop_playback` | 要求客户端立即停止指定回复 | `call_id`、`response_id`、`reason` |
| `call.reconnecting` | 服务端进入 5 秒保留期 | `call_id`、截止时间 |
| `call.resumed` | 原电话恢复成功 | `call_id` |
| `call.rejected` | 请求被拒绝 | `call_id`（如已生成）、退出码、原因 |
| `call.ended` | 通话已结束 | `call_id`、退出码、时长 |
| `call.error` | 可恢复或不可恢复错误 | `call_id`、错误码、错误信息 |

具体音频分片大小、ACK 超时和心跳间隔由技术设计确定，但必须满足本 PRD 的延迟和错误处理要求。

## 8. 音频与 Qwen Audio Realtime

### 8.1 音频格式

- 用户输入：16-bit、16 kHz、单声道 PCM。
- 客户端负责将实际麦克风格式重采样和声道转换为目标格式。
- 服务端返回音频沿用现有 GPT-SoVITS 流式输出格式，并通过 `/call_ws` JSON Base64 发送。
- 原始输入和输出音频均不持久化。

### 8.2 Qwen 职责

P0 使用 `qwen-audio-3.0-realtime-flash`：

- Qwen 同时负责 ASR、VAD 和主要通话回复生成。
- Qwen 输出模态配置为 `text`，服务端丢弃任何意外出现的 Qwen 音频输出。
- 洛天依人设、表达偏好、用户画像、用户偏好、输出格式、最近聊天上下文和工具定义在建立 Qwen 连接后写入。
- 普通通话回复不经过 `LuoTianyiAgent.main_chat`。
- `LuoTianyiAgent` 仅在主动找话题、记忆能力和用户画像等现有能力需要复用时参与。

### 8.3 回复格式与解析

系统提示词要求 Qwen 按以下格式输出，每句话占一行：

```text
[<语气>]<内容>
```

解析规则：

1. 文本增量按 `\n` 缓冲；每产生完整一行就创建一个 TTS 任务。
2. 回复完成时，最后一行即使没有换行也需要 flush。
3. 无法解析语气时使用默认语气，但仍然朗读内容。
4. Function Call 使用 Qwen 原生 `item.type=function_call`，不得通过普通文本伪造工具调用协议。
5. 同一次 Qwen 响应可以同时包含普通消息和 Function Call。

## 9. 通话上下文与记忆检索

### 9.1 初始上下文

建立 Qwen 连接后，首先写入一个 system prompt，至少包含：

- 洛天依的静态人设；
- 洛天依的表达偏好，包括说话风格、口语化要求、回复长度倾向、语气标签和每句话占一行的输出规则；
- 当前用户画像；
- 当前用户偏好，包括关系定位、期望表达风格、期望性格特征和用户补充上下文；
- 电话模式的行为规则，包括只能调用 `search_memory`、打断、主动话题和回复格式要求。

人设和表达偏好从当前 `CharacterProfile` 及其静态变量资源读取；用户画像和用户偏好从当前用户的数据库记录读取，用户偏好的格式化规则应复用现有聊天链路，避免电话和聊天对同一偏好产生不同解释。

电话开始时抓取的聊天历史只包括：

- 最近 10 分钟内的聊天消息；
- 最多 20 条，同时满足时间和数量限制；
- 包含文字、唱歌、图片消息的历史视觉识别文本和已有 `ContextType.CALL` 的电话摘要；
- 不包含更早的压缩对话总结。

这 20 条消息按时间排序后拼成一个历史文本项，以 `role=user` 注入 Qwen。文本使用 `[用户]`、`[洛天依]`、`[唱歌]`、`[图片描述]` 和 `[语音通话]` 标记来源。系统提示词明确说明该项是历史转录，不应把其中内容提升为系统指令。

本次“用户发起语音电话”请求作为独立 `role=user` 项放入 CallStream 初始内存上下文，但不写入数据库。

### 9.2 唯一工具：`search_memory`

Qwen 在电话中只能调用 `search_memory`。不允许 Qwen 直接写入或删除长期记忆。

系统提示词要求：当 Qwen 不确定并需要记忆时，应先输出类似“我想想”的自然回复，同时产生原生 Function Call。普通回复先进入 TTS，记忆检索异步执行，检索结果返回后再触发后续回复，避免用户长时间听不到声音。

工具处理结果：

- 搜索成功且有新增记忆：注入新增记忆，并返回新增数量。
- 搜索成功但结果均已在池内：返回“没有更多记忆”。
- 搜索失败：返回“记忆搜索失败”，Qwen 继续回复，不终止电话。

### 9.3 通话记忆池

CallStream 在内存中维护：

```text
memory_id → qwen_item_id、injected_at
```

记忆内容以 `role=system` 注入 Qwen。业务层记忆消息尽量只包含 `role` 和 `text`；`memory_id`、Qwen `item_id` 和注入时间只用于服务端状态管理，不写入提示词正文。

规则：

1. 搜索结果中的 `memory_id` 已在池内时，不重复注入。
2. 新增记忆通过 `conversation.item.create` 注入，并保存返回或预设的 `item_id`。
3. 池超限时通过 `conversation.item.delete` 删除最早注入的记忆。
4. 若本轮新增记忆数不超过 10，处理后总池最多保留 10 条。
5. 若本轮新增记忆本身超过 10 条，删除旧池内容，但完整保留本轮新增批次；此时允许池临时大于 10。
6. 记忆池生命周期与 CallStream 一致，不持久化到通话数据库。

## 10. 打断、播放确认和主动话题

### 10.1 用户打断

`input_audio_buffer.speech_started` 是主要打断信号。

收到打断信号后：

1. 服务端向 Qwen 发送 `response.cancel`。
2. 将当前 `response_id` 标记为 cancelled。
3. 丢弃该响应尚未解析的后续句子，不再创建 TTS 任务。
4. 删除该响应排队中的 TTS 任务。
5. 若 GPT-SoVITS 正在生成当前句，允许底层任务运行到结束，但从打断时刻起不再向客户端转发后续音频。
6. 服务端发送 `call.stop_playback`，客户端立即停止对应音频并回传 `call.playback_stopped`。
7. 被打断且未完整播放的洛天依句子不写入 `call_turns`，也不计入 memory_write 的行数。

TTS 的“不可抢占”仅指高优先级普通任务不能抢占正在运行的任务，不影响打断、挂断和断线对指定电话响应的取消语义。

### 10.2 播放完成

每个 TTS 句子具有 `audio_id`、`response_id` 和流内 `seq`。客户端完整播放后发送 `call.playback_completed`。

- 洛天依句子只有收到播放完成 ACK 后才写入 `call_turns` 并计入 memory_write。
- 同一回复第一句播放完成、第二句被打断时，只保留第一句。
- ACK 丢失或超时必须记录异常，不得错误触发主动话题；具体超时值由技术设计确定。

### 10.3 主动找话题

满足以下全部条件后开始 2 秒空闲计时：

1. 当前 Qwen `response_id` 已收到 `response.done`；
2. 该回复所有已生成 TTS 均收到播放完成 ACK；
3. 没有等待中的 Function Call；
4. 没有等待中或运行中的电话 TTS 任务；
5. 当前不存在主动话题生成任务。

2 秒内收到 `speech_started` 时取消计时。超时后调用现有 LLM 和角色能力生成主动话题，再交给 GPT-SoVITS。

竞争处理：

- 主动话题 LLM 尚未返回时用户开始说话：取消任务或丢弃结果。
- 主动话题已进入 TTS 时用户开始说话：按普通打断处理。
- 主动话题只有收到播放完成 ACK 后，才作为 assistant 消息注入 Qwen 上下文、写入 `call_turns` 并计入 memory_write。

## 11. TTS 调度

### 11.1 调度原则

继续复用并重构 `GlobalSpeakingWorker`，保证 GPT-SoVITS 同时只运行一个任务，避免 GPU OOM。

1. 普通聊天和电话都视为 stream，基础优先级一致。
2. 同一 stream 内必须严格 FIFO。
3. 调度器只比较各 stream 的队首任务，后续任务不能越过本流队首。
4. 不同 stream 同优先级时顺序任意。
5. 调度只影响下一个任务，不抢占正在执行的普通任务。

### 11.2 动态优先级

```text
p = max(t_pass / T_est, 1)
T_est = len(content) / 200 * 60 秒
```

- `t_pass`：该 stream 上一个任务开始处理至今的时间。
- `len(content)`：按中文字符数近似。
- 新 stream 尚无已处理任务时优先级为 1。
- `p` 越大，队首任务越优先。
- 每次从队列取任务时重新计算候选 stream 的优先级；后续可寻找无需全量重算的等效实现。

### 11.3 并发限制

- `REQUESTING`、`ACTIVE` 和 `RECONNECTING` 均占用电话并发名额。
- 同时最多 5 个电话流。
- 第 6 个请求返回 `exit_code=-5`，不创建通话表和 conversation，只写 observability。

## 12. 通话记录、conversation 与后处理

### 12.1 数据模型

P0 使用两张新表。

`call_sessions` 建议字段：

- `call_id`
- `user_id`
- `character_id`
- `status`
- `requested_at`
- `connected_at`
- `ended_at`
- `duration_seconds`
- `exit_code`
- `summary`
- `summary_status`
- `memory_status`
- `profile_status`
- `conversation_id`
- `created_at`
- `updated_at`

`call_turns` 建议字段：

- `id`
- `call_id`
- `seq`
- `speaker`：`user` / `assistant`
- `text`
- `started_at`
- `ended_at`
- `raw_events_json`
- `created_at`

`call_turns` 按完整语义行增量写入，避免进程崩溃时丢失整通电话。用户行以最终 ASR 文本为准；洛天依行以播放完成 ACK 为准。

`call_sessions` 在电话成功进入 `ACTIVE` 时创建，随后逐轮增量写入 `call_turns`。接通前挂断是例外：在用户挂断时直接创建退出码为 `1` 的 `call_sessions` 和 conversation。Qwen 首次建连失败和并发拒绝均不创建电话业务记录。

### 12.2 原始事件保存规则

保留事件类型、事件 ID、call ID、response ID、item ID、时间戳、文本、错误和 API usage。`audio`、`delta` 等 Base64 音频字段只保留长度、格式和时间戳，禁止保存 Base64 原文。

完整 transcript 只保存在 `call_turns`。Observability 保存 ID、文本长度、错误和 API 用量，不重复保存完整 transcript。

### 12.3 conversation 结算

通话结束时使用幂等事务：

1. 将 `call_sessions` 置为 ended。
2. 插入现有 `conversations`，`type=ContextType.CALL`，内容为“语音通话<时长>”。
3. `conversations.meta_data` 只写 `summary`；`call_id`、conversation 关联和摘要状态均由 `call_sessions` 保存。
4. 将 conversation ID 回写到 `call_sessions.conversation_id`。

conversation 在通话结束时立即创建，初始 `meta_data.summary` 允许为空，同时在 `call_sessions` 中将 `summary_status` 设为 pending。摘要任务完成后更新 `call_sessions.summary`、`call_sessions.summary_status` 和 `conversations.meta_data.summary`。摘要失败不删除 conversation。

接通前挂断也写 conversation；Qwen 首次建连失败和并发拒绝不写。

后续聊天格式化 `ContextType.CALL` 时使用：

```text
[时间] 语音通话<时长>：<summary>
```

摘要 pending 或失败且为空时，只加入“语音通话<时长>”。

### 12.4 通话摘要

1. 通话结束后将 transcript 作为 prompt 输入现有 LLM 生成摘要。
2. 提示词要求摘要简洁；150 字等合理长度允许保留。
3. 结果超过 200 字时重新生成一次。
4. 第二次仍超过 200 字时截断为 100 字。
5. 摘要状态独立记录为 pending、success 或 failed，不改变正常通话退出码。

### 12.5 保存和可见性

- `call_sessions` 和 `call_turns` 永久保留。
- 用户不能单独删除电话 transcript。
- 用户删除账号时级联删除全部通话数据。
- 管理员在 P0 控制台只能查看摘要、状态和错误；完整 transcript 查询接口放入 P1。
- 记忆内容仅对洛天依的记忆系统可见。

## 13. 记忆写入与用户画像

### 13.1 分段 memory_write

用户和洛天依合计每累计 10 行完整文本，异步触发一次 `memory_write`。

1. 用户行以最终 ASR 完成为准。
2. 洛天依行以 `call.playback_completed` 为准。
3. 被打断的半句不计入。
4. 使用 `call_id + end_seq` 作为幂等键。
5. 同一电话同时最多运行一个 memory_write；后续批次排队。
6. 单次失败重试两次，最终失败更新 `memory_status` 并写 observability，不终止电话。
7. 通话结束时，尾部不足 10 行仍执行一次；恰好为 10 的倍数时不重复执行。

### 13.2 通话事件记忆

通话结束后，将摘要写入现有 `MemoryRecord` 并向量化，作为 event_memory 表示当天和用户进行过电话交流。使用 `call_id` 保证重复结算幂等。

长期记忆仍通过现有向量数据库检索，不把全部历史记忆直接塞入 Qwen 上下文。

### 13.3 用户画像

- 仅 `exit_code=0` 的正常通话在结束后立即异步更新用户画像。
- 未接通、异常断线、Qwen 失败、TTS 失败和其他异常通话不更新用户画像。
- `profile_status` 独立记录成功或失败，失败不改变通话退出码。

## 14. 客户端需求

### 14.1 电话界面

- 独立于聊天窗口，进入后全屏展示洛天依 Live2D。
- 展示请求中、通话中、重连中、已结束和错误状态。
- 展示从进入 `ACTIVE` 开始计算的通话时长。
- 提供挂断按钮。
- P0 不展示实时 transcript。
- 发起前展示耳机提示。

### 14.2 麦克风与播放

- 请求麦克风权限并处理拒绝、设备缺失和采集失败。
- 将设备输入适配为 16-bit、16 kHz、单声道 PCM。
- 按服务端事件顺序播放 GPT-SoVITS 音频。
- 收到 `call.stop_playback` 后立即清空对应播放缓冲并发送 `call.playback_stopped`。
- 每句完整播放后发送 `call.playback_completed`。
- 客户端不得播放已取消 `response_id` 的迟到音频包。

### 14.3 聊天互斥

- 电话处于 `REQUESTING`、`ACTIVE` 或 `RECONNECTING` 时禁用聊天输入和发送按钮。
- 服务端同时拒绝该用户的新聊天 ingress，返回 `CALL_IN_PROGRESS`。
- 电话结束后恢复聊天输入。

## 15. 服务端模块边界

建议按现有架构划分职责：

- `chat_session/call_stream.py`：单个电话的状态机、音频代理、Qwen 事件编排、记忆池、主动话题、打断和后处理触发。
- `chat_session/call_stream_manager.py`：按用户管理 CallStream、并发限制、5 秒保留、恢复和销毁。
- `utils/realtime_dialogue/`：通用实时对话模型接口、Qwen Audio Realtime WebSocket 适配器、事件模型、供应商错误转换和会话工厂。它与现有 `utils/llm`、`utils/vision` 同属模型服务基础设施，不作为角色能力注册到 `CapabilityManager`。
- `RealtimeDialogueService`：与 `LLMService` 平行，由 `SystemRuntime` 初始化并注入 `ChatSessionManager`；持有供应商配置和客户端工厂，不持有具体用户的通话状态。
- `CallStream`：持有单通电话的 Qwen Realtime 会话实例及其生命周期，负责把模型事件转换为电话领域行为。
- `chat_session/dependency/global_speaking_worker.py`：流内 FIFO、流间优先级、电话任务取消和音频回调。
- `capabilities/speech/`：继续负责本地 GPT-SoVITS 调用和流式音频生成。
- `system/user_interface/`：`/call_ws`、认证、JSON 协议、聊天互斥错误和客户端连接管理。
- `system/database/`：`call_sessions`、`call_turns`、幂等 conversation 结算和查询。
- `agent`：主动话题生成，并提供对角色人设和现有能力的访问。
- `subconscious`：复用 memory facade、memory_write 和 user_profile_updater。
- `observability`：记录电话链路 spans、事件、错误、延迟和 API usage。

`CallStream` 直接依赖运行时提供的能力和服务，不通过新增全局 service locator 或 wrapper hub 获取依赖。

`capabilities` 表示角色可执行或可被上层调用的语义能力，例如唱歌、语音合成、图片理解和发布动态。Qwen Audio Realtime 适配器只是电话链路使用的模型通信基础设施，不是 Agent 可独立调用的角色动作，因此 P0 不为它增加 capability 包装。若未来多个角色能力需要以统一语义调用实时对话服务，再在 `capabilities` 层增加薄包装，但底层供应商接口仍保留在 `utils/realtime_dialogue`。

## 16. 异常处理

| 场景 | 行为 |
| --- | --- |
| 麦克风权限拒绝 | 客户端提示并不发起电话 |
| 达到 5 路并发 | 返回 `-5`，不创建记录 |
| 用户接通前挂断 | 返回 `1`，写通话表和 conversation |
| Qwen 首次建连失败 | 返回 `-2`，只写 observability |
| Qwen 通话中断开 | 返回 `-2`，保留已完成记录并结算 |
| 单句 GPT-SoVITS 失败 | 重试一次 |
| GPT-SoVITS 重试仍失败 | 返回 `-3` 并结束通话 |
| 客户端 WebSocket 断开 | 进入 5 秒 `RECONNECTING` |
| 5 秒内恢复 | 复用 `call_id` 和 Qwen 连接，从新音频继续 |
| 5 秒未恢复 | 返回 `-1` 并结算 |
| `search_memory` 失败 | 返回“记忆搜索失败”，通话继续 |
| 没有新增记忆 | 返回“没有更多记忆”，通话继续 |
| memory_write、摘要或画像失败 | 更新独立状态并记录错误，不改变 `exit_code=0` |
| 播放 ACK 丢失 | 记录异常，不错误启动主动话题 |

## 18. 验收标准

### 18.1 功能验收

1. 用户可以在 PC 和 App 主动发起电话，服务端固定等待 2 秒后默认接听。
2. 用户不能在电话状态中通过聊天窗口发送新消息，服务端也会拒绝绕过客户端的聊天 ingress。
3. 用户音频以 16-bit、16 kHz、单声道 PCM 进入 Qwen；Qwen API Key 不下发客户端。
4. Qwen 只输出文本，所有洛天依声音均由本地 GPT-SoVITS 生成。
5. Qwen 普通文本可以按行生成多个 TTS 任务，语气解析失败时仍能使用默认语气朗读。
6. 同一次回复可先朗读“我想想”等自然文本，再异步完成 `search_memory` 并生成后续回复。
7. 记忆池能够去重、注入、删除和按规则超限淘汰。
8. 用户打断后，后续句子不再进入 TTS，当前 TTS 后续音频不再发送，客户端停止播放并回传 ACK。
9. 被打断且未完整播放的洛天依句子不写入 transcript 和 memory_write 计数。
10. 同一通电话的 TTS 严格按句子顺序播放，不因动态优先级乱序。
11. 用户在 5 秒内重连可以复用原 `call_id` 和 CallStream；超时按 `-1` 结算。
12. 沉默条件满足后 2 秒触发主动话题；用户开始说话时可以取消尚未播放的主动话题。
13. 每累计 10 行完整文本触发 memory_write，结束时不足 10 行仍处理，重复结算不产生重复记忆。
14. 正常结束后生成 conversation、摘要、event_memory 和用户画像更新任务。
15. 未接通就挂断写入退出码 `1` 的通话记录和 conversation。
16. Qwen 首次建连失败和并发拒绝不写通话表和 conversation，但有 observability 记录。
17. `ContextType.CALL` 能在后续聊天上下文中显示通话时长和摘要。
18. 数据库和日志中不存在原始输入、输出音频 Base64。
19. 用户删除账号后，通话表和逐轮记录级联删除。
20. P0 客户端在发起电话前显示耳机提示。

### 18.2 性能和稳定性验收

1. 建立请求到进入通话中的 P95 延迟小于 5 秒，包含固定 2 秒接听延迟。
2. Qwen `speech_stopped` 到 GPT-SoVITS 首包发送的 P95 延迟小于 2 秒。
3. Qwen `speech_started` 到客户端停止播放 ACK 的 P95 延迟小于 1 秒。
4. 正常挂断结算成功率不低于 95%。
5. `call_sessions` 与 conversations 一致率以 100% 为目标；任何不一致均应产生可追踪错误。
6. Qwen、GPT-SoVITS 和网络调用错误率分别低于 1%，按对应调用或传输事件统计。
7. 5 个电话流持续对话并同时创建 1 个普通聊天 TTS 流时：
   - GPT-SoVITS 实际并发始终为 1；
   - 不发生 GPU OOM；
   - 电话和聊天流内部均不乱序；
   - 普通聊天 TTS 排队时间不超过 10 秒；
   - 任一持续产生任务的流不能永久压制其他流。
8. P0 暂不为“5 秒内重连成功率”设置数值指标，但必须覆盖成功恢复和超时结算的功能测试。

## 19. 风险

1. P0 没有客户端 AEC，扬声器外放可能把洛天依声音重新采集为用户语音并触发错误打断，因此必须明确提示使用耳机。
2. JSON Base64 音频比二进制帧有额外带宽、内存复制和 CPU 开销，需要通过首包延迟和 5 路并发测试验证是否可接受。
3. 当前 GPT-SoVITS 全局串行，电话会显著增加持续 TTS 压力；调度器重构错误可能造成乱序、饥饿或聊天延迟。
4. 打断不能保证底层 GPT-SoVITS 推理真正停止，虽然用户侧能立即停止播放，但 GPU 资源仍可能被已取消任务短暂占用。
5. Qwen 会自动裁剪长上下文。P0 已将初始聊天历史压缩到最近 10 分钟、最多 20 条，但长电话仍可能遗忘早期内容。
6. 播放完成 ACK 是 transcript、memory_write 和主动话题计时的共同依据，ACK 丢失会影响多个下游行为，必须有超时、错误记录和迟到事件防护。
7. 通话 transcript 永久保存且管理员未来可能查看完整内容，需要确保账号删除级联、权限隔离和日志脱敏正确。
8. P0 同时覆盖服务端、PC 和 App，客户端音频采集、权限、播放和重连行为差异可能扩大测试范围。

- 动态优先级队列的等效高效实现。
- 数据库索引、批量写入和 observability 采样策略。
