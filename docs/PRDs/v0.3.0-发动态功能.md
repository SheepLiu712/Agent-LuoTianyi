# 产品需求文档 - v0.3.0 发动态功能

## 更新日志
- 2026-07-04：创建第一版产品需求文档。
- 2026-07-04：补充完整产品边界、可见性规则、记忆规则、P0/P1范围和验收标准。

## 1. 功能背景
目前AgentLuo的主要交互方式是聊天窗口。用户发送消息后，AgentLuo在聊天中回复。这种方式已经可以支撑对话体验，但仍有几个明显局限：

1. 角色缺少聊天窗口之外的生活痕迹。随着world功能增加，天依会城市漫步、学习歌曲、接收外部事件，但这些行为目前主要藏在后台，用户很难感知“天依在世界中生活”。
2. 系统通知缺少合适通道。部分需要所有用户知道的消息，如果直接通过主动发言发送，会进入聊天历史、上下文和记忆，污染正常对话。
3. 用户缺少一种慢交流方式。聊天强调即时回复，而动态可以允许用户发布一段更完整的故事，等待天依稍后看到并回应。
4. 动态天然适合作为记忆候选。用户在动态中讲述的内容通常更完整，更适合围绕一条事件构建记忆。

因此，v0.3.0希望增加一个独立的“动态”功能，让天依、用户和系统都可以在聊天之外发布信息，并让天依以较慢节奏回应用户动态。

## 2. 产品目标
1. 增加一个独立的动态流界面，展示用户自己的动态、天依的动态和系统通知。
2. 支持用户发布动态、评论动态，并等待天依稍后回复。
3. 支持天依在完成world事件后主动发布动态，例如城市漫步完成、学会新歌。
4. 支持系统通知通过动态通道发布，不进入聊天历史和记忆。
5. 支持动态入口未读红点，让用户知道有新动态或新回复。
6. 服务端提供完整的动态读写、评论、轮询回复和管理控制台查看能力。

## 3. 产品原则
1. 动态是聊天之外的慢交流通道，不替代聊天。
2. 动态默认保护用户隐私，用户之间不可互相查看动态和评论。
3. 天依的动态可以对所有用户可见，但不同用户对天依动态的评论彼此不可见。
4. 用户动态和用户评论可以尝试进入记忆，系统通知明确不进入记忆。
5. v0.3.0优先完成可用闭环，不把动态做成完整社交平台。

## 4. 用户范围与可见性
动态中存在三类发布者：

| 发布者 | 示例 | 用户是否可见 | 是否进入记忆 |
| --- | --- | --- | --- |
| 用户 | 用户写下今天发生的事 | 仅发布者本人和管理员可见 | 尝试进入记忆 |
| 天依 | 城市漫步日记、学歌完成感想 | 所有用户可见 | 不直接进入用户记忆 |
| 系统 | 维护通知、版本公告 | 所有用户可见 | 不进入记忆 |

评论可见性规则：
1. 用户评论自己的动态：仅该用户、天依和管理员可见。
2. 用户评论天依的动态：仅该用户、天依和管理员可见，其他用户不可见。
3. 天依回复用户动态或评论：仅对应用户和管理员可见。
4. 系统通知默认不可评论；如后续需要互动，再单独设计。

管理员可见性：
1. 管理员可以在控制台查看所有动态和评论。
2. v0.3.0不要求动态审核后发布。
3. v0.3.0不要求用户或管理员删除动态，但数据库设计应保留状态字段，便于未来支持隐藏、删除或风控。

## 5. 动态类型
### 5.1 用户动态
用户主动发布的动态。用于讲述自己的故事、记录状态、向天依分享生活。

P0支持：
- 文字动态。
- 用户评论。
- 天依稍后回复。
- 动态作为记忆候选进入memory_writer。

P1支持：
- 图片动态。
- 编辑或删除。
- 更复杂的二级评论。

### 5.2 天依动态
天依主动发布的动态。用于展示天依在world中的行为和状态。

P0支持：
- citywalk完成后发布城市漫步动态。
- 自动学歌成功后发布学歌动态。
- 用户可以对天依动态发表评论。
- 天依可以稍后回复用户对天依动态的评论。

P1支持：
- 更多world任务接入。
- 动态附带更多结构化信息，例如地点、歌曲、心情、关联事件。
- 图片动态。

### 5.3 系统通知
系统或管理员发布的通知。用于公告、维护、版本提醒等。

P0支持：
- 系统通知出现在动态流中。
- 系统通知不进入聊天历史、上下文和记忆。
- 系统通知默认不可评论。

P1支持：
- 管理员在控制台发布系统通知。
- 通知置顶、过期时间、已读统计。

## 6. 核心用户流程
### 6.1 用户查看动态
1. 用户从客户端进入动态入口。
2. 客户端请求最新一批动态。
3. 服务端返回该用户可见的动态，按发布时间从新到旧排序。
4. 用户向下滑动时加载更早动态。
5. 没有更多动态时，页面显示“没有更多动态了”。

### 6.2 用户发布动态
1. 用户点击发布按钮。
2. 用户输入文字，点击发送。
3. 客户端提交动态到服务端。
4. 服务端写入动态，并将该动态标记为待天依处理。
5. 客户端将新动态显示在动态流顶部。
6. 后台任务稍后处理该动态，尝试让天依回复。
7. 若生成天依回复，用户再次进入动态入口时可看到红点提示。

### 6.3 用户评论动态
1. 用户在某条动态下输入评论。
2. 服务端写入评论，并将该评论标记为待天依处理。
3. 如果评论的是用户自己的动态，天依可以稍后回复。
4. 如果评论的是天依动态，天依可以稍后判断是否回复。
5. 其他用户不可看到这条评论。

### 6.4 天依发布world动态
1. world任务完成，例如citywalk或自动学歌。
2. world任务将事件内容交给agent生成动态文案。
3. 动态发布能力写入一条天依动态。
4. 对所有用户可见。
5. 所有用户的动态入口出现未读红点。

### 6.5 系统发布通知
1. 系统或管理员写入系统通知。
2. 所有用户可在动态流中看到该通知。
3. 系统通知不进入记忆，也不进入聊天上下文。

## 7. 未读与红点规则
1. 动态入口需要显示红点，提示用户有未读动态、未读回复或未读系统通知。
2. 外层菜单按钮不显示红点，避免主界面被过度打扰。
3. 用户进入动态页后，应将当前可见的新动态和新回复标记为已读。
4. 以下情况应产生未读：
   - 天依发布新动态。
   - 系统发布新通知。
   - 天依回复用户动态或评论。
5. 用户自己发布的动态和评论不产生自己的未读红点。

## 8. 天依回复规则
后台任务每30分钟检查一次待处理的用户动态和评论。

处理规则：
1. 用户发布的主动态：默认尝试回复。
2. 用户对天依动态的评论：由LLM判断是否需要回复。
3. 用户对自己动态下的补充评论：由LLM判断是否需要回复。
4. 明显不适合回复的内容可以不回复，例如纯表情、重复内容、敏感内容或无实际信息量内容。
5. 天依回复失败时，应记录错误，不应影响用户继续使用动态功能。

回复风格：
1. 回复应比聊天窗口更慢、更完整、更像认真读过动态后的留言。
2. 回复不需要像聊天一样高频互动，避免把评论区变成即时聊天。
3. 回复应能引用动态中的具体内容，体现天依确实看到了用户分享的故事。

## 9. 记忆规则
1. 用户发布的动态应作为记忆候选，复用现有memory_writer判断是否写入记忆。
2. 用户评论应作为记忆候选，复用现有memory_writer判断是否写入记忆。
3. 天依回复不直接写入用户记忆，除非现有memory_writer基于上下文判断需要记录。
4. 天依自己的动态不直接写入用户记忆，但可以作为角色事件或world事件保存。
5. 系统通知明确不进入记忆。
6. 动态记忆写入应带有来源信息，方便未来在控制台追踪其来自动态、评论还是聊天。

## 10. 功能范围
### 10.1 P0范围
P0必须完成以下功能：

服务端：
- 动态表和评论表。
- 动态读写接口。
- 评论读写接口。
- 用户可见性过滤。
- 动态未读状态。
- 天依动态发布能力。
- 天依回复动态和评论的后台任务。
- citywalk完成后发布天依动态（由citywalk模块生成内容）。
- 自动学歌成功后发布天依动态（由song_learning模块生成内容，包括基于歌词的对歌曲的评价）。
- 用户动态和评论接入memory_writer。
- 管理控制台查看所有动态和评论。

App客户端：
- 动态入口。
- 动态流页面。
- 发布文字动态。
- 评论动态。
- 分页加载。
- 下拉刷新。
- 无更多内容提示。
- 动态入口红点。

PC客户端：
- 工具栏或菜单中增加动态入口。
- 打开独立动态窗口。
- 展示动态流。
- 发布文字动态。
- 评论动态。
- 刷新和分页加载。

### 10.2 P1范围
P1可以在P0稳定后继续实现：
- 图片动态。
- 评论的二级跟评。
- 用户编辑或删除动态。
- 管理员发布系统通知。
- 通知置顶和过期时间。
- 更丰富的动态卡片样式。
- 动态关联地点、歌曲、world事件等结构化信息。
- 更细粒度的记忆写入追踪和人工标注。
- 移动端图片预览和多图上传。

### 10.3 暂不做
v0.3.0不做以下内容：
- 用户之间互相查看动态。
- 公开动态广场。
- 点赞、转发、收藏。
- 关注关系。
- 审核后发布。
- 完整内容风控系统。
- 复杂推荐流。

## 11. 服务端功能设计
### 11.1 数据模型
建议至少包含：

动态表：
- `id`
- `author_type`：`user` / `agent` / `system`
- `author_id`
- `owner_user_id`：用户私有动态所属用户；天依动态和系统通知可为空
- `visibility`：`private` / `global`
- `content`
- `image_refs`
- `source_type`：`user_post` / `citywalk` / `song_learned` / `system_notice`
- `source_id`
- `memory_policy`：`candidate` / `disabled`
- `status`：`published` / `hidden` / `deleted`
- `created_at`
- `updated_at`

评论表：
- `id`
- `dynamic_id`
- `author_type`
- `author_id`
- `owner_user_id`
- `parent_comment_id`
- `content`
- `memory_policy`
- `reply_policy`：`pending` / `processed` / `ignored` / `failed`
- `status`
- `created_at`
- `updated_at`

未读表或已读游标：
- `user_id`
- `last_read_dynamic_at`
- `last_read_comment_at`
- `unread_count`
- `updated_at`

### 11.2 模块边界
按现有架构，建议职责如下：

- `system/database`：负责动态和评论的持久化，提供dynamic相关service。
- `system/user_interface`：提供用户侧REST接口和管理员侧接口。
- `agent`：生成天依动态文案、生成天依评论、判断是否需要回复。
- `capabilities`：提供“发布动态/发布评论”这种角色可调用能力，但不直接承载复杂数据库逻辑。
- `world`：在citywalk、自动学歌等任务完成后触发天依动态；定时扫描待处理动态和评论。
- `subconscious`：通过现有memory_writer处理用户动态和评论的记忆写入。
- `observability`：记录动态生成、回复、记忆写入耗时和异常。

### 11.3 用户接口
P0建议接口：
- `GET /dynamics`：获取当前用户可见动态列表。
- `POST /dynamics`：发布用户动态。
- `GET /dynamics/{dynamic_id}/comments`：获取当前用户可见评论。
- `POST /dynamics/{dynamic_id}/comments`：发表评论。
- `GET /dynamics/unread`：获取动态未读状态。
- `POST /dynamics/read`：标记动态已读。

接口必须按当前登录用户过滤可见性，不能把其他用户评论返回给当前用户。

### 11.4 管理员接口
P0建议在控制台增加“动态管理”页面：
- 查看所有动态。
- 查看某条动态下所有评论。
- 按用户、作者类型、来源类型、时间、状态筛选。
- 查看天依回复处理状态和失败原因。
- 查看动态是否进入记忆候选，以及memory_writer处理结果。

P0不要求管理员审核、删除或修改动态。

## 12. App客户端需求
### 12.1 入口
- 在菜单中增加“动态”入口。
- 动态入口显示红点；外层菜单按钮不显示红点。
- 点击入口进入独立动态页面。

### 12.2 动态流页面
- 使用“动态流”而非瀑布流。
- 按时间从新到旧展示。
- 每条动态包含作者、正文、图片区域、发布时间、评论区和评论输入框。
- 页面左上角有返回按钮。
- 页面顶端有bar，双击回到顶部。
- 进入页面时加载最新动态。
- 下拉刷新最新动态。
- 接近底部时自动加载下一页。
- 没有更多内容时显示“没有更多动态了”。

### 12.3 发布动态
- 右下角提供悬浮发布按钮。
- P0支持文字发布。
- 发布成功后，新动态显示在顶部，页面回到顶部。
- 发布失败时提示用户重试。

### 12.4 评论
- 用户可以在动态下发表评论。
- 评论成功后立即显示在当前动态下。
- 若天依稍后回复，动态入口红点提示。

## 13. PC客户端需求
- 在工具栏或菜单中增加“动态”入口。
- 点击后打开独立动态窗口。
- 无返回按钮，关闭窗口即可回到主界面。
- 提供刷新按钮。
- 支持动态流展示、发布文字动态、发表评论和分页加载。
- 动态入口显示红点；外层菜单按钮不显示红点。

## 14. 异常与空状态
客户端需要处理：
- 无动态：显示空状态。
- 网络失败：显示重试按钮。
- 发布失败：保留输入内容，允许重试。
- 评论失败：保留输入内容，允许重试。
- 服务端处理中：可显示“天依稍后会看到”一类的轻提示。

服务端需要处理：
- 天依回复生成失败。
- memory_writer失败。
- world任务发动态失败。
- 动态可见性过滤异常。
- 非法动态或评论ID。

## 15. 埋点与监控
建议记录：
- 动态发布次数。
- 评论发布次数。
- 天依动态生成次数。
- 天依回复成功率和失败率。
- 从用户发布动态到天依回复的耗时。
- 动态触发memory_writer的次数和成功率。
- 动态接口错误率。

这些指标可以后续接入管理控制台。

## 16. 验收标准
P0完成时，应满足：

1. 用户可以在App和PC客户端进入动态流。
2. 用户只能看到自己的动态、天依动态和系统通知，看不到其他用户动态和评论。
3. 用户可以发布文字动态，并在动态流顶部看到。
4. 用户可以评论自己可见的动态。
5. 天依可以在后台稍后回复用户动态或评论。
6. citywalk完成后可以发布一条天依动态。
7. 自动学歌成功后可以发布一条天依动态。
8. 系统通知不进入聊天历史、上下文和记忆。
9. 用户动态和评论会作为记忆候选交给memory_writer。
10. 动态入口在有未读动态或回复时显示红点，外层菜单按钮不显示红点。
11. 管理员可以在控制台查看所有动态和评论。
12. 动态列表分页、刷新、空状态和失败重试可用。

## 17. 风险与待确认问题
1. 天依动态对所有用户可见，但评论对用户隔离，服务端查询必须严格处理可见性，避免隐私泄露。
2. 动态写入记忆可能引入噪声，需要后续在控制台观察memory_writer效果。
3. 每30分钟批处理可能导致回复延迟较大，但符合慢交流定位；后续可根据体验调整周期。
4. 图片动态暂不进入P0，避免文件上传、存储和审核问题拖慢主功能闭环。
5. 管理员暂不删除动态，但数据库保留状态字段，为未来处理异常内容预留空间。
