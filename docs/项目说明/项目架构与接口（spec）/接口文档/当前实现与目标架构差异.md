# 当前实现与目标架构差异

本文档只记录已经从当前源码确认的差异。它不是未来重构的完成声明，也不表示目标 interface 已经存在。

## 差异清单

### 1. 新 Stage 与生产 ChatStream 并存

`src/stage/ChatStage` 已实现 Agent 两接口调度、pending、取消和期限；StageManager 管理绑定与离线回收。生产 `/chat_ws` 仍走旧 ChatStream，尚未切换文本决策 handler。

### 2. 共享 adapter 已独立

`src/adapter/websocket` 通过四个主要接口完成 StageOutput 投递、事件转换和连接绑定。WebSocketService 提供新刺激接入函数；认证、心跳、ACK 和连接维护留在网络层。协议与新链路通过测试 WebSocket 验证。

### 3. Agent 有限门面尚未实现

- **目标**：`agent_runtime.get_agent(character_id)` 返回只暴露少量 interface 的 Agent 门面，stage 和 world 不访问潜意识、能力管理器、数据库或提示词对象。
- **当前**：`get_agent()` 直接返回 `LuoTianyiAgent`；守则示例中的 `handle_stimulus(stimulus, interaction_context)` 尚不存在。
- **当前影响**：调用者能够看到 `LuoTianyiAgent` 的全部公开方法和内部依赖属性。
- **迁移方向**：先增加薄门面并委托给现有实现；用 interface 测试保护行为后，再逐个替换旧调用。

### 4. `AgentRuntime` 仍包含业务编排

- **目标**：`AgentRuntime` 主要负责创建、注册、缓存、查找和生命周期。
- **当前**：除 `get_agent()` 外还公开 `preprocess_chat_event()`、`try_handle_reflex()`、`extract_topic()`、`plan_topic_turn()`、`realize_topic_plan()`、`write_topic_memories()`、`detect_dates_for_topic()` 和 `update_user_profile_by_context()`。
- **迁移方向**：新功能不得继续增加这类方法；相关功能修改时逐步移动到 Agent 门面。

### 5. 调用者仍绕过 Agent 门面

- **目标**：stage、world 和用户接口只调用 Agent 的有限 interface。
- **当前**：
  - stage 通过 `SystemRuntime.agent_runtime` 调用多个业务方法；
  - `topic_replier.py` 直接读取 `SystemRuntime.capabilities.singing`；
  - world 通过 `get_character_runtime()` 取得 `mind`、`capability_manager` 和角色上下文；
  - `GlobalSpeakingWorker` 直接调用 speech 和 singing capability。
- **迁移方向**：先明确 Agent 返回的是“回复内容”还是“待执行动作”，再在一个功能切片内替换，不能只增加一层转发而保留全部旧路径。

### 6. stage 直接依赖 Adapter 和整个 `SystemRuntime`

- **目标**：stage 使用内部事件和窄依赖，不理解 WebSocket 具体类型。
- **当前**：`ChatStream` 和 `ChatStreamManager` 直接依赖 `WebSocketConnection`、`WSEventType`、`ChatResponse` 以及整个 `SystemRuntime`。
- **迁移方向**：把连接发送能力和 Agent 调用能力收敛成 stage 所需的最小 interface；迁移前现有签名仍是当前事实。

### 7. world 获得整个 `SystemRuntime`

- **目标**：world 产生内部刺激；需要持续交互时交给 stage，并只接收任务所需依赖。
- **当前**：`WorldRuntime.wire_dependencies(system_runtime=...)` 把整个运行时交给每个 `WorldTask`，任务可以任意访问数据库、Agent、能力和 stage。
- **迁移方向**：按任务真实需要注入 Agent 门面、事件存储或能力 interface，不一次性重写全部任务。

### 8. `utils` 存在反向业务依赖

- **目标**：`utils` 不依赖 `system/user_interface`，也不理解业务状态。
- **当前**：
  - `utils/llm/client_llm_executor.py` 导入 `WSEventType`；
  - `utils/llm/llm_module.py` 和 `utils/vision/vlm_module.py` 导入系统观测全局入口。
- **迁移方向**：由调用者传入通知和观测 callback/interface；在此之前这些依赖列为已知技术债。

### 9. 仍存在全局取服务入口

当前仍有 `get_system_runtime()`、`get_agent_runtime()`、`get_GCSM()`、`get_database_manager()`、`get_vector_store()`、`get_knowledge_graph()`、`get_global_speaking_worker()` 和 `get_observability_service()` 等全局入口。

开发守则要求新代码优先显式接收依赖，因此这些入口只记录为当前兼容 interface，不应在新模块中继续扩散。

### 10. package 导出与真实实现不一致

- `server/src/system/__init__.py` 声明导出 `ConversationService`，但延迟导入路径是当前不存在的 `src.chat_session.conversation`。
- `server/src/capabilities/__init__.py` 实际导入 `CapabilityManager`，但 `__all__` 中列出未定义的 `CapabilityRegistry`，且没有列出 `CapabilityManager`。
- `server/src/subconscious/__init__.py` 声明导出 `extract_song_entities`，但目标模块没有定义该名称。
- `server/src/agent/__init__.py` 没有导出 `LuoTianyiAgent` 或目标 Agent 门面。

因此本套文档以真实源码和调用点为准，不能把 `__all__` 直接视为可靠接口清单。

### 11. world 与 capabilities 存在反向依赖

`capabilities/singing/singing_manager.py` 当前从 `world.learn_sing_songs.auto_song_learner` 导入 `WishlistManager`。目标方向应由 world 调用 capability，能力模块不应依赖具体 world 任务。

### 12. 电话 stage 仍是占位实现

`CallStreamManager` 当前只保存配置和依赖，启动、停止均为空操作；尚不存在 `CallStream` 当前 interface。电话 PRD 中设计的调用方式不能写成已经实现。

## 已符合目标的部分

- `domain` 基本保持为纯数据类型，没有导入 FastAPI、数据库和具体业务模块。
- `SystemRuntime` 已是主要的创建、连接和关闭位置。
- `agent`、`subconscious`、`capabilities` 已经是不同目录。
- `base` 模块没有创建，符合当前守则。
- WebSocket 输入已经能够先转换为 `Stimulus`，再兼容旧聊天事件。

## 建议迁移顺序

1. 定义并测试 Agent 有限门面。
2. 让一个 stage 调用点改用门面，保留行为不变。
3. 把 stage 与 WebSocket 类型之间的发送/接收能力抽成窄 interface。
4. 按 world 任务逐个替换整个 `SystemRuntime` 注入。
5. 清理 utils 的反向依赖和全局 service locator。
6. `adapter` 已独立；`stage` 的物理目录和生产入口迁移另行处理。
