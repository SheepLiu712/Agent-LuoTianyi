# 开发指引
本文档用于指导开发者如何为本项目贡献代码。本文档主要面向有一定编程基础的开发者，尤其是熟悉Python和Typescript的开发者。

## 技术栈
下面介绍本项目的主要技术栈，供开发者参考：
- **操作系统**：Windows 10/11
- **编程语言**：Python 3.10（桌面客户端与服务器） 与Typescripts（app客户端）
- **Web框架**：FastAPI
- **client UI框架**：PySide6（后续可能降级至PySide5）
- **app 框架**：Expo + React Native + WebView
- **数据库**：sqlite（使用 SQLAlchemy 进行 ORM 操作）
- **向量数据库**：ChromaDB
- **TTS合成**：GPT-SoVITS(轻量化：gsv-tts-lite)
- **公网访问**：使用 sakurafrp 实现内网穿透，支持公网访问


## 客户端架构
桌面客户端与app客户端统一采用以下五层架构：
1. WebSocket层：建立并维护web socket连接，处理web socket发送和接收任务。
2. NetworkClient层：处理具体的网络服务，包括登录、注册、拉取历史等。对话消息通过调用WebSocket暴露的接口实现。
3. MessageProcessor：实际处理用户操作和服务器发包的部分。其中包括MultiMediaProcessor，用于处理音频播放和口型同步。
4. Binder：连接前端UI和MessageProcessor的中间层。
5. GUI：实际绘制前端，将用户输入发回中层，并显示服务器发来的数据。

## 服务端架构
从v0.2版本开始，服务端从「聊天 pipeline 驱动」迁移到「认知运行时驱动」。我们在服务端中明确区分了“角色”和“外部世界”两部分，将用户的交互过程理解为“外部世界”对“角色”的多种刺激方式的其中一种。服务端不仅仅仅是一个聊天 pipeline，同时维护了“角色”的认知运行时，并额外抽象出了“箱庭世界”作为角色生活的环境。

目标 handle 输入边界（SPEC，尚未实现）：stage 直接传入不可变交互事实及取消令牌；Agent 内部按角色和 interaction 管理历史对话、摘要及 Recall 工作上下文，统一管理其临时生命周期。输入快照不持久化，也不通过通用 ID 引用上下文。详见 [handle 输入契约](接口文档/domain/handle-input.md)。现有 ChatStream/ConversationService 等事实接口仍处于迁移期。

### 1. 模块划分
#### 主要对象定义：domain
位置：`server/src/domain`

职责：
1. 定义核心领域对象。
2. 给系统其他模块提供共同语言。

#### 角色心智表意识：agent
位置：`server/src/agent`

职责：
1. 作为角色心智的表意识，提供对用户输入的处理能力。即对给定的用户输入以及潜意识唤起内容进行处理，生成对用户的回复。该模块主要依赖LLM进行处理。例如，根据当前对话的上下文，生成风格化回复。
2. 实现上，提供`LuoTianyiAgent`类作为外界调用的接口。

目前主要实现了以下模块：
- `LuoTianyiAgent`：提供外部世界调用的接口，处理用户输入，生成智能体的响应。其包括主回复模块、潜意识模块、能力模块以及角色档案等。
- `MainChat`：主回复模块，处理用户输入，生成智能体的响应，并解析为项目定义的对象。

#### 角色心智潜意识：subconscious
位置：`server/src/subconscious`

职责：作为角色心智的潜意识，为表意识提供唤起内容。该模块主要依赖LLM进行处理。主要的功能有：
1. 根据用户输入，初步唤起对专有名词的记忆；
2. 根据用户输入，规划记忆检索命令；
3. 管理记忆以及音乐知识；
4. （待实现）管理对用户的好感度、角色的状态，以及角色在对话中的注意力；

目前主要实现了以下对象
- `CharacterSubconscious`：为每个角色提供独立的潜意识实例，管理该角色的记忆、知识以及状态，提供记忆检索和写入，话题规划，重要日期检测等功能；
- `memory`模块：管理记忆的存储、检索和写入。
- `music_knowledge`模块：管理音乐知识的存储、检索和写入。

#### 角色心智运行时：agent_runtime
位置：`server/src/agent_runtime`

职责：为多角色统一管理提供的接口，供外部世界直接调用对应的角色进行响应。

我们在实现时区分了“角色”和“智能体”（Agent）两种对象。“角色”更类似于人设卡片，而“智能体”是对“角色”的一个运行时实例。每个智能体都绑定了一个角色，并且拥有独立的记忆、状态和上下文。

目前其模块包括：
- `CharacterRegistry`：注册和管理所有的角色卡；
- `CharacterRuntime`：为每个角色提供独立的运行时实例，成为智能体；
- `AgentRegistry`：注册和管理所有的智能体；
- `AgentRuntime`：为外部世界提供统一的接口，供外部世界调用对应的智能体进行响应。

实例边界需要特别注意：`AgentRuntime`初始化时会为每个角色创建一个对应的`CharacterRuntime`智能体实例，角色的`LuoTianyiAgent`、`CharacterSubconscious`、反射处理和角色档案都属于该角色自己的运行时状态。`capabilities`不是按角色复制的对象，而是全局所有角色共用的一组能力服务；调用能力时应通过`character_id`、`character_name`、`character_persona`、`speaking_style`等参数选择当前角色，不要把某个角色的可变状态长期写进全局能力实例。

#### 角色能力接口：capabilities
位置：`server/src/capabilities`

职责：提供除了心智之外的，角色应该拥有的与外界交互的能力接口。包括
- 说话：提供TTS语音合成的接口，供角色发声；
- 唱歌：提供唱歌的接口，供角色唱歌；
- 图片理解：提供图片理解的接口，供角色理解图片内容；
- 动态：提供发布角色动态、发布动态评论和生成动态回复的接口，供角色在聊天之外表达和回应；

目前其模块包括：
- `speech`模块：提供TTS语音合成的接口，供角色发声；
- `singing`模块：提供唱歌的接口，供角色唱歌；
- `image_understanding`模块：提供图片理解的接口，供角色理解图片内容；
- `dynamic`模块：提供动态发布和动态回复能力。world任务可以把城市漫步、学会新歌等事件材料交给该能力生成并发布角色动态；后台动态检查任务也通过它生成并写入天依对用户动态或评论的回复。

`capabilities`整体由系统运行时创建一次并全局复用。多角色开发时，能力方法必须显式接收角色标识或角色上下文，而不是依赖单例内部保存的“当前角色”。如果某个能力确实需要角色专属配置，应从`CharacterRuntime`或调用参数中传入，并保证一次调用只影响本次请求。

#### 聊天会话维护：chat_session
位置：`server/src/chat_session`

职责：为每个登录的用户提供独立的聊天会话，维护用户与角色对话的上下文与状态，实现实际会话中的逻辑。

其主要模块包括：
- `ChatSessionManager`，管理所有的聊天会话流，包括文字聊天流和打电话流（暂时未实现）。
- `ChatStreamManager`，管理所有的文字聊天流，包括聊天流的创建，查找，回收等。
- `ChatStream`，为每个用户提供独立的聊天流，维护用户与角色对话的上下文与状态，实现实际会话中的逻辑。位于`chat_session/chat_pipeline`中。

#### 外部世界接口：world
位置：`server/src/world`

职责：
1. 维护外部世界，提供外部世界对角色的接口。
2. 提供世界时钟，可以注册定时任务，在特定的时间会唤起对应的角色进行交互。

其主要模块包括：
- `world_runtime`模块，外部世界接口的运行时，注册所有的任务以及世界时钟。
- `world_clock`模块，提供世界时钟的接口，供外部世界注册定时任务。

目前已经注册的定时任务包括：
- `bili_event_update`：每6小时检查b站动态是否更新，如果动态中有新的活动，加入到角色的日程中；
- `citywalk`：每天有10%的概率找个地方旅游，进行一次城市漫步，并生成相应的记忆；
- `get_new_songs`：每天检查VCPedia是否有新的歌曲，如果有新的就加入知识库。
- `learn_sing_songs`：每天检查用户是否有想让角色唱的歌，如果有，就尝试学习这些歌曲。
- `event_clean_up`：每天清理过期的事件。
- `dynamic_interaction`：周期检查待处理的用户动态和评论，触发角色回复，并把用户动态、用户评论送入记忆写入候选。
- `proactive_topic`：每5分钟检查所有对话流，如果沉默且有需要提醒的事件，就主动发言。

拓展规范：每个任务应该继承自`WorldTask`，提供对应的时钟配置，并实现`run_once`方法。

#### 系统运行管理：system
位置：`server/src/system`

职责：提供了整个服务端系统的运行管理支持，其主要职责如下
- 提供数据库服务，对应`database`模块；
- 提供暴露给管理员的服务，对应`admin`模块；
- 提供埋点接口，对应`observability`模块；
- 提供暴露给用户的网络服务的具体实现，对应`user_interface`模块；
- 提供服务端的运行时管理，对应`system_runtime`模块；

#### 工具模块：utils
位置：`server/src/utils`

职责：提供了整个服务端系统的工具支持，其主要职责如下
- 提供了LLM调用的工具，对应`llm`模块；
- 提供了视觉处理的工具，对应`vision`模块；
- 提供了音频处理的工具，对应`audio_processor.py`；
- 提供了常用的工具函数，对应`helper.py`；
- 提供了logger的工具，对应`logger.py`；
- 其它工具，如农历工具库`lunar.py`

### 2. 功能应该放在哪里
开发新功能时，最常见的问题不是“怎么写”，而是“应该写到哪个模块里”。本项目的判断原则是：先判断这个功能属于角色、外部世界、会话过程、长期记忆，还是系统基础设施，再选择对应目录。

| 功能类型 | 应放位置 | 判断标准 | 示例 |
| --- | --- | --- | --- |
| 领域对象、事件对象、跨模块共享的数据结构 | `server/src/domain` | 多个模块都需要使用同一种业务对象，且它不是某个具体模块的私有实现 | 记忆对象、会话消息、角色状态、世界事件 |
| 角色的对外接口；角色最终生成的风格化回复 | `server/src/agent` | 这部分逻辑直接决定角色“怎么想、怎么说、怎么行动” | 主回复、回复解析、角色人设提示词组装 |
| 长期记忆、用户画像、注意力、知识召回 | `server/src/subconscious` | 这部分内容不是直接回复用户，而是为回复提供被唤起的背景 | 记忆检索、记忆写入、用户画像更新、歌曲知识检索 |
| 角色可以使用的具体能力 | `server/src/capabilities` | 这是一个可被角色调用的能力，不负责定时调度，也不负责维护外部世界状态 | TTS、唱歌、图片理解、写日记文本、发布动态、回复动态 |
| 外部世界的周期任务、主动任务、环境事件 | `server/src/world` | 这个功能像是“世界里发生的事情”，通常由时钟或后台任务触发 | citywalk、B站动态更新、自动学歌、动态检查、浏览小红书 |
| 用户连接、消息队列、topic聚合、回复发送 | `server/src/chat_session` | 这部分逻辑只关心一次用户会话如何被拆分、排队、处理和返回 | WebSocket消息进入后的聊天流、未读消息缓冲、topic规划 |
| 数据库、运行时生命周期、admin、观测、用户接口 | `server/src/system` | 这是服务端基础设施，不属于某个角色能力或世界任务 | SystemRuntime、DatabaseService、admin接口、监控埋点 |
| 纯工具函数或第三方服务薄封装 | `server/src/utils` | 不带明确业务归属，可以被多个模块复用 | LLM调用工具、日志工具、音频处理工具、农历工具 |

有些功能会横跨多个模块，此时应该把“调度”和“能力”拆开，而不是强行塞进同一个目录。例如：

- 增加“浏览小红书”：如果是角色每天随机浏览外部平台、发现内容并形成世界事件，主流程应该放在`world/xiaohongshu`。如果其中有通用的小红书搜索/读取客户端，可以作为该world任务的内部实现；如果将来多个模块都要调用，再抽成独立服务或能力。
- 增加“动态”：发布动态和回复动态属于角色能力，适合放在`capabilities/dynamic`；检查哪些动态或评论需要处理、什么时候触发回复和记忆写入，属于后台世界任务，应放在`world/dynamic_interaction`。
- 增加一种记忆检索策略：检索、排序、写入、用户画像相关逻辑应放在`subconscious`；如果只是为了某次对话决定何时触发检索，则触发编排可以在`agent`或`chat_session`。
- 增加一个新的HTTP接口：接口声明和请求响应模型属于`system/user_interface`，真正的业务逻辑应该继续放回对应的业务模块，避免把业务都写进接口层。

可以用下面的规则快速判断：
1. 是否是后台定时或外部环境变化？是，则优先放在`world`。
2. 是否是角色能主动使用的一种能力？是，则优先放在`capabilities`。
3. 是否是长期记忆、画像或知识召回？是，则优先放在`subconscious`。
4. 是否直接决定角色回复内容和行为编排？是，则优先放在`agent`。
5. 是否只是会话排队、topic切分、连接管理？是，则优先放在`chat_session`。
6. 是否是数据库、配置、admin、运行时启动停止？是，则优先放在`system`。

### 3. 项目目录
服务端主要目录如下：

```text
server/
├─ server_main.py              # FastAPI入口，注册WebSocket、REST接口和lifespan
├─ res/admin_ui/               # 管理控制台前端
├─ config/                     # 服务端配置文件
├─ data/                       # 运行时数据、诊断数据、数据库等
├─ logs/                       # 服务端日志
├─ res/                        # 模型、音频、歌曲、知识库等资源文件
├─ scripts/                    # 运维、诊断、数据修复脚本
├─ tests/                      # 服务端测试
└─ src/
   ├─ domain/                  # 领域对象和跨模块共享类型
   ├─ agent/                   # 角色表意识：主回复、提示词组装、回复解析
   ├─ subconscious/            # 角色潜意识：记忆、画像、注意力、知识召回
   ├─ agent_runtime/           # 多角色、多智能体运行时
   ├─ capabilities/            # 角色能力：speech、singing、image_understanding、dynamic
   ├─ chat_session/            # 用户聊天会话、ChatStream、topic pipeline
   ├─ world/                   # 外部世界、世界时钟、周期任务
   ├─ system/                  # 系统运行时、数据库、用户接口、admin、监控
   └─ utils/                   # 通用工具和第三方服务薄封装
```

一些重要入口：
- `server_main.py`：服务端进程入口。这里应该只做FastAPI注册、生命周期托管和少量顶层路由，不应该塞入具体业务逻辑。
- `src/system/system_runtime.py`：服务端运行时容器，负责初始化和关闭长生命周期服务。
- `src/system/user_interface/`：面向用户和管理员的接口实现。接口层负责校验请求、调用服务、返回结果，不负责承载复杂业务。
- `src/chat_session/chat_pipeline/chat_stream.py`：文字聊天流入口。用户消息进入后，会在这里进入ingress、topic规划和回复流程。
- `src/agent/luotianyi_agent.py`：角色智能体的主要门面。外部模块需要角色处理刺激或生成回复时，应优先通过这里进入。
- `src/world/world_runtime.py`和`src/world/world_clock.py`：外部世界任务注册、启动和调度入口。

目录使用时需要注意：
- 不要把新的业务逻辑直接写进`server_main.py`。如果需要暴露接口，在`system/user_interface`添加接口，再调用对应业务模块。
- 不要让`chat_session`承担角色思考逻辑。它负责会话流控，角色怎么想应该交给`agent`和`subconscious`。
- 不要让`world`直接变成“万能后台任务目录”。只有外部世界、周期任务、主动事件适合放在这里。
- 不要让`utils`承载业务语义。如果一个工具开始理解“记忆”“歌曲”“角色状态”，它通常应该移动到对应业务模块。

### 4. 消息流动
服务端有三条最重要的消息流：用户聊天流、角色能力调用流、外部世界任务流。

#### 用户文字聊天流
用户通过WebSocket发送消息后，服务端大致按以下顺序处理：

```text
client/app
  -> /chat_ws
  -> websocket_service 鉴权、心跳、事件封装
  -> ChatSessionManager / ChatStreamManager 获取用户聊天流
  -> ChatStream.ingress_queue
  -> ingress_helper 处理图片、歌曲实体、重要日期等预处理
  -> unread_store / listen_timer 等待用户输入形成完整topic
  -> topic_planner 将用户消息整理为topic
  -> topic_replier 调用角色生成回复
  -> LuoTianyiAgent
  -> CharacterSubconscious 检索记忆、画像、知识
  -> MainChat 生成并解析角色回复
  -> capabilities.speech / capabilities.singing 等能力
  -> websocket_service 将文本、状态、音频包发送给客户端
```

这条链路里，各模块的职责边界是：
- `websocket_service`负责网络事件格式，不理解角色业务。
- `ChatStream`负责排队、等待、拆topic和调度回复，不负责写角色思考逻辑。
- `topic_planner`负责把用户连续输入整理为可回复的话题。
- `topic_replier`负责把topic交给角色，并处理回复发送、TTS、异步反思等后续动作。
- `LuoTianyiAgent`负责角色层面的统一编排。
- `CharacterSubconscious`负责给回复提供记忆、知识和画像背景。
- `MainChat`负责最终回复生成和结构化解析。

#### 图片、唱歌和TTS能力流
能力调用一般由`agent`或`topic_replier`触发，但具体能力实现应留在`capabilities`中。

```text
角色需要看图
  -> capabilities.image_understanding
  -> VLM生成图片描述
  -> 描述回到聊天上下文或角色回复逻辑
```

```text
角色需要唱歌
  -> capabilities.singing
  -> 匹配歌曲和歌词片段
  -> 找到歌曲则发送唱歌事件
  -> 找不到歌曲则进入角色wishlist
  -> world.learn_sing_songs 后台学习歌曲
```

```text
角色需要说话
  -> GlobalSpeakingWorker 排队
  -> capabilities.speech
  -> GPT-SoVITS生成音频流
  -> websocket_service发送音频包
```

```text
角色需要发布或回复动态
  -> CharacterRuntime传入角色ID和角色上下文
  -> capabilities.dynamic生成动态文案或评论回复
  -> system.database.dynamic_store写入动态或评论
  -> 客户端通过动态REST接口拉取并显示
```

TTS需要特别注意：用于界面显示的文本和用于语音合成的文本可能不同。显示文本应保留在回复对象中，语音合成应使用清理后的`sound_content`，最终由全局说话队列送入`speech`能力。

#### 外部世界任务流
外部世界任务不由用户消息直接触发，而是由世界时钟或后台任务触发：

```text
SystemRuntime启动
  -> WorldRuntime启动
  -> WorldClock注册任务
  -> WorldTask.run_once
  -> 访问外部服务或生成世界事件
  -> 写入database / event_store / memory
  -> 必要时通过AgentRuntime唤起角色
```

例如：
- `citywalk`：随机决定是否出行，调用地图服务，生成城市漫步事件和相关记忆。
- `bili_event_updater`：定时检查B站动态，把新活动写入事件系统。
- `learn_sing_songs`：读取角色wishlist，尝试下载和处理歌曲资源，成功后更新角色歌曲库。
- `dynamic_interaction`：检查待回复、待记忆写入的动态和评论，通过角色运行时与动态能力生成回复并写入结果。
- `proactive_topic`：检查会话是否沉默，并在合适时机主动发起话题。

写新的world任务时，应该继承`WorldTask`，实现`run_once`，并在`world_runtime`中注册。任务内部可以调用数据库、LLM、角色运行时或能力模块，但应保持职责清楚：`world`负责“什么时候发生、外部发生了什么”，具体的角色能力仍应放在`capabilities`，长期记忆和画像仍应交给`subconscious`。
