# 如何为项目出一份力？
目前项目非常缺人！欢迎所有朋友为项目出一份力，只要你：
- 熟悉Python/Typescript/Unity编程，或者有其它一技之长；
- 认可本项目理念；
- 希望为项目做出贡献/锻炼自己的能力。

你就可以尝试为项目贡献代码！

## 关于AI工具使用
⚠警告：我们注意到中文Vocaloid社区对AI生成内容的极度敏感。在社区共识改变之前，我们**不会**向项目中引入：①AI生成的美术作品；②AI创作的音乐。因此，如果你想为项目贡献美术资源或者音乐资源，请确保这些资源不是由AI生成的。另外，你设计的功能不应引入 AI 生成美术作品或 AI 创作音乐的能力。但以下AI使用方式是可接受的：
- 使用LLM进行文本生成，例如对话回复、记忆管理、上下文压缩等；
- 使用开源的语音合成模型进行TTS合成，例如GPT-SoVITS。
- 使用AI辅助编程工具（如GitHub Copilot）进行代码编写，但核心逻辑和设计需要由开发者完成。
- 所有的判别式模型，例如人物识别、术语提取、情感分类等。所有不生成新内容的生成式模型（如伴奏分离）。
- 所有非神经网络的算法。

## 如何贡献代码
你可以用常用的方式贡献代码：
1. 将项目fork到你自己的目录；
2. 创建feat分支或bugfix分支；
3. 实现功能；
4. 提交Pull request，等待作者和协作者审核
5. 完成贡献！

在当下，AI辅助编程已经成为主流的编程方式。我们鼓励开发者使用AI辅助编程工具实现功能的具体细节，但提交者需要能解释、调试并维护由 AI 辅助生成的代码。

对开发者，我希望你能做到：
- 明确自己所需要开发的功能是什么，希望实现什么样的效果；
- 自己（或与AI共同）确定实现这一功能时的框架、逻辑，以及可能模块的编排；
- 检查功能与当前框架是否冲突，是否需要修改现有模块的接口或逻辑；
- 代码功能应尽量提供单元测试；如果不适合写单元测试，应在 PR 中说明验证方式。；

在尝试提交Pull request时，你应该注意：
- 你的pull request应该专注于你想要实现的功能，并且只包含一个功能。
- pull request的修改量不应该太大，对于特别大的功能，应该先与作者沟通，然后逐步提交。原则上业务代码修改不超过 1000 行；如果包含资源、生成文件或大规模迁移，应提前说明。
- 在你的pr中应该包含：
  - 功能的描述；
  - 功能的实现逻辑（不是你具体实现了哪些模块，而是用自然语言描述你的想法）；
  - 功能所涉及到的模块，以及你对这些模块的修改；
  - 单元测试；
  - 功能的使用示例（如果是UI功能，应该包含截图或录屏）；

在编写代码时，你应该遵守以下规范：
- 代码风格：遵循PEP8规范，但我们也没这么严格，建议以下几条重点遵循：
  - 变量、函数名应使用小写字母，单词间用下划线分隔。类名采用首字母大写的驼峰命名法。常量使用全大写字母，单词间用下划线分隔。
  - 导入总是放在文件的顶部，紧随模块注释和文档字符串之后，以及模块全局变量和常量之前导入应按以下顺序：官方库、第三方库、本地库。建议使用绝对导入，但如果是同一目录下的模块，可以使用相对导入。
  - 空格等问题：可以使用标准化的代码格式化工具（如black）进行格式化，或者使用IDE自带的格式化工具。
- 注释与类型提示：
  - “公共类、公共函数和复杂逻辑应有 docstring 或必要注释，描述其功能、参数和返回值。
  - 对于复杂的逻辑，应该在代码中添加必要的注释，解释为什么这样做，而不仅仅是做了什么。
  - 尽量使用类型提示（type hints），以提高代码的可读性和可维护性。至少函数的参数和返回值应该有类型提示。（有时候，我们只需要类型提示，但不需要完整地导入这个模块，此时我会倾向于使用从`typing`导入`TYPE_CHECKING`来实现）

在你提交之前，请记得检查：
- 确认功能放在符合架构边界的位置；
- 运行相关测试；
- 如果修改服务端，优先使用 lty conda 环境验证；
- 如果没有测试，说明手动验证方式；
- 确认【没有】提交密钥、cookie、credential、日志和临时文件。

## 还有其他贡献方式
我们也欢迎你为项目贡献以下内容：
- 美术资源：如果你愿意为项目提供美术资源，绘制角色的模型或服装，欢迎与我们联系；
- 文档：如果你发现文档中有不清楚的地方，或者有更好的表达方式，欢迎提交PR；
- 测试：如果你发现项目中有bug，或者有更好的测试用例，欢迎提交PR；
