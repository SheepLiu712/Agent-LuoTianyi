# 开发守则

本文档规定项目开发时必须遵守的架构和流程。我们的目标不是增加工作量，而是让开发更加高效、合作更加顺利、并保证开发者产出可靠的代码。

## 人与AI的行为边界
在开发本项目时，人和AI负责的部分区分如下：
1. 人类必须准确描述产品目标、使用场景和不可接受的结果，审查并确认功能的验收标准。目标或验收标准有歧义时，先讨论清楚再把它当作开发依据。
2. AI可以起草和修改业务代码、测试及项目文档，包括spec和代码地图；人类必须完全理解AI产出的文档与代码。人类对产品目标、验收结论和最终交付负责。
3. spec可以由人类和AI共同完成。模块边界、跨模块契约、接口和技术选型可以在检查现有实现后提出并讨论；完整spec须经过非作者的其他开发者审核，才可作为后续交付的依据。

## 项目开发规范
### 代码风格标准
当前代码执行的风格检查主要检查server部分，规则为：
- 导入与语法问题（E4/E7/E9）；
- Pyflakes（F）；
- 导入排序（I）；
- 行尾和空白字符（W291/W292/W293）；
- 无效转义（W605）；
- 超过 120 字符的行（E501）；
- 函数复杂度超过 10（C901）。

默认使用Black进行代码格式化，行宽为 120 字符。

app客户端使用Expo 的默认规则。

当前在提交时尚未配置 pre-commit 钩子，AI 应该在生成完毕后执行一次检查。

### 文档管理
开发者应该关注以下几个文档：
- [代码地图](./代码地图.md)：介绍项目目录结构、模块职责、关键调用链和依赖关系。
- [开发守则](./开发守则.md)：介绍项目开发流程与规范。
- [TODO](./TODO.md)：记录当前计划开发的功能和改进。
- 模板中的
  - [spec文档模板](./spec文档模板.md)：介绍如何编写功能spec文档；
- 开发进程文档，保留了当前正在开发的功能的spec文档。

项目库长期维护《代码地图》《开发守则》《TODO》和模板目录。开发进程文档仅保留当前正在开发的功能的spec文档，对应的工单使用GitHub Issue管理。功能完成后，按下述流程在`dev`上单独提交删除已完成的spec；持久有效的行为约束由测试承载。

### 功能实现设计哲学
按照以下原则设计某一功能的实现：
1. 遵循现有架构：参考[代码地图](./代码地图.md)的各个模块职责和调用关系，根据现有模块边界划分功能实现的各个部分的归属。
2. 最小实现原则：任意一个功能立项和实现时
   1. 尽量不修改现有模块的接口和行为；
   2. 选择能实现需求的最小范围的改动；不为未明确的需求或者可能的服务失效情况而过度设计；
   3. 根据未来可能的方向可以预留接口的兼容性，但必须明确该功能未来会加入。
3. 深模块原则：一个接口的调用方只需要学习少量、稳定的知识，复杂实现都留在模块内部。
4. 高内聚低耦合原则：模块内部的功能紧密相关，模块之间的依赖尽量少。

验收时，人类审查可观察的触发条件、结果和边界；具体测试输入、预期输出及验证方法可以由AI提出。提交交付时，以相关测试证明本次承诺的验收标准已经满足。

### 开发管理原则
在具体开发时，我们遵循以下原则：
1. 产品目标和经审查的验收标准指导开发。完整spec可以由人类或AI起草、共同修订，但须由非作者开发者审核；不要求人类独自撰写文档。
2. 工单以能够独立说明交付结果、验收范围和影响边界的工作为单位。一个工单可以包含多个紧密相关的行为场景和跨模块修改，不按文件、模块或测试种类机械拆分；大版本的一个feat可以拆成多个工单和PR，小feat也可以只用一个工单和PR。
3. 不规定先写测试还是先写实现。提交PR前补齐能够证明本次交付验收标准的测试，运行受影响的测试范围并记录结果；不要求每个feat都完成全量回归或让仓库所有测试通过。相关验收测试失败时，不得宣称该范围已交付；无关失败、跳过及未验证范围须如实说明。
4. 人类负责确认产品目标和验收标准，并在最终交付时理解关键行为、边界和验证证据；具体实现和文档可以由AI完成。

## 开发流程

### 01：新特性开发
开发新功能时，使用以下流程：
1. 项目负责人准确描述产品目标与场景；人类和AI共同形成包含用户故事、验收标准、模块归属、接口、失败与边界情况的完整spec。
2. 根据feat大小建立GitHub Issue。每个工单写明本次交付结果、对应的spec验收标准、影响边界与依赖；可以覆盖几个相关场景，但不能大到无法在一个PR中解释改动和验证证据。一个大feat可由多个工单和PR完成，不为每个工单重复编写切片spec。每一个小的feat应该可以被验收。
3. 小feat可从`dev`建立`feat/<功能名>`分支，用一个PR交付。大feat可使用特性开发分支，将各工单的PR合入该分支，最后通过集成PR合入`dev`；不要求不同工单必须由不同开发者完成，也不强制一个feat只有一个PR。
4. 实现与测试可按实际需要排序。每个交付PR提交前，应补齐并运行证明其承诺验收范围的测试，说明结果、相关跳过或失败及未验证范围。审核者检查实际行为、架构边界和证据；不以全量回归测试通过作为所有PR的前提。
5. 功能的实现PR审核通过并合入`dev`、其验收标准均有测试证据后，关闭完成的功能工单，新增一个清理Issue，并在`dev`上用单独提交删除已完成的spec。删除spec前，确认持久有效的行为约束已由测试承载。

### 02：发布
发布时，将dev分支普通合入master分支，并打上版本号标签，发布release版本。

### 03：Bug修复
明确影响用户体验、且被项目负责人决定为热修复的Bug，执行热修复流程；其他Bug执行普通修复流程。是否在生产环境发现，不单独决定修复类型。

在热修复时，使用以下流程：
1. 从`master`分支拉出`hotfix/<bug名>`分支；
2. 定位Bug，确定触发条件、期望结果和受影响范围；
3. 修复Bug，并在提交PR前补充和运行证明修复有效的相关测试；不要求全量测试通过；
4. 提交PR进行代码审查和测试验证。提交PR的说明文档中，需要说明触发条件、被违反的不变量、根因、修复点及验证结果。
5. 通过后合入`master`分支，并打上版本号标签，部署到生产环境。
6. 将`hotfix/<bug名>`分支合入`dev`分支，确保开发环境也修复了该Bug。如果当前的特性开发分支中也包含该Bug，则将`hotfix/<bug名>`分支合入特性开发分支。

在普通Bug修复时，使用以下流程：
1. 从`dev`分支拉出`bugfix/<bug名>`分支；
2. 定位Bug，确定触发条件、期望结果和受影响范围；
3. 修复Bug，并在提交PR前补充和运行证明修复有效的相关测试；不要求全量测试通过；
4. 提交PR进行代码审查和测试验证。提交PR的说明文档中，需要说明触发条件、被违反的不变量、根因、修复点及验证结果。
5. 通过后合入`dev`分支。如果当前的特性开发分支中也包含该Bug，则将`bugfix/<bug名>`分支合入特性开发分支。

### PR提交规范
对于非仓库维护者的开发者，所提交的PR必须与对应的、已经由仓库维护者认可的（被标记为should be solved的）GitHub Issue关联。

一个PR应该只包含一个功能点的改动，若一个PR包含多个功能点的改动，应拆分为多个PR。

提交PR时，若是涉及代码修改的，必须使用[PR描述模板](./模板/pr描述模板.md)撰写PR描述文档，说明本次PR的目的、改动内容、改动范围、关键调用链和验证方法。撰写完成后应该自查是否符合规范，是否可以进一步打磨文档，再提交PR。

不满足上述要求的PR将被直接关闭，并要求开发者重新提交符合要求的PR。

### PR审查规范
PR审查者应该首先根据PR描述模板的要求，检查PR描述是否完整、准确地反映了本次PR的目的、改动内容、改动范围、关键调用链和验证方法。若PR描述不完整或不准确，审查者应要求开发者补充或修改PR描述。

随后，审查者应该使用`code-review`技能，分别对代码的STANDARD和SPEC两轴进行审查。该技能可以从[matt skill](https://github.com/mattpocock/skills/tree/main/skills/engineering/code-review)中学习。STANDARD参照“项目开发规范”一节的约定，SPEC根据该功能对应的SPEC文档或issue中的描述。所有的发现的SPEC问题应该有充足的证据证明这一问题可以在实际运行时发生。

PR审查结果使用[pr审查结论模板](./模板/pr审查结论模板.md)撰写，并提交PR回复。若有问题，审查者应要求开发者修改PR并重新提交。若超过3次PR审查仍未通过，应将此PR汇报给项目负责人，由项目负责人组织讨论决定是否继续审查或关闭PR，并考虑PR提交者和审查者的能力和经验是否符合要求。
