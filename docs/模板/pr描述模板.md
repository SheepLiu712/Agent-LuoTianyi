# PR描述模板
本文档供涉及代码改动的PR使用，帮助开发者在提交PR时，清晰、准确地描述本次PR的目的和改动。

无论由开发者直接撰写，还是由人工智能（AI）起草，均须遵守本模板。以下示例仅用于说明写法，不代表当前代码的实际行为；撰写时须根据本次改动核实，不得直接套用示例中的功能、实现和验证结论。

## 标题
根据本次PR的内容，简要描述本次PR的目的和改动，两个部分缺一不可。

一个PR应围绕能够独立说明、独立验收的交付目标组织改动。若难以用一句话概括目的和改动，应检查是否混入了彼此独立的工作，并据此拆分；不能仅凭句子长短判断是否需要拆分。为完成同一用户目标所必需的跨模块、跨客户端改动，可以在同一个PR中交付。

下面是一些标题的例子：
1. 修复了Issue #1234 中的登录错误，增加了登录失败的提示信息
2. 根据Issue #5678 的需求，为语音通话的响铃界面增加了《心印》作为铃声。
3. 针对将语音通话迁移至使用 omni-realtime 模型的方案，设计了新的模块接口与实现方案。



## 正文
正文应该使用准确、简洁的中文工程语言写作，以不了解关联讨论的初级工程师或研究生能够理解为准则。优先使用常用表达，只在有助于准确说明改动时使用专业术语。

描述改动时，应使用完整句子，明确说明执行主体、动作、操作对象和必要的触发条件。列表中的每一项也应表达完整意思。避免用连续的名词、斜杠或含义不明的简称代替行为说明；判断表达是否清楚，不以词语字数为依据。

例如：

- 不清楚：“服务端：协议读取、签署、登录门禁。”
- 清楚：“服务端新增了读取用户协议和提交签署记录的接口，并在用户登录时检查其是否已签署当前要求的协议版本。”

术语和英文缩写须在首次出现时用中文解释，不能只展开英文全称。代码名称应与源码中的英文标识符保持一致，并使用行内代码格式；仅在帮助理解改动或定位实现时使用。首次提到函数、类、模块或接口时，应说明其定义位置、职责以及与本次改动的关系。可以使用术语表，但不得将必要的解释推迟到使用之后。

正文必须能够独立说明本次交付。审查者应在不打开关联Issue（问题或需求工单）、PR（合并请求）、spec（功能规格说明）和源代码的情况下，理解为什么改、改后有什么变化、实现为什么有效，以及交付到什么程度。外部链接用于提供依据和详细资料，不得替代必要说明。引用验收标准编号时，须同时概述其具体要求。

正文由以下几个部分构成，下面分别说明其内容和写作要求。

### PR概述
在本节说明PR的出发点，以及PR的主要改动内容。

若PR源于某个Issue，应说明其编号、标题和具体需求，不能仅列出引用链接。若该PR是较大需求的一部分，应说明整体目标、此前已完成的部分、本次交付的部分及尚未完成的部分。涉及其他PR时，应明确依赖关系及其是否已合入。

用用户或开发者能够观察到的行为概括主要变化，必要时分条列举。围绕同一交付目标的多个相关场景可以一并说明；能够独立交付和验收的无关功能应拆分为多个PR。说明本次交付的边界，不把依赖项、计划工作或尚未验证的行为写成已完成结果。

例如：“本次改动要求用户在登录前签署当前版本的用户协议。服务端负责检查签署状态，桌面端和移动端负责展示协议并引导用户签署。本次不包含历史账号的人工补签。”比“承接某PR，完成跨端协议流程”更容易理解。

### 术语表（可选）
术语解释是必需的，术语表只是可选的组织形式。术语较少时，在首次出现处解释即可；需要反复使用时，可以集中列入本节，但概述中已经使用的术语仍须在概述中解释。

专业术语应说明其在当前场景中的含义。例如，TOCTOU（检查时与使用时状态不一致的问题）在凭据校验场景中，可以表现为：“请求通过身份检查后、写入签署记录前，用户重置了密码，导致之前通过检查的凭据已经失效。”

代码名称除了给出定义位置和职责，还应解释为什么与本次改动有关。仅列出类名、文件路径或英文全称，不能代替解释。没有必要使用的代码名称应省略。

### 改动的动机
详细说明本次PR提交的动机。若修复缺陷，应说明触发条件、期望结果、实际结果、影响及导致问题的原因；原因尚未确认时，应明确说明，不能把推测写成事实。若实现新功能，应说明需求来源、使用场景，以及现有行为为什么不能满足需求。

不能仅写“根据Issue #123实现需求”。应概述该需求，使审查者不打开工单也能理解改动的必要性。本节解释问题和原因，不必重复概述中的交付清单。

### 实现思路
说明本次改动如何解决上述问题，保留理解方案所必需的机制，不必逐行解释代码。至少回答以下问题：

1. 原来的处理方式为什么不能满足需求？
2. 本次在哪个环节改变了处理方式，关键步骤是什么？
3. 这些步骤为什么能够解决问题？若依赖执行顺序、数据库事务或并发控制，应说明其必要性。

例如，仅写“在同一事务中再次校验凭据”不足以解释方案。应结合实际实现说明：“原流程只在请求开始时检查身份凭据，写入签署记录前凭据可能已经失效。新流程在同一个数据库写事务中重新检查凭据并写入签署记录，使检查结果与写入操作之间不会插入另一个使凭据失效的数据库写操作；检查不通过时拒绝写入。”只有实现确实提供该保证时，才能这样表述。

### 改动说明
#### 改动范围
按行为或职责组织说明，交代各模块承担了什么处理，以及新增、修改、删除了哪些相关接口。文件路径用于定位实现，不能代替行为说明，也不必罗列所有改动文件。

若调用流程发生变化，应说明修改前后的差异；若数据结构发生变化，应说明变化内容及其对数据读写的影响。涉及现有客户端兼容性或数据库迁移时，应说明实际影响。明确与交付目标相关但本次未覆盖的范围，避免使用“完成全流程”等超出证据的表述。

#### 关键调用链
说明与本次改动直接相关的关键调用链：从用户操作、外部请求或任务触发开始，解释各步骤的作用，并以用户或开发者能够观察到的结果结束。不得只列出函数名称；仅在必要步骤附上代码位置，不必展开无关的底层调用。

例如：“用户点击签署 → 客户端提交协议版本和身份凭据 → 服务端检查凭据及协议版本并保存签署记录 → 客户端显示签署成功，用户可继续登录。”若存在影响验收的拒绝或失败分支，也应说明触发条件和结果。

没有相关调用链，或本次未改变调用流程时，可以注明不适用或流程未变，并说明原因，不为填充章节而罗列代码。

### 验证方法
说明每项主要交付如何验证，以及实际执行结果。测试应验证用户或开发者能够感知的行为；不要求为填写模板新增无意义的测试。验证说明应覆盖：

1. 验证场景与对应的交付要求。
2. 测试条件、环境、输入或操作步骤。
3. 预期结果和实际结果。
4. 可复现的执行命令、测试文件位置，或截图、录屏等证据。

使用自动化测试时，应解释测试验证了什么行为，不能只列文件名或通过数量。例如，应说明“使用未签署当前协议的账号登录，服务端拒绝登录并返回需要签署协议的提示”，再给出测试位置和执行结果。

对于自动化测试不足以证明的界面效果或设备行为，应补充截图、录屏或人工操作记录，并说明环境、操作和观察结果。

如实列出相关失败、跳过、尚未执行的验证及其影响；未执行的验证只能写为计划，不能写为通过。正文须保留验证结论和主要限制，详细日志可以链接提供。不得仅用测试通过数量证明功能已经完成。

提交前，请以不了解关联讨论的审查者为读者自查：仅凭正文，能否说明为什么改、改后有什么变化、实现为什么有效、验证了什么、还有什么未完成？若必须打开链接或阅读代码才能回答，应补充正文。各节篇幅按改动复杂程度安排，不重复堆砌相同内容；不适用的内容应简要说明原因。
