# PR 审查

本技能是 AI 审查本项目合并请求（PR）的唯一流程标准。审查期间只读被审改动。项目规范见[《开发守则》](../../../开发守则.md)，报告必须使用 [PR 审查结论模板](../../pr审查结论模板.md)。

## 固定审查范围

1. 记录目标分支及其完整提交标识、本轮被审提交的完整标识。复审时记录上轮提交，核对上轮发现。若 PR 依赖前置 PR，只检查本次增量并说明依赖。文件行号、链接及验证结果均对应本轮版本。
2. 按 [PR 描述模板](../../pr描述模板.md)核对目的、改动内容、范围、关键调用链和验证方法。结合实际差异判断描述是否准确；缺失或不符时指出作者需补充的内容。需求有歧义时，列出需要确认的具体行为。

## 审查实现与验证证据

使用仓库内的 [code-review 双轴审查方法](../code-review/SKILL.md)，分别检查规范符合性（STANDARD）和需求符合性（SPEC）。前者以《开发守则》的“项目开发规范”为依据，后者以关联工单或功能规格说明中已确认的验收要求为依据。认定运行时缺陷须给出真实入口、触发条件及用户或开发者可观察的后果。对各专项的发现核对原始差异和依据，合并重复问题，注明涉及的审查方面。

按项目指定环境运行与改动有关的检查，记录命令、实际输出和未验证范围；门禁按日志判定时应核对日志。高影响问题应尽可能用最小实验复核。区分作者提供的结果、本轮实测、静态可证和无法判定的事项。复核推翻原判断时撤回该项并说明依据。

## 审查关键测试预期

先比较测试差异，包括删除、跳过、放宽断言，以及通过测试数据或模拟对象间接改变的预期。未修改的既有测试继续作为回归基线。只有交付目标明确改变既有行为时，才可同步调整测试并说明契约变更依据；否则要求恢复原有保证。

对本次新增或修改、用作交付证据的关键预期，先写清触发条件和用户或开发者应观察到的行为，再核对三项：

1. **预期来源**。指出测试之外的依据，如经确认的目标或验收标准、稳定接口契约、领域不变量、适用的外部规范或独立确认的正确用户行为。只有当前或历史实现、其他测试或模拟返回值支持时，记录“契约待确认”，交由维护者确认具体预期。
2. **行为正确性**。沿真实入口检查断言能否发现目标错误。若独立依据表明断言要求错误行为，应指出需要修改的测试。若行为出错时断言仍能通过，应说明缺失的验收证据。测试通过只说明实现满足该断言。
3. **约束范围**。判断调用顺序、中间状态、提示时机、重试次数等细节是否为保证目标行为所必需。若另一种满足契约的实现会因附带细节不同而失败，指出应收窄的断言。使用模拟对象或内部断言本身不构成问题。

## 形成结论并复审

- 按模板用中文撰写一份报告。引用新增或修改的测试时，给出测试位置、关键预期依据及验证边界。将测试问题写在模板第二节，明确缺少验收证据、契约待确认或已证实行为错误及其影响；依据证据区分必须修改与建议。已确认的测试证据写入第三节，运行记录写入附录。
- 阻断项按模板写明证据、复现或静态触发路径、影响、修改方向和测试缺口。编号连续，复审沿用原编号。要求作者修复并提交复审时，列出须重新验证的场景。
- 获授权向 GitHub 提交审查时，将报告全文作为 PR 审查回复，只提交一次，核对提交结果。要求修改、建议通过、仅建议或证据不足分别对应请求更改、批准、评论。更新提交后须复核相关结论。
- 超过三次审查仍未通过时，报告项目负责人，由负责人组织讨论是否继续审查或关闭 PR，并评估提交者和审查者的能力与经验是否符合要求。最终合并决定由维护者作出。
